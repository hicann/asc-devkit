# MatmulConfig

The template parameter **MatmulConfig** is used to configure the Matmul template information and related parameters. If the Norm template is not configured, the Norm template is enabled by default. For details about the Norm template, see [Table Template features](#table6981133810309). For the parameter description of **MatmulConfig**, see [Table 2](#matmulconfig-params). **MatmulConfig** can be defined as follows:

-   This parameter can be set to one of the provided templates. Currently, the value range of the MatmulConfig template is [CFG\_NORM, CFG\_MDL, CFG\_IBSHARE\_NORM, MM\_CFG\_BB], corresponding to the default Norm, MDL, IBShare, and BasicBlock templates. For details about each template, see [Table 1](#table6981133810309).
<a id="get-matmulconfig-api"></a>
-   This template parameter can be used to customize template parameter configurations and obtain customized templates based on various interfaces for obtaining templates. The APIs for obtaining templates include [GetNormalConfig](GetNormalConfig.md), [GetMDLConfig](GetMDLConfig.md), [GetSpecialMDLConfig](GetSpecialMDLConfig.md), [GetIBShareNormConfig](GetIBShareNormConfig.md), and [GetBasicConfig](GetBasicConfig.md).
-   In addition, **MatmulConfig** can be split into level-2 sub-Configs ([MatmulShapeParams](GetMMConfig.md#table16317184295116), [MatmulQuantParams](GetMMConfig.md#table8313111211573), [MatmulBatchParams](GetMMConfig.md#table15129204644) and [MatmulFuncParams](GetMMConfig.md#table66217141862)). The [GetMMConfig](GetMMConfig.md) API is used to set the required level-2 sub-Configs and [MatmulConfigMode](GetMMConfig.md#table17837129144319), you can flexibly obtain the customized template parameter **MatmulConfig**.

**Table 1** Template features

<a name="table6981133810309"></a>
| Template| Implementation| Advantage| Recommended Usage Scenario|
| --- | --- | --- | --- |
| Norm | L1 can cache multiple base blocks. MTE2 moves base blocks from GM to L1 multiple times, with one base block moved each time. The moved base blocks are not cleared. For example, if [depthA1](../Matmul-Tiling/tcubetiling_structure.md#tcubetiling-struct) is set to **6** in the Tiling structure indicates that six basic blocks of matrix A are moved to L1, one basic block is moved at a time, and MTE2 moves data six times.| The MTE1 pipeline can be started in advance, because the subsequent computation of MTE1 can be performed after one base block is moved.| The Norm template is enabled by default.|
| MDL and SpecialMDL| L1 can cache multiple base blocks. The data movement of MTE2 from GM to L1 is a one-time large-packet movement. For example, if [depthA1](../Matmul-Tiling/tcubetiling_structure.md#tcubetiling-struct) is set to **6** in the Tiling structure indicates that six basic blocks of matrix A are moved to L1 at one time and MTE2 moves data once. For details about the differences between the MDL template and the SpecialMDL template, see [Table 2](#matmulconfig-params).| In common large-shape scenarios, this parameter can be used reduce cyclic data movement using MTE2 to improve performance.| Large-shape scenarios|
| IBShare | In the MIX scenario, when the GM addresses of matrix A or matrix B are the same, L1 Buffer is shared to reduce MTE2 movement.| This reduces MTE2 movement and improves performance.| The GM addresses of matrix A or matrix B of multiple AIVs are the same in the MIX scenario.<br><br>Note: The IBShare template requires that the A/B matrix multiplexed by multiple AIVs must be fully loaded on the L1 buffer.|
| BasicBlock | If there is no tail block and the base block size is fixed, the [GetBasicConfig](GetBasicConfig.md) API can be used to configure the size of input base blocks, and fix the size of the matrix moved by MTE1 each time and the size of the matrix computed by matrix multiplication each time to reduce the parameter computation workload.| This reduces the parameter computation overhead during MTE1 matrix movement and matrix multiplication computation.| There is no tail block, and the size of the base block (baseM, baseN) is determined.|
| SpecialBasicBlock | If there is no tail block and the shape size of the basic block and single core is determined, you can configure the **MatmulConfig** parameter to further eliminate the header overhead scalar calculation based on the BasicBlock template.| This reduces the parameter computation overhead during MTE1 matrix movement and matrix multiplication computation, and further eliminates the header overhead scalar computation.| There is no tail block, and the size of the base block (baseM, baseN) and the shape size of the single core (singleCoreM, singleCoreN) are determined.<br><br>Note: In the same scenario, you are advised to use [constant quantization](GetMatmulApiTiling.md) to achieve better performance.|

| enableKdimReorderLoad | Whether to enable staggered data loading along the K axis. When Matmul computation is performed based on the same tiling parameters, if the left or right matrices of multiple cores are the same and stored in the global memory, the cores usually access the same address at the same time to load matrix data. This causes access conflicts at the same address and affects performance. After staggered data loading along the K axis is enabled, when multiple cores execute Matmul computation, they will try to access different global memory addresses of the matrix at the same time. This reduces the probability of address access conflicts and improves performance. This parameter is supported only by the MDL template.
