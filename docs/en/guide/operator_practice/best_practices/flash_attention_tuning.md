Based on the implementation of the FlashAttention backward computation flow, the overall computation flow is briefly described as follows. Users who are interested in the algorithm of this operator can simply understand it without paying special attention.

1.  Recompute p. In this step, the softmax result p in the FlashAttention flow is recomputed, and the result is stored in the UB.

    ![](../../figures/zh-cn_formulaimage_0000002098517589.png)

2.  Compute dp. This computation includes a matmul computation and a dropout computation. In the matmul computation, the left cube is dy, and the right cube is the transposed value.

    ![](../../figures/zh-cn_formulaimage_0000002062439026.png)

3.  Calculate ds. In this calculation, the inputs of FlashSoftmaxGrad are dy and the forward output attention\_in. The result is subtracted from dp, and the final result is multiplied by p to obtain ds.

    ![](../../figures/zh-cn_formulaimage_0000002098517777.png)

4.  Calculate dq. In this calculation, the ds result is multiplied with key through Matmul, and the result is multiplied by scale to obtain dq.

    ![](../../figures/zh-cn_formulaimage_0000002062439086.png)

5.  Calculate dk. In this calculation, the transposed ds result is multiplied with query through matmul, and the result is multiplied by scale to obtain dk.

    ![](../../figures/zh-cn_formulaimage_0000002098517781.png)

6.  Calculate dv. In this calculation, the p result is processed through drop, transposed, and then multiplied with dy through matmul.

    ![](../../figures/zh-cn_formulaimage_0000002062439090.png)

## Obtaining Performance Data<a name="section4647105095111"></a>

The pipeline optimization analysis tools include CAModel and Profiling, which analyze performance from two aspects. First, the proportion of each pipeline is analyzed based on the Profiling data generated by the Profiling tool. Second, the parallelism of each pipeline is analyzed based on the dotting chart generated by the CAModel tool.

## Analyzing the Main Bottleneck<a name="section371410542511"></a>

Determine the performance bottlenecks by observing and analyzing the pipeline diagram and Profiling data, combined with optimization experience. Different bottlenecks may appear at different stages of the optimization process, and continuous optimization is required to achieve the best performance.

-   Based on optimization experience, there may be some unnecessary performance overhead between loops, and the more loops there are, the worse the performance may be. When the maximum space limit of the Unified Buffer (UB) is met, the larger the base block into which the UB is divided, the fewer the loops. In the operator, the UB buffer size is allocated through the **InitBuffer** API.

    ```
    pipe->InitBuffer(ubBuffer, 120 * 1024);  
    pipe->InitBuffer(tmpBuffer, 30 * 1024);  
    pipe->InitBuffer(vecClc3, 8 * 1024);
    ```

    As shown in the preceding code, the second parameter of the **InitBuffer** API indicates the size occupied by the buffer, and the sum of all buffer sizes is the total space occupied. Here, 120 \* 1024 + 30 \* 1024 + 8 \* 1024 = 158KB < UB Size, which means the UB space is not fully utilized.

-   Observe the following pipeline diagram. Green indicates the pipeline on the vector side, and orange indicates the pipeline on the cube side. It can be seen that there are large gaps in the pipelines on both sides, and the CV pipelines are largely not parallel. Therefore, CV pipeline optimization needs to be considered.

    **Figure 3**  Operator pipeline before optimization<a name="fig101953515215"></a>  
    ![](../../figures/op_pipe_before.png "Operator pipeline before optimization")

-   For scenario 1 above, in the causal scenario, the cores may be unevenly distributed. As shown in the following figure, after **atten\_mask** masking, the red part is the part that the operator needs to compute, and the green part does not need to be computed. If the cores are not divided by the number of base blocks but by the size of the first axis, 8 (rows), and it is assumed that they are evenly divided among 9 cores, with each core processing ceil\(8 / 9\) = 1 row, then the first core only needs to process 1 base block, but the eighth core needs to process 8 base blocks, resulting in obvious load imbalance. ## Designing the Optimization Solution<a name="section7611135813517"></a>

-   Optimization point 1: Adjust the tiling base block

    On the premise of meeting the UB space size limit, the tiling base block should be split as large as possible. As shown in the following figure, before optimization, the computation is split by \(64, 128\), requiring a total of 32 loop computations.

    **Figure 7** Computation base block and number of iterations before optimization<a name="fig96297211869"></a>  
    ![](../../figures/bb_before.png "Computation base block and number of iterations before optimization")

    Considering that the UB space is not fully used, the base block is adjusted to \(128, 128\). As shown in the following figure, after optimization, only 16 loop computations are required, and the operator performance is doubled after the split.

    **Figure 8** Computation base block and number of iterations after optimization<a name="fig1872271218713"></a>  
    ![](../../figures/bb_after.png "Computation base block and number of iterations after optimization")

-   Optimization point 2: CV pipeline parallelism

    In the FAG operator, cube computation is faster than vector computation and there is a dependency between them. To reduce the number of communications between CVs, a caching mechanism is used to make matmul compute multiple blocks in advance. The caching mechanism here refers to computing multiple base blocks of mm at a time and caching them to GM. In the following code, the **singleCoreM** and **singleCoreN** sizes set by **SetTail** are multiples of **BaseM** and **BaseN** respectively, that is, matmul initiates the computation of multiple base blocks at a time to cache the Matmul results, and the vector side retrieves the matmul results in multiple passes.

    ```
    mm3.SetTail(s2CvExtend, -1, preS1Extend);  
    mm3.SetTensorA(mulWorkSpaceGm[pingpongIdx * coreNum * cubeBaseMN + cBlockIdx * cubeBaseMN], true); 
    mm3.SetTensorB(queryGm[mm2aTensorOffsetCv]);  
    mm3.template IterateAll<false>(dkWorkSpaceGm[bTensorOffsetCv], true);
    ```

    **Figure 9** Pipeline that completes mm1/mm2/mm3 caching<a name="fig183930515717"></a>  
    ![](../../figures/mm_cache_pipe.png "Pipeline that completes mm1-mm2-mm3 caching")

    The preceding figure shows the pipeline that implements the caching of mm1, mm2, and mm3. The parallelism is improved and the CV interval is reduced, which improves the operator performance.

    **Figure 10**  Inserting vector computation into the interval of vector waiting for cube pipeline<a name="fig11911442083"></a>  
    ![](../../figures/vec_cube_pipe.png "Inserting Vector computation into the intervals of Vector waiting for Cube pipeline")

    Based on the optimization of caching mm1/mm2/mm3, in the interval where the current round of Vector computation waits for the cube pipeline, the vector computation of the next loop iteration is inserted, as shown in the preceding figure. This increases the parallelism between the vector pipeline and the cube pipeline, which is reflected in the pipeline diagram as denser vector computation. The pseudocode of the original computation process and the pseudocode of inserting the next round of vector computation into the CV interval are shown in the following two blocks, respectively.

    ```
    // Pseudocode of the original computation process 
    // mm1 computation;
    dropout();
    Sub();
    // mm2 computation;
    Softmax();
    AttenMask();
    ...
    ```

    ```
    // Pseudocode of inserting the next round of Vector computation into the interval of vector waiting for cube pipeline 
    // mm1 computation;
    dropout();
    Sub();
    dropout(); // Vector computation of the next loop iteration
    Sub();  // Vector computation of the next loop iteration
    // mm2 computation;
    Softmax();
    AttenMask();
    ...
    ```

-   Optimization point 3: load balancing across cores

    **Figure 11** Computation amount of each core before causal scenario optimization<a name="fig093211251714"></a>  
    ![](../../figures/causal_before.png "Computation amount of each core before causal scenario optimization")

    **Figure 12** Computation amount of each core after causal scenario optimization<a name="fig7236118193316"></a>  
    ![](../../figures/causal_after.png "Computation amount of each core after causal scenario optimization")

    Try to make the computation amount of each core uniform to achieve load balancing. The core partitioning and the computation amount of each core before optimization are shown in [Figure 11 Computation amount of each core before causal scenario optimization](#fig093211251714). Cores are partitioned by the size 8 (rows) of the first axis and evenly distributed to nine cores. Each core computes ceil\(8/9\)=1 rows. The first core computes only one base block, while the eighth core computes eight base blocks. After optimization, as shown in [Figure 12 Computation amount of each core after causal scenario optimization](#fig7236118193316), the 36 base blocks marked in red are evenly distributed to each core, so that each core computes four base blocks, doubling the performance.

-   Optimization point 4: FixPipe optimization

    According to the collected Profiling data, the Cube FixPipe ratio is as high as 81%, indicating a severe bound (reaching the upper limit). The CAModel tool reports many abnormal 128B transfers. After checking the code, it is found that the workspace address is not 512B-aligned.

    **Figure 13** Profiling data before scenario 1 optimization<a name="fig93221731191012"></a>  
    ![](../../figures/scene1_bef.png "Profiling data before scenario 1 optimization")

    In the code implementation, the SetGlobalBuffer API is used to set the start address of the workspace. If the start address is not 512B-aligned, the transfer efficiency is very low. You can enforce [GM address 512-byte alignment](../simd_operator_optimization/memory_access/gm_address_512b_alignment.md) to avoid this. In the following code, ADDR\_ALIGN\_SIZE is 512.

    ```
    // init workspace address  
    syncGlobal.SetGlobalBuffer((__gm__ int32_t*)workspace);  
    uint64_t workspaceOffsets = SYNC_GLOBAL_WORKSPACE_SIZE;  
    dqWorkSpaceGm.SetGlobalBuffer((__gm__ float*)workspace + workspaceOffsets / sizeof(T2));  
    workspaceOffsets = (workspaceOffsets + qPostBlockTotal * sizeof(float) + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE;  dkWorkSpaceGm.SetGlobalBuffer((__gm__ float*)workspace + workspaceOffsets / sizeof(T2));  
    workspaceOffsets = (workspaceOffsets + kvPostBlockTotal * sizeof(float) + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE;  dvWorkSpaceGm.SetGlobalBuffer((__gm__ float*)workspace + workspaceOffsets / sizeof(T2));  
    workspaceOffsets = (workspaceOffsets + kvPostBlockTotal * sizeof(float) + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE; 
    // matmul1 and matmul2 workspace size  
    matmulWorkspaceSize = cubeBaseMN * sizeof(float); 
    mm1WorkspaceGm.SetGlobalBuffer((__gm__ T2*)(workspace + workspaceOffsets + cBlockIdx * matmulWorkspaceSize));  mm2WorkspaceGm.SetGlobalBuffer((__gm__ T2*)(workspace + workspaceOffsets + coreNum * matmulWorkspaceSize + cBlockIdx * matmulWorkspaceSize));   // drop workspace offset  
    workspaceOffsets = (workspaceOffsets + coreNum * cubeBaseMN * sizeof(float) * INPUT_NUMS + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE;  
    dropWorkSpaceGm.SetGlobalBuffer((__gm__ T1*)workspace + workspaceOffsets / sizeof(T1));   
    // mul workspace offset  
    workspaceOffsets = (workspaceOffsets + coreNum * cubeBaseMN * sizeof(half) * 2 + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE;  
    mulWorkSpaceGm.SetGlobalBuffer((__gm__ T1*)workspace + workspaceOffsets / sizeof(T1));
    ```

    After the code is modified and the workspace address is 512B-aligned, the FixPipe time is halved.

    **Figure 14** Profiling data after scenario 1 optimization<a name="fig17483105414106"></a>  
    ![](../../figures/scene1_aft.png "Profiling data after scenario 1 optimization")

    Based on the following Profiling data and pipeline diagram, it can be seen that the operator is MTE2 bound, and the transfer time of some MTE2 operations is abnormal.

    **Figure 15**  Profiling data of scenario 2<a name="fig932111118913"></a>

    After the input data layout is changed from BSH to BNSD, the data transfer becomes continuous, and data no longer needs to be read by skipping addresses. As a result, the transfer efficiency is doubled, and the duration of some abnormal transfers is reduced by half.

## Verifying the Performance Gains of the Optimization Solution<a name="section8934151165215"></a>

-   Adjusting the tiling base block: The theoretical evaluation shows that the larger the Vector block, the fewer the computation and data transfer loops, and the more fully the transfer bandwidth and vector computing power are utilized. After the base block size is increased from \(64, 128\) to \(128, 128\), the performance is doubled, which is consistent with the theoretical analysis.
-   CV pipeline parallelism: The time hidden by the CV pipeline is exactly the performance improvement, which meets the expected gains.
-   Inter-core load balancing: The factor by which the computation amount of the most heavily loaded core is reduced after optimization is the expected performance improvement. In this case, the computation amount of the most heavily loaded core before optimization is 8 blocks, and 4 blocks after optimization. The actual performance is doubled, which meets the expected gains.
-   FixPipe optimization: The Profiling data shows that the FixPipe ratio is 0.8 before optimization and 0.55 after optimization. The measured operator performance is improved by 45%, which is consistent with the theoretical analysis.
-   MTE2 optimization: The Profiling data shows that the MTE2 ratio is 0.52 before optimization and is reduced by half after optimization. The measured operator performance is improved by 30%, which is consistent with the theoretical analysis.
