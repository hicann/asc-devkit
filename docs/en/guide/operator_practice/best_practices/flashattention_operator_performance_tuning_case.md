Based on the implementation of the FlashAttention backward computation process, the overall computation process is briefly described as follows. Users who are interested in the algorithm of this operator can simply understand it without focusing on the details.

1.  Recompute p. In this step, the softmax result p in the FlashAttention process is recomputed, and the computation result is stored in UB.

    ![](../../figures/zh-cn_formulaimage_0000002098517589.png)

2.  Compute dp. This computation includes matmul computation and dropout computation. In the matmul computation, the left matrix is dy, and the right matrix is the transposed value.

    ![](../../figures/zh-cn_formulaimage_0000002062439026.png)

3.  Calculate ds. In this computation, the inputs of FlashSoftmaxGrad are dy and the forward output attention\_in. This result is subtracted from dp, and the final result is multiplied with p to obtain the result ds.

    ![](../../figures/zh-cn_formulaimage_0000002098517777.png)

4.  Calculate dq. In this computation, the ds result is multiplied with key through matmul, and the result is multiplied with scale to obtain the result dq.

    ![](../../figures/zh-cn_formulaimage_0000002062439086.png)

5.  Calculate dk. In this computation, the transposed ds result is multiplied with query through matmul, and the result is multiplied with scale to obtain the result dk.

    ![](../../figures/zh-cn_formulaimage_0000002098517781.png)

6.  Calculate dv. In this computation, the p result is processed through drop, transposed, and then multiplied with dy through matmul.

    ![](../../figures/zh-cn_formulaimage_0000002062439090.png)

## Obtaining Performance Data<a name="section4647105095111"></a>

The pipeline optimization analysis tools include CAModel and Profiling tools, which analyze from two aspects: the first is to analyze the proportion of each pipeline from the Profiling data generated by the Profiling tool, and the second is to analyze the parallelism of each pipeline from the dot chart generated by the CAModel tool.

## Analyzing the Main Bottleneck<a name="section371410542511"></a>

Determine the performance bottlenecks by observing and analyzing the pipeline chart and Profiling data, combined with optimization experience. Different bottlenecks may appear at different stages of the optimization process, and continuous optimization is required to achieve the best performance.

-   Based on optimization experience, there may be some unnecessary performance overhead between loops, and the more loops there are, the worse the performance may be. When the maximum UB space limit is satisfied, the larger the base blocks into which the UB is divided, the fewer the loops. In the operator, the UB buffer size is allocated through the InitBuffer API.

    ```
    pipe->InitBuffer(ubBuffer, 120 * 1024);  
    pipe->InitBuffer(tmpBuffer, 30 * 1024);  
    pipe->InitBuffer(vecClc3, 8 * 1024);
    ```

    As shown in the code above, the second parameter of the InitBuffer API indicates the size occupied by the buffer, and the sum of all buffer sizes is the total space occupied. Here, 120 \* 1024 + 30 \* 1024 + 8 \* 1024 = 158KB < UB Size, which means the UB space is not fully utilized.

-   Observe the following pipeline chart. Green indicates the pipeline on the Vector side, and orange indicates the pipeline on the Cube side. It can be seen that both pipelines have large gaps, and the CV pipelines are largely not parallelized. Therefore, CV pipeline optimization needs to be considered.

    **Figure 3**  Operator pipeline before optimization<a name="fig101953515215"></a>  
    ![](../../figures/operator_pipeline_before_optimization.png "Operator pipeline before optimization")

-   For scenario 1 above, in the causal scenario, the distribution across cores may be uneven. As shown in the following figure, after the atten\_mask masking, the red part is the part that the operator needs to compute, and the green part does not need to be computed. If the cores are not divided by the number of base blocks but by the size of the first axis, 8 (rows), and it is assumed that the cores are evenly distributed across 9 cores, with each core computing ceil\(8 / 9\) = 1 row, then the first core only needs to compute 1 base block, but the eighth core needs to compute 8 base blocks, resulting in obvious load imbalance. Therefore, it is necessary to consider evenly distributing the red blocks to multiple cores for computation.

## Designing an Optimization Solution<a name="section7611135813517"></a>

-   Optimization point 1: Adjust the tiling base blocks

    Provided that the UB space size limit is satisfied, the tiling base blocks should be made as large as possible. As shown in the following figure, before optimization, the computation is split by \(64, 128\), requiring a total of 32 loop computations.

    **Figure 7**  Computation base blocks and count before optimization<a name="fig96297211869"></a>  
    ![](../../figures/computation_basic_blocks_and_count_before_optimization.png "Computation base blocks and count before optimization")

    Considering that the UB space is not fully used, the base blocks are adjusted to \(128, 128\). As shown in the following figure, after optimization, only 16 loop computations are required, and the operator performance is doubled after the split.

    **Figure 8**  Computation base blocks and count after optimization<a name="fig1872271218713"></a>  
    ![](../../figures/computation_basic_blocks_and_count_after_optimization.png "Computation base blocks and count after optimization")

-   Optimization point 2: CV pipeline parallelism

    In the FAG operator, Cube computation is faster than Vector computation and there is a dependency between them. To reduce the number of communications between CV, a caching mechanism is used to make matmul compute multiple blocks in advance. The caching mechanism here refers to computing multiple base blocks at a time with mm and caching them to GM. In the following code, the singleCoreM and singleCoreN sizes set by SetTail are multiples of BaseM and BaseN respectively, that is, matmul initiates the computation of multiple base blocks at a time to cache the matmul results, and the Vector side retrieves the matmul results in multiple passes.

    ```
    mm3.SetTail(s2CvExtend, -1, preS1Extend);  
    mm3.SetTensorA(mulWorkSpaceGm[pingpongIdx * coreNum * cubeBaseMN + cBlockIdx * cubeBaseMN], true); 
    mm3.SetTensorB(queryGm[mm2aTensorOffsetCv]);  
    mm3.template IterateAll<false>(dkWorkSpaceGm[bTensorOffsetCv], true);
    ```

    **Figure 9**  Pipeline that completes mm1/mm2/mm3 caching<a name="fig183930515717"></a>  
    ![](../../figures/pipeline_that_completes_mm1_mm2_mm3_caching.png "Pipeline that completes mm1/mm2/mm3 caching")

    As shown in the preceding figure, this is the pipeline chart that implements the caching of mm1, mm2, and mm3. The parallelism is improved and the CV interval is reduced, which improves the operator performance.

    **Figure 10**  Inserting Vector computation into the intervals of Cube pipelines such as Vector<a name="fig11911442083"></a>  
    ![](../../figures/insert_vector_computation_into_intervals_of_cube_pipelines_such_as_vector.png "Inserting Vector computation into the intervals of Cube pipelines such as Vector")

    Based on the optimization of caching mm1/mm2/mm3, the Vector computation of the next loop iteration is inserted into the intervals of the Cube pipeline while the current Vector computation waits, as shown in the preceding figure. This increases the parallelism between the Vector pipeline and the Cube pipeline, which is reflected in the pipeline chart as denser Vector computation. The pseudocode of the original computation process and the pseudocode with the next iteration's Vector computation inserted into the CV intervals are shown in the following two blocks, respectively.

    ```
    // Pseudocode of the original computation process
    // mm1 computation;
    dropout();
    Sub();
    // mm2 computation;
    Softmax();
    AttenMask();
    ...
    ```

    ```
    // Pseudocode of inserting the next loop iteration's Vector computation into the intervals of Cube pipelines such as Vector
    // mm1 computation;
    dropout();
    Sub();
    dropout(); // Vector computation of the next loop iteration
    Sub();  // Vector computation of the next loop iteration
    // mm2 computation;
    Softmax();
    AttenMask();
    ...
    ```

-   Optimization point 3: Load balance for each core

    **Figure 11**  Computation amount of each core before optimization in the causal scenario<a name="fig093211251714"></a>  
    ![](../../figures/computation_amount_per_core_before_optimization_in_causal_scenario.png "Computation amount of each core before optimization in the causal scenario")

    **Figure 12**  Computation amount of each core after optimization in the causal scenario<a name="fig7236118193316"></a>  
    ![](../../figures/computation_amount_per_core_after_optimization_in_causal_scenario.png "Computation amount of each core after optimization in the causal scenario")

    Try to make the computation amount of each core uniform and balanced. The core allocation and computation amount of each core before optimization are as shown in [Figure 11 Computation amount of each core before optimization in the causal scenario](#fig093211251714). Cores are allocated by the size 8 (rows) of the first axis and evenly distributed to 9 cores, with each core computing ceil(8/9)=1 row. The first core computes only 1 base block, while the eighth core computes 8 base blocks. After optimization, as shown in [Figure 12 Computation amount of each core after optimization in the causal scenario](#fig7236118193316), the red blocks total 36 base blocks, which are evenly distributed to each core, with each core computing 4 base blocks, achieving a 2x performance improvement.

-   Optimization point 4: FIXPIPE optimization

    According to the collected Profiling data, Cube FixPipe accounts for as high as 81%, causing a severe bound (reaching the upper limit). The CAModel tool output shows many abnormal 128B transfers. After checking the code, it is found that the workspace address is not 512B-aligned.

    **Figure 13**  Profiling data before optimization in scenario 1<a name="fig93221731191012"></a>  
    ![](../../figures/profiling_data_before_optimization_in_scenario_1.png "Profiling data before optimization in scenario 1")

    In the code implementation, the SetGlobalBuffer API is used to set the start address of the workspace. If the start address is not 512B-aligned, the transfer efficiency will be very low. This can be avoided by enforcing [512-byte alignment of the GM address](../simd_operator_optimization/memory_access/gm_address_512b_alignment.md). In the following code, ADDR_ALIGN_SIZE is 512.

    ```
    // init workspace address  
    syncGlobal.SetGlobalBuffer((__gm__ int32_t*)workspace);  
    uint64_t workspaceOffsets = SYNC_GLOBAL_WORKSPACE_SIZE;  
    dqWorkSpaceGm.SetGlobalBuffer((__gm__ float*)workspace + workspaceOffsets / sizeof(T2));  
    workspaceOffsets = (workspaceOffsets + qPostBlockTotal * sizeof(float) + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE;  dkWorkSpaceGm.SetGlobalBuffer((__gm__ float*)workspace + workspaceOffsets / sizeof(T2));  
    workspaceOffsets = (workspaceOffsets + kvPostBlockTotal * sizeof(float) + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE;  dvWorkSpaceGm.SetGlobalBuffer((__gm__ float*)workspace + workspaceOffsets / sizeof(T2));  
    workspaceOffsets = (workspaceOffsets + kvPostBlockTotal * sizeof(float) + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE; 
    // matmul1 and matmul2 workspace size  
    matmulWorkspaceSize = cubeBaseMN * sizeof(float); 
    mm1WorkspaceGm.SetGlobalBuffer((__gm__ T2*)(workspace + workspaceOffsets + cBlockIdx * matmulWorkspaceSize));  mm2WorkspaceGm.SetGlobalBuffer((__gm__ T2*)(workspace + workspaceOffsets + coreNum * matmulWorkspaceSize + cBlockIdx * matmulWorkspaceSize));   // drop workspace offset  
    workspaceOffsets = (workspaceOffsets + coreNum * cubeBaseMN * sizeof(float) * INPUT_NUMS + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE;  
    dropWorkSpaceGm.SetGlobalBuffer((__gm__ T1*)workspace + workspaceOffsets / sizeof(T1));   
    // mul workspace offset  
    workspaceOffsets = (workspaceOffsets + coreNum * cubeBaseMN * sizeof(half) * 2 + ADDR_ALIGN_SIZE) / ADDR_ALIGN_SIZE * ADDR_ALIGN_SIZE;  
    mulWorkSpaceGm.SetGlobalBuffer((__gm__ T1*)workspace + workspaceOffsets / sizeof(T1));
    ```

    After modifying the code so that the workspace address is 512B-aligned, the FixPipe time is halved.

    **Figure 14**  Profiling data after optimization in scenario 1<a name="fig17483105414106"></a>  
    ![](../../figures/profiling_data_after_optimization_in_scenario_1.png "Profiling data after optimization in scenario 1")

## Verifying the Performance Gains of the Optimization Solution<a name="section8934151165215"></a>

-   Adjusting the tiling base blocks: The theoretical evaluation shows that the larger the Vector block, the fewer the computation and data transfer loops, while fully utilizing the transfer bandwidth and Vector computing power. After the base block size is increased from \(64, 128\) to \(128, 128\), the performance doubles, which is consistent with the theoretical analysis.
-   CV pipeline parallelism: The time masked by the CV pipeline is exactly the performance gained, which meets the expected benefit.
-   Inter-core load balancing: The factor by which the computation amount of the most heavily loaded core is reduced before optimization is the expected performance improvement. In this case, the computation amount of the most heavily loaded core before optimization is 8 blocks, and after optimization it is 4 blocks, so the actual performance improvement doubles, which meets the expected benefit.
-   FixPipe optimization: The Profiling data shows that FixPipe accounts for 0.8 before optimization and 0.55 after optimization. The measured operator performance improves by 45%, which is consistent with the theoretical analysis.
-   MTE2 optimization: The Profiling data shows that MTE2 accounts for 0.52 before optimization, and its proportion is reduced by half after optimization. The measured operator performance improves by 30%, which is consistent with the theoretical analysis.
