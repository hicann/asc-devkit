# Atomic Operation Instruction Optimization

<!-- md-trans-meta sourceCommit=58025861f63fbbf547b32a1e64731b761bd8937e translatedAt=2026-10-23T13:12:58.184Z pushedAt=2026-11-03T07:05:13.374Z nl=2 -->

[Priority] High

[Description] In SIMT programming mode, when multiple threads update the same memory address, the [atomic operation API](../../../../api/SIMT-API/atomic_operations/atomic_operations_intro.md) must be used to ensure correct update results. Atomic operations are high-cost instructions, and their execution time is determined by two factors: first, atomic operations on the same address can only be queued and executed sequentially; second, the processing overhead of a single atomic instruction.


An atomic operation must complete three steps: read the old value, compute the new value, and write back the new value. If multiple threads update the same address simultaneously without protection, multiple threads may read the same old value, and the result written back later may overwrite the result written back earlier, causing some updates to be lost. To avoid such loss, atomic operations ensure that the three steps are completed as an indivisible whole. Therefore, multiple atomic operations on the same address cannot be executed in parallel and can only be queued and executed sequentially. The more atomic operations queued on the same address, the higher the total execution time.

Therefore, atomic operation optimization focuses on two aspects: reducing the number of atomic operations queued on the same address and lowering the processing overhead of a single atomic instruction. Specifically, optimization can be performed in the following ways:

- **Migrate atomic operations from GM to Unified Buffer (UB) through hierarchical reduction**: Global Memory (GM) is located outside the AI Core, with a longer access path and higher latency; UB is located inside the AI Core, with a shorter access path and lower latency. In addition, UB is private to a thread block, so UB atomic operations of different thread blocks do not compete with each other. Performing local reduction in the UB of each thread block first and then aggregating to GM can simultaneously reduce the per-operation processing overhead and the number of atomic operations queued on the same address.
- **Do not use the return value of atomic operations unless necessary**: Whether the return value is used affects the atomic instruction generated by the compiler. When the return value is not used, the compiler can generate optimized instructions with lower processing overhead.
- **Distribute the destination addresses of atomic operations on GM**: When atomic operations must be executed on GM due to business requirements, since GM atomic operations use a 128B Sector as the processing granularity, processing efficiency is low when destination addresses are concentrated in the same Sector. Use padding or other methods to make the atomic targets cover more Sectors. This method applies only to GM, not to atomic operations on UB.

[Sample introduction] This section uses two samples to illustrate the above optimization directions:

- [asc_atomic_add API performance comparison sample](../../../../../../examples/03_simt_api/02_features/01_api_features/02_atomic_operation/atomic_add_perf/README.md): Contains 16 scenarios grouped into 5 controlled experiments, quantifying the impact of memory hierarchy, atomic accumulation organization, whether the return value is used, the degree of contention on the same address, and the Sector distribution of destination addresses on atomic add performance. Each controlled group changes only one attribute while keeping other configurations consistent.
- [Histogram atomic operation performance tuning sample](../../../../../../examples/03_simt_api/03_best_practices/03_instruction_optimizations/atomic_histogram/README.md): Performs histogram statistics on a uint8_t byte stream of shape [262144] and outputs uint32_t count results for 256 buckets. The sample launches 64 thread blocks, each with 2048 threads, and compares two implementations—"all threads directly updating the GM histogram" versus "first performing statistics on the UB of each thread block and then aggregating to GM"—to illustrate the optimization effect of hierarchical reduction.

## Migrating Atomic Operations from GM to UB Through Hierarchical Reduction

[Negative example] All threads directly perform atomic accumulation on the global histogram in GM.

**Figure 1** GM global counting diagram

![](../../../figures/atomic_operation_gm_global_count.png)

```cpp
__global__ __launch_bounds__(THREADS_PER_BLOCK) void histogram_gm_global(
    uint32_t* histogram, const uint8_t* input, uint32_t byte_count)
{
    uint32_t index = blockIdx.x * blockDim.x + threadIdx.x;
    const uint32_t stride = gridDim.x * blockDim.x;
    for (; index < byte_count; index += stride) {
        asc_atomic_add(&histogram[input[index]], 1U);
    }
}
```

In the above implementation, each thread traverses the input bytes in a grid-stride manner (that is, each thread uses the total number of threads as a fixed stride to process bytes at different positions in the input in multiple passes), and directly performs atomic increment by 1 on the corresponding bucket of the GM histogram. All 262144 atomic updates are concentrated on 256 GM addresses, with an average of 1024 atomic additions queued per address, and each atomic addition operates on GM, which has high access latency. The performance data of this implementation is as follows:

| Count Position | Task Duration (μs) |
| :---: | :---: |
| GM | 424.22 |

[Positive example] Each thread block first maintains a private histogram in UB, and finally aggregates it into GM.

**Figure 2** UB block-local counting diagram

![](../../../figures/atomic_operation_ub_block_local_count.png)

```cpp
__global__ __launch_bounds__(THREADS_PER_BLOCK) void histogram_ub_block_local(
    uint32_t* histogram, const uint8_t* input, uint32_t byte_count)
{
    __ubuf__ uint32_t block_histogram[HISTOGRAM_BIN_COUNT]; // __ubuf__ indicates that this array resides in UB on-chip storage.

    // Clear the UB histogram cooperatively by all threads in the thread block.
    for (uint32_t bin_index = threadIdx.x; bin_index < HISTOGRAM_BIN_COUNT; bin_index += blockDim.x) {
        block_histogram[bin_index] = 0;
    }
    asc_syncthreads();

    // Traverse in a grid-stride manner and perform atomic accumulation on the UB histogram private to this thread block.
    uint32_t index = blockIdx.x * blockDim.x + threadIdx.x;
    const uint32_t stride = gridDim.x * blockDim.x;
    for (; index < byte_count; index += stride) {
        asc_atomic_add(&block_histogram[input[index]], 1U);
    }
    asc_syncthreads();

    // The first 256 threads each handle one bucket and atomically accumulate the thread block's local results into the final GM histogram.
    for (uint32_t bin_index = threadIdx.x; bin_index < HISTOGRAM_BIN_COUNT; bin_index += blockDim.x) {
        asc_atomic_add(histogram + bin_index, block_histogram[bin_index]);
    }
}
```

The function of the above implementation is the same as that of the negative example. The number of thread blocks, the number of threads, the input read method, and the total number of atomic updates are all identical. The only change is the memory hierarchy where the atomic operation targets reside and the contention scope. The performance data of this implementation is as follows:

| Count Position | Task Duration (μs) |
| :---: | :---: |
| UB block | 7.95 |

The performance data of the two implementations is summarized as follows:

| Writing Style | Count Position | Task Duration (μs) |
| :---: | :---: | :---: |
| **UB block reduction then aggregation to GM** | **UB** | **7.95** |
| GM global direct accumulation | GM | 424.22 |

According to the Task Duration data, after adopting hierarchical reduction, the execution time decreases from 424.22μs to 7.95μs, a decrease of approximately 98.1%, with a performance improvement of about 53x. The benefit comes from two superimposed factors:

- **Reduced processing overhead per atomic operation**: The target of the atomic operation migrates from GM to UB, shortening the access path and reducing latency. Given that atomic operations on the same address must be executed in a queue, the difference in per-operation overhead accumulates with each queued execution.
- **Significantly reduced number of queued atomic operations on the same address**: In the negative example, 256 GM addresses are shared by all threads, with an average of 1024 atomic operations executed per address. In the positive example, each thread block holds an independent 256-bucket UB histogram, the contention scope is limited to the 2048 threads within the thread block, an average of 16 atomic operations are executed per address, and the UB atomic operations across the 64 thread blocks do not contend with each other and can execute in parallel. The atomic operations ultimately applied to GM are only `64 × 256 = 16384` aggregations, a significant reduction compared to the 262144 in the negative example.

The two factors work together, and the resulting benefit significantly outweighs the additional overhead introduced by UB initialization, `asc_syncthreads()` synchronization, and GM aggregation.

> [!NOTE] Note
> UB is private storage of a thread block, with a total capacity of 256 KB. Hierarchical reduction applies to scenarios where the local reduction result can fit entirely in UB (such as the 256 buckets in this example). If the reduction target is too large to fit in UB, you can use partial reduction or process the target in segments.

## Avoiding Using the Return Value of Atomic Operations When Unnecessary

Atomic operation APIs typically return the old value at the destination address. Whether the return value is used affects the instructions generated by the compiler: when the return value is not used, the compiler can select atomic instructions with lower processing overhead; when the return value is used, the generated instructions incur higher overhead. Therefore, in scenarios where the business logic does not depend on the old value, avoid using the return value.

[Negative example] In a pure counting scenario, the return value of the atomic add is still received and used.

```cpp
// GM single address, with the return value used.
__global__ void atomic_add_gm_single_return(int32_t* counter)
{
    volatile int32_t old_value_sink = asc_atomic_add(counter, 1);
    (void)old_value_sink;
}
```

[Positive example] When the old value is not needed, discard the return value directly.

```cpp
// GM single address, without the return value used.
__global__ void atomic_add_gm_single_no_return(int32_t* counter)
{
    asc_atomic_add(counter, 1);
}
```

With the configuration of one thread block, 2048 threads per thread block, and all threads contending for the same address, the two writing styles are tested on GM and UB respectively. The performance data is as follows:

| Memory Location | Data Type | With Return Value (μs) | Without Return Value (μs) | Time Ratio |
| :---: | :---: | :---: | :---: | :---: |
| GM | int32_t | 421.59 | 159.88 | 2.64× |
| UB | int32_t | 3.17 | 2.76 | 1.15× |

According to the Task Duration data, on GM, when the return value is not used, the duration decreases from 421.59μs to 159.88μs, a decrease of approximately 62.1%; on UB, it decreases from 3.17μs to 2.76μs, a decrease of approximately 12.9%. The overhead difference caused by the instruction form is significantly amplified on GM and relatively small on UB. Therefore, in GM scenarios, it is even more important to avoid using the return value.

It should be noted that this instruction optimization is related to the data type and does not take effect for all types. With the configuration of 48 thread blocks, 256 threads per thread block, and 1024 tightly packed GM destination addresses, int32_t and int64_t are tested respectively. The performance data is as follows:

| Data Type | With Return Value (μs) | Without Return Value (μs) |
| :---: | :---: | :---: |
| int32_t | 110.95 | 1.89 |
| int64_t | 54.28 | 58.46 |

For int32_t, the time without a return value decreases to 1.89 μs, whereas for int64_t both writing styles are on the order of 54 to 58 μs with no significant difference, indicating that this instruction optimization takes effect only for int32_t. Therefore, the benefit of avoiding the return value is mainly reflected in types such as int32_t that can trigger the optimization.

## Distributing Destination Addresses of Atomic Operations on GM

This optimization method is based on the premise that atomic operations must be executed on GM. If the atomic targets can be transferred to UB through hierarchical reduction, the method described above should be preferred. Only when the business requires atomic updates to act directly on GM is it necessary to further consider the distribution of destination addresses on GM.

GM atomic operations pass through the L2 Cache hierarchy, where the "read-compute-write" operation is completed on the L2 side, with a 128B Sector as the processing granularity. When the destination addresses of atomic operations are concentrated in the same Sector, the processing efficiency is lower; when they are distributed across more Sectors, the processing efficiency is higher. Therefore, with the total number of atomic operations unchanged, the destination addresses should cover as many Sectors as possible.

A 128B Sector can hold 32 int32_t addresses (`32 × 4B = 128B`). Based on this, two address layouts can be constructed: the tightly packed layout stores 32 destination addresses contiguously, concentrating them in the same Sector; the padding layout expands the interval between adjacent destination addresses to 128B, so that the 32 destination addresses are located in 32 Sectors respectively.

**Figure 3**  Comparison of tightly packed and padding address layouts

![](../../../figures/atomic_operation_address_layout.png)

The following uses a configuration of 48 thread blocks, 256 threads per thread block, 32 int32_t GM destination addresses, 384 threads per address, and one atomic add per thread (12288 atomic adds in total) as an example. The address layout is controlled through the function parameter `target_stride` to compare the two cases of concentrated and distributed destination addresses. In the two cases, the number of destination addresses, the number of threads per address, and the total number of atomic adds are exactly the same; only the address layout differs, so the impact of Sector distribution can be reflected independently.

[Negative example] The destination addresses are tightly packed, and all atomic targets are concentrated in the same Sector.

```cpp
__global__ __launch_bounds__(MAX_THREADS_PER_BLOCK) void atomic_add_gm_case4_i32_return(
    int32_t* counters, uint64_t target_count, uint64_t threads_per_target, uint64_t target_stride)
{
    uint64_t global_tid = blockIdx.x * blockDim.x + threadIdx.x;
    uint64_t active_threads = target_count * threads_per_target;
    if (global_tid >= active_threads) {
        return;
    }

    uint64_t target_id = global_tid % target_count;
    int32_t* target = counters + target_id * target_stride;
    volatile int32_t old_value_sink = asc_atomic_add(target, 1);
    (void)old_value_sink;
}

// target_stride is set to 1: 32 consecutive int32_t addresses occupy one 128B Sector.
atomic_add_gm_case4_i32_return<<<48, 256, 0, stream>>>(counters_device, 32, 384, 1);
```

In the above implementation, the start address of the target array is aligned to 128B, and `target_stride = 1` makes the 32 destination addresses stored contiguously, all located in the same Sector. The performance data of this implementation is as follows:

| Address Layout | target_stride | Sectors Covered | Task Duration (μs) |
| :---: | :---: | :---: | :---: |
| Tightly Packed | 1 | 1 | 2164.72 |

[Positive Example] Use padding to increase the interval between destination addresses, so that the atomic targets are distributed across more Sectors.

```cpp
// The kernel function remains unchanged. Only increase target_stride from 1 to 32: the interval between adjacent destination addresses is 128B, and the 32 addresses are located in 32 Sectors respectively.
atomic_add_gm_case4_i32_return<<<48, 256, 0, stream>>>(counters_device, 32, 384, 32);
```

The kernel function of the above implementation is exactly the same as that of the negative example. The data type, whether the return value is used, thread scale, number of destination addresses, number of threads per address, and total number of atomic additions all remain consistent. Only `target_stride` is increased from 1 int32_t element to 32 int32_t elements (that is, 128B), so that the atomic targets cover 32 Sectors. The performance data of this implementation is as follows:

| Address Layout | target_stride | Sectors Covered | Task Duration (μs) |
| :---: | :---: | :---: | :---: |
| padding | 32 | 32 | 80.17 |

The performance data of the two implementations is summarized as follows:

| Writing Style | Address Layout | Sectors Covered | Task Duration (μs) |
| :---: | :---: | :---: | :---: |
| **padding to distribute destination addresses** | **padding** | **32** | **80.17** |
| Tightly packed destination addresses | Tightly Packed | 1 | 2164.72 |

According to the Task Duration data, with the workload being exactly the same, after distributing the destination addresses from 1 Sector to 32 Sectors, the execution time decreases from 2164.72 μs to 80.17 μs, a decrease of approximately 96.3%, and the performance improves by approximately 27 times. In addition to increasing the address interval, the same effect can also be achieved by increasing the number of destination addresses or aligning the structure.

> [!NOTE] Note
> This section uniformly uses the return value for comparison. As described above, when int32_t does not use the return value, instruction optimization is triggered, and its time consumption is mainly determined by this optimization, which will mask the impact of Sector distribution on performance.

The number of Sectors covered is determined by the byte interval between destination addresses. Therefore, when the number of destination addresses is the same, a data type with a larger bit width will occupy more Sectors. When evaluating the impact of the data type on atomic operation performance, it is necessary to distinguish the overhead of the bit width itself from the impact brought by changes in Sector coverage.

[Summary] Atomic operations are high-cost instructions, and their latency is determined by both the number of atomic operations queued on the same address and the processing overhead of a single instruction. Consider the following order when optimizing:

- **Prioritize hierarchical reduction to migrate atomic operations from GM to UB**: Atomic updates that can be completed in UB should avoid being executed directly on GM. When multiple thread blocks update the same target, perform local reduction in the UB of each thread block first, and then have each thread block aggregate the results to GM. This reduces the processing overhead of a single atomic operation and splits the contention scope from global to within each thread block.
- **Do not use the return value unless necessary**: When the return value is not used, the compiler can generate atomic instructions with lower overhead. This difference is especially noticeable on GM.
- **When atomic operations must be executed on GM, distribute their destination addresses**: GM atomic operations are processed at a granularity of 128B Sectors. If the destination addresses are too concentrated, processing efficiency decreases. You can use padding and structure alignment to make the atomic targets cover more Sectors.
