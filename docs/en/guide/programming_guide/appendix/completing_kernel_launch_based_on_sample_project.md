>[!NOTE] Note

The following uses the Add vector operator as an example to describe the development process of kernel launch operators in detail.

## Environment Setup<a name="section33636642419"></a>

-   Before using the Kernel Launch operator project, install the driver firmware and CANN software package by referring to [Environment Setup](../../getting_started/environment_setup.md) to prepare the development environment and runtime environment.
-   This operator project requires CMake 3.16 or later. If the installed version does not meet the requirement, update CMake by referring to the following command example, which uses CMake 3.16.0 as an example.

    ```
    wget https://cmake.org/files/v3.16/cmake-3.16.0.tar.gz 
    tar -zxvf cmake-3.16.0.tar.gz 
    cd cmake-3.16.0
     ./bootstrap --prefix=/usr 
    sudo make 
    sudo make install
    ```

## Project Directory<a name="section7363202715148"></a>

The sample directory structure is as follows:

```
AddKernelInvocationNeo
|-- cmake                                                 // CMake compilation file
|-- scripts
|  ├── gen_data.py                                     // Script for generating input data and true value data
|  ├── verify_result.py                                // Script for verifying whether the output data matches the true value data
|-- CMakeLists.txt                                        // CMake compilation configuration file
|-- add_custom.cpp                                        // Vector operator kernel implementation
|-- data_utils.h                                          // Functions for reading and writing data
|-- main.cpp                                              // Main function, the application program that calls the operator, including CPU-side and NPU-side calls
|-- run.sh                                                // Script for compiling and running the operator
```

Based on this operator project, developers perform operator development as follows:

-   Complete the kernel-side implementation of the operator.
-   Write the operator call application program main.cpp.
-   Write the CMake build configuration file **CMakeLists.txt**.

-   Modify the script file **gen\_data.py** for generating input data and true value data as needed, and the verification script **verify\_result.py** for verifying whether the output data is consistent with the true value data.
-   Modify the script **run.sh** for compiling and running the operator as needed, and execute the script to complete the compilation, execution, and result verification of the operator.

## Operator Implementation on the Kernel Side<a name="section186929199494"></a>

Refer to the kernel implementations of the vector operator, cube operator, and fusion operator in the project directory to complete the Ascend C operator implementation file.

>[!NOTE] Note
>Only one kernel function can be defined in an operator kernel implementation file.

## Operator Call Application Program<a name="section883611324486"></a>

The following code uses the add\_custom operator with a fixed shape as an example to describe how to write main.cpp, the application program for calling the operator kernel function. When implementing your own application program, you need to pay attention to the modifications caused by differences in the operator kernel function, including the kernel function name and the differences in input and output parameters, and properly arrange the corresponding memory allocation, memory copy, and file read/write operations. The calling methods of the related APIs can be reused directly.

1.  Include the required header files as needed, and use the ASCENDC\_CPU\_DEBUG macro to distinguish the header files required on the CPU side and the NPU side. Note that the NPU side needs to include aclrtlaunch\_\{kernel\_name\}.h, the header file where the declaration of the corresponding kernel function call API resides (this header file is automatically generated by the project framework). Here, kernel\_name is the name of the operator kernel function.

    ```
    #include "data_utils.h"
    #ifndef ASCENDC_CPU_DEBUG
    #include "acl/acl.h"
    #include "aclrtlaunch_add_custom.h"
    #else
    #include "tikicpulib.h"
    extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z);
    #endif
    ```

2.  Write the application program framework. The application program uses the ASCENDC\_CPU\_DEBUG macro to distinguish whether the code logic runs on the CPU side or the NPU side.

    ```
    int32_t main(int32_t argc, char* argv[])
    {
        uint32_t numBlocks = 8;
        size_t inputByteSize = 8 * 2048 * sizeof(uint16_t);
        size_t outputByteSize = 8 * 2048 * sizeof(uint16_t);
    
    #ifdef ASCENDC_CPU_DEBUG
        // Call program for CPU debugging
    #else
        // Call program for running the operator on the NPU side
    #endif
        return 0;
    }
    ```

3.  Verify the execution on the CPU side. The steps to complete the CPU-side execution verification of the operator kernel function are as follows:

    **Figure 1**  CPU-side execution verification steps<a name="fig13576112114442"></a>  
    ![](../../figures/cpu_side_execution_verification_steps.png "CPU-side execution verification steps")

    ```
        // Use GmAlloc to allocate shared memory and initialize the data.
        uint8_t* x = (uint8_t*)AscendC::GmAlloc(inputByteSize);
        uint8_t* y = (uint8_t*)AscendC::GmAlloc(inputByteSize);
        uint8_t* z = (uint8_t*)AscendC::GmAlloc(outputByteSize);
    
        ReadFile("./input/input_x.bin", inputByteSize, x, inputByteSize);
        ReadFile("./input/input_y.bin", inputByteSize, y, inputByteSize);
        // For vector operators, set the kernel mode to AIV mode.
        AscendC::SetKernelMode(KernelMode::AIV_MODE);
        // Call the ICPU_RUN_KF debugging macro to call the kernel function on the CPU side.
        ICPU_RUN_KF(add_custom, numBlocks, x, y, z);
        // Write the output data.
        WriteFile("./output/output_z.bin", z, outputByteSize);
        // Call GmFree to release the allocated resources.
        AscendC::GmFree((void *)x);
        AscendC::GmFree((void *)y);
        AscendC::GmFree((void *)z);
    ```

4.  Verify the execution on the NPU side. The steps to complete the NPU-side execution verification of the operator kernel function are as follows:

    **Figure 2**  NPU-side execution verification steps<a name="fig558132018817"></a>  
    ![](../../figures/npu_side_run_verification_steps.png "NPU-side execution verification steps")

    ```
        // Initialize
        CHECK_ACL(aclInit(nullptr));
        // Allocate runtime management resources
        int32_t deviceId = 0;
        CHECK_ACL(aclrtSetDevice(deviceId));
        aclrtStream stream = nullptr;
        CHECK_ACL(aclrtCreateStream(&stream));
        // Allocate host memory
        uint8_t *xHost, *yHost, *zHost;
        uint8_t *xDevice, *yDevice, *zDevice;
    
        CHECK_ACL(aclrtMallocHost((void**)(&xHost), inputByteSize));
        CHECK_ACL(aclrtMallocHost((void**)(&yHost), inputByteSize));
        CHECK_ACL(aclrtMallocHost((void**)(&zHost), outputByteSize));
        // Allocate device memory
        CHECK_ACL(aclrtMalloc((void**)&xDevice, inputByteSize, ACL_MEM_MALLOC_HUGE_FIRST));
        CHECK_ACL(aclrtMalloc((void**)&yDevice, inputByteSize, ACL_MEM_MALLOC_HUGE_FIRST));
        CHECK_ACL(aclrtMalloc((void**)&zDevice, outputByteSize, ACL_MEM_MALLOC_HUGE_FIRST));
        // Initialize host memory
        ReadFile("./input/input_x.bin", inputByteSize, xHost, inputByteSize);
        ReadFile("./input/input_y.bin", inputByteSize, yHost, inputByteSize);
        // Copy the data from the host to the device.
        CHECK_ACL(aclrtMemcpy(xDevice, inputByteSize, xHost, inputByteSize, ACL_MEMCPY_HOST_TO_DEVICE));
        CHECK_ACL(aclrtMemcpy(yDevice, inputByteSize, yHost, inputByteSize, ACL_MEMCPY_HOST_TO_DEVICE));
        // Use the kernel call operator <<<>>> to call the kernel function to complete the specified operation. The <<<>>> call is encapsulated in add_custom_do.
        add_custom_do(numBlocks, nullptr, stream, xDevice, yDevice, zDevice);
        // Use the ACLRT_LAUNCH_KERNEL API to call the kernel function to complete the specified operation.
        // ACLRT_LAUNCH_KERNEL(add_custom)(numBlocks, stream, xDevice, yDevice, zDevice);
        CHECK_ACL(aclrtSynchronizeStream(stream));
        // Copy the operation result from the device back to the host.
        CHECK_ACL(aclrtMemcpy(zHost, outputByteSize, zDevice, outputByteSize, ACL_MEMCPY_DEVICE_TO_HOST));
        WriteFile("./output/output_z.bin", zHost, outputByteSize);
        // Release the requested resources.
        CHECK_ACL(aclrtFree(xDevice));
        CHECK_ACL(aclrtFree(yDevice));
        CHECK_ACL(aclrtFree(zDevice));
        CHECK_ACL(aclrtFreeHost(xHost));
        CHECK_ACL(aclrtFreeHost(yHost));
        CHECK_ACL(aclrtFreeHost(zHost));
        // Deinitialize.
        CHECK_ACL(aclrtDestroyStream(stream));
        CHECK_ACL(aclrtResetDevice(deviceId));
        CHECK_ACL(aclFinalize());
    ```

    >[!NOTE] Note
    >The <<<\>\>\> call method is described in the [kernel function](../programming_model/ai_core_simd_programming/kernel_function.md) section. Only the usage of the ACLRT\_LAUNCH\_KERNEL call API is described here:
    >```
    >ACLRT_LAUNCH_KERNEL(kernel_name)(numBlocks, stream, argument list);
    >```
    >- kernel\_name: name of the operator kernel function.
    >- numBlocks: specifies the number of cores on which the kernel function will be executed. Each core that executes the kernel function is assigned a logical ID, that is, block\_idx. You can call [GetBlockIdx](../../../api/SIMD-API/basic_api/tool_interface/system_resources_and_variables/GetBlockIdx.md) in the kernel function implementation to obtain block\_idx.
    >- stream: of the aclrtStream type. The stream is used to maintain the execution order of asynchronous operations to ensure that they are executed on the device in the call order specified in the application program code. For details about the stream creation and management APIs, see [*Runtime API*](https://hiascend.com/document/redirect/CannCommunityRuntimeApi).
    >- argument list: parameter list, which must be consistent with the parameter list of the kernel function.

## Script File for Generating and Verifying Input Data and True Value Data<a name="section1234873541816"></a>

Take the add\_custom operator with a fixed shape as an example. The following is a sample script for generating input data and true value data: write a script based on the input and output of the operator to generate the input data and true value data.

```
#!/usr/bin/python3
# -*- coding:utf-8 -*-
import numpy as np

def gen_golden_data_simple():
    input_x = np.random.uniform(1, 100, [8, 2048]).astype(np.float16)
    input_y = np.random.uniform(1, 100, [8, 2048]).astype(np.float16)
    golden = (input_x + input_y).astype(np.float16)

    input_x.tofile("./input/input_x.bin")
    input_y.tofile("./input/input_y.bin")
    golden.tofile("./output/golden.bin")

if __name__ == "__main__":
    gen_golden_data_simple()
```

The following is a sample verification script for checking whether the output data is consistent with the true value data: the numpy API is used to calculate the absolute error and relative error between the output data and the true value data. If the errors are within the tolerance range, the precision is considered compliant, and "test pass" is printed.

```
import os
import sys
import numpy as np

loss = 1e-3 # Tolerance. For fp16, both the absolute error and the relative error must not exceed one thousandth.
minimum = 10e-10

def verify_result(real_result, golden):
    real_result = np.fromfile(real_result, dtype=np.float16) # Read the actual computation result from the bin file.
    golden = np.fromfile(golden, dtype=np.float16) # Read the expected computation result from the bin file.
    result = np.abs(real_result - golden) # Calculate the deviation between the computation result and the expected result.
    deno = np.maximum(np.abs(real_result), np.abs(golden)) # Obtain the maximum values and form a new array.
    result_atol = np.less_equal(result, loss) # Calculate the absolute error.
    result_rtol = np.less_equal(result / np.add(deno, minimum), loss) # Calculate the relative error.
    if not result_rtol.all() and not result_atol.all():
        if np.sum(result_rtol == False) > real_result.size * loss and np.sum(result_atol == False) > real_result.size * loss:
            print("[ERROR] result error")
            return False
    print("test pass")
    return True

if __name__ == '__main__':
    verify_result(sys.argv[1],sys.argv[2])
```

## Verifying the Kernel Function on the CPU Side<a name="section13472164395818"></a>

On non-Ascend devices, developers can use the CPU simulation environment to develop and test operators first, and then use Ascend devices for accelerated computation once everything is ready. In the [Compilation and Execution](../compilation_and_execution/operator_compilation/ai_core_operator_compilation_basic_usage.md) section, we have already introduced the compilation and execution of the operator kernel program in the NPU domain. Compared with the operator execution logic in the NPU domain, CPU-domain debugging actually compiles the operator kernel program using the standard GCC compiler. In this case, the operator kernel program links the CPU debugging library, and the generated executable file is executed to complete the CPU-domain execution verification of the operator. The CPU-side execution program can be debugged step by step using the general-purpose GDB debugging tool, which accurately verifies whether the program execution flow meets expectations.

**Figure 5**  Comparison of kernel function execution logic between the CPU domain and the NPU domain<a name="fig1274642720202"></a>  
![](../../figures/kernel_function_execution_logic_comparison_between_cpu_and_npu_domains_36.png "Comparison of kernel function execution logic between the CPU domain and the NPU domain-36")

Based on the kernel launch sample project, when the kernel function is called through the ACLRT\_LAUNCH\_KERNEL API, the CPU-domain and NPU-domain code can be unified. This method supports only the following models:

-   Atlas A3 training products/Atlas A3 inference products
-   Atlas A2 training products/Atlas A2 inference products
-   Atlas inference products

The following code uses the add\_custom operator as an example to describe how to write the operator call application program when verifying the operator kernel function on the CPU side (by calling the kernel function through the ACLRT\_LAUNCH\_KERNEL API). When implementing your own application program, you need to pay attention to the modifications caused by different operator kernel functions, including the operator kernel function name and the differences in input and output parameters, and properly arrange the corresponding memory allocation, memory copy, and file read/write operations. The calling methods of the related APIs can be directly reused.

1.  Include the required header files.

    ```
    #include "data_utils.h"
    #include "acl/acl.h"
    #include "aclrtlaunch_add_custom.h"
    ```

2.  Write the application program framework.

    ```
    int32_t main(int32_t argc, char* argv[])
    {
        uint32_t numBlocks = 8;
        size_t inputByteSize = 8 * 2048 * sizeof(uint16_t);
        size_t outputByteSize = 8 * 2048 * sizeof(uint16_t);
        // Run the operator call program
        return 0;
    }
    ```

3.  Run verification.

    ```
        // Initialize
        CHECK_ACL(aclInit(nullptr));
        // Allocate runtime management resources
        int32_t deviceId = 0;
        CHECK_ACL(aclrtSetDevice(deviceId));
        aclrtStream stream = nullptr;
        CHECK_ACL(aclrtCreateStream(&stream));
        // Allocate host memory
        uint8_t *xHost, *yHost, *zHost;
        uint8_t *xDevice, *yDevice, *zDevice;
    
        CHECK_ACL(aclrtMallocHost((void**)(&xHost), inputByteSize));
        CHECK_ACL(aclrtMallocHost((void**)(&yHost), inputByteSize));
        CHECK_ACL(aclrtMallocHost((void**)(&zHost), outputByteSize));
        // Allocate device memory
        CHECK_ACL(aclrtMalloc((void**)&xDevice, inputByteSize, ACL_MEM_MALLOC_HUGE_FIRST));
        CHECK_ACL(aclrtMalloc((void**)&yDevice, inputByteSize, ACL_MEM_MALLOC_HUGE_FIRST));
        CHECK_ACL(aclrtMalloc((void**)&zDevice, outputByteSize, ACL_MEM_MALLOC_HUGE_FIRST));
        // Initialize host memory
        ReadFile("./input/input_x.bin", inputByteSize, xHost, inputByteSize);
        ReadFile("./input/input_y.bin", inputByteSize, yHost, inputByteSize);
        // Copy data from host to device
        CHECK_ACL(aclrtMemcpy(xDevice, inputByteSize, xHost, inputByteSize, ACL_MEMCPY_HOST_TO_DEVICE));
        CHECK_ACL(aclrtMemcpy(yDevice, inputByteSize, yHost, inputByteSize, ACL_MEMCPY_HOST_TO_DEVICE));
        // Call the kernel function through the ACLRT_LAUNCH_KERNEL API to perform the specified operation
        ACLRT_LAUNCH_KERNEL(add_custom)(numBlocks, stream, xDevice, yDevice, zDevice);
        CHECK_ACL(aclrtSynchronizeStream(stream));
        // Copy the operation result from device back to host
        CHECK_ACL(aclrtMemcpy(zHost, outputByteSize, zDevice, outputByteSize, ACL_MEMCPY_DEVICE_TO_HOST));
        WriteFile("./output/output_z.bin", zHost, outputByteSize);
        // Release the allocated resources
        CHECK_ACL(aclrtFree(xDevice));
        CHECK_ACL(aclrtFree(yDevice));
        CHECK_ACL(aclrtFree(zDevice));
        CHECK_ACL(aclrtFreeHost(xHost));
        CHECK_ACL(aclrtFreeHost(yHost));
        CHECK_ACL(aclrtFreeHost(zHost));
        // Deinitialize
        CHECK_ACL(aclrtDestroyStream(stream));
        CHECK_ACL(aclrtResetDevice(deviceId));
        CHECK_ACL(aclFinalize());
    ```

>[!NOTE] Note
>To unify the code of the CPU domain and NPU domain, only some ACL APIs are adapted. When developers use the CPU domain debugging feature, only the following ACL APIs are supported:
>- APIs with actual functions, supporting CPU domain call
>    - aclDataTypeSize, aclFloat16ToFloat, aclFloatToFloat16.
>    - aclrtMalloc, aclrtFree, aclrtMallocHost, aclrtFreeHost, aclrtMemset, aclrtMemsetAsync, aclrtMemcpy, aclrtMemcpyAsync, aclrtMemcpy2d, aclrtMemcpy2dAsync, aclrtCreateContext, aclrtDestroyContext.
>- APIs without actual functions, implemented as stubs
>    - Profiling data collection
>        aclprofInit, aclprofSetConfig, aclprofStart, aclprofStop, aclprofFinalize.
>    - System configuration
>        aclInit, aclFinalize, aclrtGetVersion.
>    - Runtime management
>        aclrtSetDevice, aclrtResetDevice, aclrtCreateStream, aclrtCreateStreamWithConfig, aclrtDestroyStream, aclrtDestroyStreamForce, aclrtSynchronizeStream, aclrtCreateContext, aclrtDestroyContext.
