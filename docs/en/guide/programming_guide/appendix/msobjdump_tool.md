# msobjdump Tool<a name="ZH-CN_TOPIC_0000002028951292"></a>

<!-- md-trans-meta sourceCommit=d0ede7621d11bdc88cdafb221560ec6e0bfe996d translatedAt=2026-08-26T11:08:17.971Z pushedAt=2026-09-01T01:41:04.105Z -->

This tool mainly provides parsing and extraction for the operator Executable and Linkable Format (ELF) files generated by project compilation, and presents the result information in a readable form, making it convenient for developers to intuitively obtain kernel file information. It currently supports parsing the related artifacts generated by fusion compilation projects, standard/simple custom operator projects, and kernel launch projects.

>[!NOTE] Note
>- An ELF file is a file format used for binary files, executable files, object code, shared libraries, and core dumps, including common \*.a and \*.so files. A typical ELF file consists of the following:
>    - ELF header: describes the overall organization of the file, including the file type, machine type, version number, and other information.
>    - Program header table: describes the information of various segments in the file, including how the program is loaded into memory for execution.
>    - Section header table: describes the information of various sections in the file, including the program's code, data, symbol table, and so on.
>- During tool usage, if the following scenarios occur, analyze and troubleshoot the issue based on the log prompt information.
>    - The ELF file is not found.
>    - ELF file permission error.
>    - ELF file exists but parsing or extraction is not supported.

## Supported Products

- Ascend 950PR/Ascend 950DT: Supported
- Atlas A3 training products/Atlas A3 inference products: Supported
- Atlas A2 training products/Atlas A2 inference products: Supported
- Atlas 200I/500 A2 inference products: Supported
- Atlas inference products: Supported
- Atlas training products: Supported

## Tool Installation<a name="section2423188195113"></a>

1.  Install the msobjdump tool.

    The tool is released with the CANN software package (see [Environment Setup](../../getting_started/environment_setup.md) to complete the CANN installation). Its default path is "\$\{INSTALL\_DIR\}/tools/msobjdump", where \$\{INSTALL\_DIR\} must be replaced with the storage path of the CANN software after installation. For example, when installed by the **root** user, the default storage path after installation is **/usr/local/Ascend/cann**.

2.  Set the environment variables.
    -   When installing the Ascend-cann-toolkit package using the root user

        ```
        source /usr/local/Ascend/cann/set_env.sh
        ```

    -   When installing the Ascend-cann-toolkit package using a non-root user

        ```
        source ${HOME}/Ascend/cann/set_env.sh
        ```

3.  Check whether the tool is installed successfully.

    Run the following command. If the **--help** or **-h** information is displayed normally, the tool environment is normal and its functions can be used properly.

    ```
    msobjdump -h
    ```

## Command Format<a name="section101202511916"></a>

-   **Command for parsing an ELF file**

    ```
    msobjdump --dump-elf <elf_file> [--verbose]
    ```

    **Table 1**  Parameter description<a name="table167911947163519"></a>

    | Parameter (Case-Sensitive) | Optional/Required | Description |
    | ---- | ---- | ---- |
    | `--dump-elf <elf_file>`, `-d` | Required | Parses the device information contained in the ELF file, such as the file name, file type, file length, and symbol table, and displays it on the terminal screen.<br>`<elf_file>` indicates the path of the ELF file to be parsed, for example, `/home/op_api/lib_api.so`. Two print modes are supported:<br>Simple print: By default, only part of the device information is printed.<br>Full print: Used together with `--verbose` to enable full device information display on the screen.<br>Different build projects print different field information. For details, see <a href="#table94384560259">Table 4</a> and <a href="#table217334916136">Table 6</a>. |
    | `--verbose`, `-V` | Optional | Must be used together with `--dump-elf` to enable full device information printing in the ELF file. |

-   **Command for extracting an ELF file**

    ```
    msobjdump --extract-elf <elf_file> [--out-dir <out_path>]
    ```

    **Table 2**  Parameter description<a name="table131531242133819"></a>

    | Parameter (Case-Sensitive) | Optional/Required | Description |
    | ---- | ---- | ---- |
    | `--extract-elf <elf_file>`, `-e` | Required | Extracts the device information contained in the ELF file and saves the parsed results to the output path.<br>`<elf_file>` indicates the path of the ELF file to be extracted, for example, `/home/op_api/lib_api.so`.<br>Default path: The extracted result files are saved to the current execution path by default.<br>Custom path: Can be used together with `--out-dir` to set the save path. |
    | `--out-dir <out_path>`, `-o` | Optional | Must be used together with `--extract-elf` to set the save path of the extracted files.<br>`<out_path>` is the directory for the saved files, for example, `/home/extract/`.<br>**Note**: `msobjdump` supports concurrent call by multiple users, but different `--out-dir` values must be specified; otherwise, the saved content may be overwritten. |

-   **Command for obtaining the ELF file list**

    ```
    msobjdump --list-elf <elf_file>
    ```

    **Table 3**  Parameter description

    <a name="table121952819427"></a>
    | Parameter (Case-Sensitive) | Optional/Required | Description |
    | ---- | ---- | ---- |
    | `--list-elf <elf_file>`, `-l` | Required | Obtains the list of device information files contained in the ELF file and prints them.<br>`<elf_file>` indicates the path of the ELF file to be printed, for example, `/home/op_api/lib_api.so`. |

**Table 4**  ELF parsing fields (standard/simple custom operator project and fusion compilation project)<a name="table94384560259"></a>

| Field Name | Meaning | Optional/Required | Print Description |
| ---- | ---- | ---- | ---- |
| `.ascend.meta. ${id}` | Represents the operator kernel function name, where `${id}` indicates the index value of the meta information. | Required | Printed by default when `--verbose` is not set. |
| `VERSION` | Represents the version number. | Required | Printed by default when `--verbose` is not set. |
| `DEBUG` | Debug-related information, including the following two parts:<br>`debugBufSize`: memory space required for debug information.<br>`debugOptions`: debug switch status. The values are as follows:<br>`0`: debug switch disabled.<br>`1`: debug through DumpTensor and printf printing.<br>`2`: debug through assert assertion.<br>`4`: debug through timestamp marking.<br>`8`: debug through memory out-of-bounds detection. | Optional | Printed by default when `--verbose` is not set. |
| `DYNAMIC_PARAM` | Whether dynamic parameters are enabled for the operator kernel function. The values are as follows:<br>`0`: dynamic parameter mode disabled.<br>`1`: dynamic parameter mode enabled. | Optional | Printed by default when `--verbose` is not set. |
| `OPTIONAL_PARAM` | Optional parameter information, including the following two parts:<br>`optionalInputMode`: whether optional inputs need to occupy a placeholder in the operator kernel function.<br>`0`: optional inputs do not occupy a placeholder.<br>`1`: optional inputs occupy a placeholder.<br>`optionalOutputMode`: whether optional outputs need to occupy a placeholder in the operator kernel function.<br>`0`: optional outputs do not occupy a placeholder.<br>`1`: optional outputs occupy a placeholder. | Optional | Printed by default when `--verbose` is not set. |
| `RUNTIME_IMPLICIT_INFO` | Represents the runtime implicit information flag. The values are as follows:<br>`1`: `SIMD Printf Flag`, indicating the SIMD-side Printf flag.<br>`2`: `Hardware Sync Flag`, indicating the hardware synchronization flag.<br>`3`: `L2Cache Hint Flag`, indicating the L2 Cache hit flag.<br>`4`: `SIMT Printf Flag`, indicating the SIMT-side Printf flag.<br>`5`: `SIMD Assert Flag`, indicating the SIMD-side Assert flag.<br>For other values, the original value is printed. | Optional | Printed by default when `--verbose` is not set. |
| `KERNEL_TYPE` | Represents the core type at kernel function runtime. For the values, see <a href="#table187419221164">Table 5</a>. | Optional | Printed by default when `--verbose` is not set. |
| `CROSS_CORE_SYNC` | Represents the hardware synchronization syncall type.<br>`USE_SYNC`: hardware synchronization is used.<br>`NO_USE_SYNC`: hardware synchronization is not used. | Optional | Printed by default when `--verbose` is not set. |
| `MIX_TASK_RATION` | Represents the Cube core/Vector core ratio allocation type at kernel function runtime. | Optional | Printed by default when `--verbose` is not set. |
| `DETERMINISTIC_INFO` | Represents whether the operator uses deterministic computation.<br>`0`: non-deterministic computation.<br>`1`: deterministic computation. | Optional | Printed by default when `--verbose` is not set. |
| `BLOCK_NUM` | Represents the number of cores for operator execution. This field is not supported currently, and only the default value `0xFFFFFFFF` is printed. | Optional | Printed by default when `--verbose` is not set. |
| `FUNCTION_ENTRY` | The value of the operator TilingKey. | Optional | Printed by default when `--verbose` is not set. |
| `elf header infos` | Includes information such as ELF Header, Section Headers, Key to Flags, Program Headers, and Symbol table. | Optional | Full print is enabled when `--verbose` is set. |

**Table 5**  kernel type information

<a name="table187419221164"></a>
| KERNEL_TYPE | Description |
| ---- | ---- |
| `AICORE` | **This parameter is reserved and not supported in the current version.**<br>During operator execution, only AI Core is started. For example, if the user sets blocknum to 5 on the host side, 5 AI Cores are started. |
| `AIC` | During operator execution, only the Cube core on AI Core is started. For example, if the user sets blocknum to 10 on the host side, 10 Cube cores are started. |
| `AIV` | During operator execution, only the Vector core on AI Core is started. For example, if the user sets blocknum to 10 on the host side, 10 Vector cores are started. |
| `MIX_AIC_MAIN` | In the AIC and AIV mixed scenario, the kernel function type is set to MIX. During operator execution, both the Cube core and Vector core on AI Core are started simultaneously. For example, if the user sets blocknum to 10 on the host side and sets task_ration to 1:2, 10 Cube cores and 20 Vector cores are started. |
| `MIX_AIV_MAIN` | In the AIC and AIV mixed scenario, when multi-core control related instructions are used, the kernel function type is set to MIX. During operator execution, both the Cube core and Vector core on AI Core are started simultaneously. For example, if the user sets blocknum to 10 on the host side and sets task_ration to 1:2, 10 Vector cores and 20 Cube cores are started. |
| `AIC_ROLLBACK` | During operator execution, both AI Core and Vector Core are started simultaneously. In this case, AI Core is used as Cube Core. |
| `AIV_ROLLBACK` | During operator execution, both AI Core and Vector Core are started simultaneously. In this case, AI Core is used as Vector Core. |


**Table 6**  ELF parsing fields (kernel launch project)

<a name="table217334916136"></a>
| Field Name | Meaning | Optional/Required | Print Description |
| ---- | ---- | ---- | ---- |
| `VERSION` | Represents the version number. | Required | Printed by default when `--verbose` is not set. |
| `TYPE COUNT` | Represents the number of kernel files contained in the ELF file. | Required | Printed by default when `--verbose` is not set. |
| `ELF FILE ${id}` | Represents the kernel file name contained in the ELF file, where `${id}` indicates the kernel file sequence number.<br>The kernel file naming rule is as follows:<br>It is concatenated as `${sec_prefix}_${file_index}_${kernel_type}.o`, where `${sec_prefix}` is the section name (obtained by the tool by searching for the `.ascend.kernel` keyword), `${file_index}` indicates the file number, and `${kernel_type}` indicates the kernel type. | Required | Printed by default when `--verbose` is not set. |
| `KERNEL LEN` | Represents the length of the kernel file. | Required | Printed by default when `--verbose` is not set. |
| `KERNEL TYPE` | Represents the kernel type. The mapping relationship is `{0: mix, 1: aiv, 2: aic}`. | Optional | Printed by default when `--verbose` is not set. |
| `ASCEND META` | Represents information such as inter-core synchronization and Cube/Vector core ratio (task_ration) during operator execution.<br>If this information is not obtained, `None` is displayed by default. | Optional | Printed by default when `--verbose` is not set. |
| `elf header infos` | Includes information such as ELF Header, Section Headers, Key to Flags, Program Headers, and Symbol table. | Optional | Full print is enabled when `--verbose` is set. |

## Example (Fusion Compilation Project)<a name="section_fusion_compile_msobjdump"></a>

Take the executable file generated by a fusion compile build project as an example. Assume that `${build_dir}` is the project build directory and the generated executable file is named `demo`. For such artifacts, the tool parses the device-related information in the executable file. `--dump-elf` is used to display the binary meta and function meta information, `--list-elf` is used to view the names of extractable device files, and `--extract-elf` is used to save the parsed device files to disk. For call examples, see [msobjdump examples](https://gitcode.com/cann/asc-tools/tree/9.1.0/examples/04_msobjdump).

-   **Parsing the fusion compilation project artifact**

    Two print methods are supported. Select one as needed. For the meaning of parsing fields, see [Table 4](#table94384560259).

    -   Simple print

        ```
        msobjdump --dump-elf ${build_dir}/demo
        ```

        Run the above command. The terminal prints the basic device information. The following is an example:

        ```
        .ascend.meta META INFO

    ```


## Example (Kernel Launch Operator Project)<a name="section12189203721319"></a>

Take the MatMulInvocationNeo operator as an example (NPU mode). Assume that $\{cmake\_install\_dir\} is the root directory of the operator CMake compilation output. The directory structure is as follows (for reference only; the actual structure depends on the operator project), similar to [Writing the CMake Compilation Configuration File](completing_kernel_launch_based_on_sample_project.md#section185111259496).

```
out
├── lib
│   ├── libascendc_kernels_npu.so
├── include
│   ├── ascendc_kernels_npu
│           ├── aclrtlaunch_matmul_custom.h
│           ├── aclrtlaunch_triple_chevrons_func.h
......
```

The tool parses and extracts the library files generated by compilation (such as \*.so and \*.a). The commands for implementing the functions are as follows:

-   **Parsing the library file that contains device information**

        ```
        msobjdump --dump-elf ${cmake_install_dir}/out/libascendc_kernels_npu.so
        ```
