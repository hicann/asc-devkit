# NPU Architecture Version 3510

This section describes the hardware constraints and recommended solutions. The corresponding product models are:

<!-- npu="950" id1 -->
-   Ascend 950PR&950DT products
<!-- end id1 -->

**Table 1** Hardware constraints and recommended solutions

| Category | Hardware Constraint Description | Solution Recommendation |
| --- | --- | --- |
| Memory Access Alignment Constraint | Minimum access granularity/address alignment requirements of each storage unit:<br> Unified Buffer: 32-byte alignment.<br> L1 Buffer: 32-byte alignment.<br> L0A Buffer/L0B Buffer: 512-byte alignment.<br> L0C Buffer: 64/1024-byte alignment.<br> BiasTable Buffer: 64-byte alignment.<br> Fixpipe Buffer: 64/128-byte alignment. | When performing data movement, you need to be aware of the alignment constraints.<br> For UB, in non-aligned scenarios, you can use the non-aligned load-in instruction LoadUnAlign and the non-aligned store-out instruction StoreUnAlign, which support 1-byte aligned access. When the first address is non-aligned and access is continuous, the performance is basically the same as in the aligned scenario. When the first address is non-aligned and access is non-continuous, the compute-bound scenario is not affected, but the UB memory-access-bound scenario is affected.<br> For L0C Buffer, Mmad computation uses 1024B alignment, and cube computation store-out uses 64B alignment.<br> For Fixpipe Buffer, the relu scenario uses 64B alignment, and the quant scenario uses 128B alignment. |
| General API Constraint | When using Ascend C basic APIs, the general constraint on address overlap between the source operand and the destination operand. | When using the Tensor high-dimensional sharding computation APIs of the basic APIs, to save address space, developers can define one Tensor that is used by both the source operand and the destination operand (that is, address overlap). Note the following constraints when using it:<br> - Within a single iteration: the source operand and the destination operand must overlap 100% completely. Partial overlap is not supported.<br>- Across multiple iterations: overlap between the destination operand of a preceding iteration and the source operand of a subsequent iteration is not supported. For example, the destination operand of the Nth iteration is the source operand of the (N+1)th iteration. In this case, the Nth iteration may overwrite the value of the source operand, causing unexpected results. In particular, for some binary computation APIs (Add, Sub, Mul, Max, Min, AddRelu, SubRelu), when the data type is half, int32_t, or float, overlap between the destination operand of a preceding iteration and the source operand of a subsequent iteration is supported: only for the case where the destination operand overlaps the second source operand, and src1RepStride or dstRepStride must be 0. |
| Memory Access (GM) | When the length of a single transfer exceeds 16KB, the optimal bandwidth performance can be achieved. | Based on measured experience, when the length of a single transfer exceeds 16KB, the optimal bandwidth performance can usually be achieved. Therefore, for a single transfer, you should transfer as large a data block as possible (this varies by chip).<br> For the specific solution, see [Transfer Larger Data Blocks in a Batch If Possible](../../../../operator_practice/simd_operator_optimization/memory_access/transfer_larger_data_blocks.md). |
| Memory Access (GM) | Data movement is split into transfers of different lengths of 128B/256B/512B, and non-aligned transfers are rounded up. | In Tiling, align the inner axis of the transfer to 128B, 256B, or 512B as much as possible.<br> For the specific solution, see [Aligning GM Addresses to 512B Whenever Possible](../../../../operator_practice/simd_operator_optimization/memory_access/gm_address_512b_alignment.md). |
| Memory Access (UB) | UB bank access conflict (Vector computation access/movement access). | UB needs to stagger the processed addresses in software implementation according to the chip requirements to resolve bank conflicts. For the specific solution, see [Avoiding Bank Conflicts (NPU Architecture Version 3510)](../../../../operator_practice/simd_operator_optimization/memory_access/avoid_ub_bank_conflict/avoid_bank_conflict_npu_arch_3510.md). |
| Vector Computation | APIs such as Ln, Exp, Sqrt, Rsqrt, Reciprocal, and Div do not support Subnormal computation. | If Ln, Exp, Sqrt, Rsqrt, Reciprocal, and Div need to support Subnormal computation on 3510, you need to configure the corresponding FTZ_FALSE algorithm. See [Compatibility Migration Guide - Removing Subnormal Hardware Computation](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#subnormal-migration). |
| Cube Data Movement | The data path from L1 Buffer to GM is deleted. | The compatibility solutions are as follows:<br> 1. For pure Cube-side operators, the data pathway L1 Buffer -> L0A Buffer/L0B Buffer -> L0C Buffer -> GM can be used;<br> 2. For Cube+Vector fused operators, the pathway L1 Buffer -> UB -> GM can be used.<br> See [Compatibility Migration Guide - Removing the L1 Buffer->GM Hardware Path](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#data-copy-l1-to-gm-migration). |
| Cube Data Movement | The data pathway from GM to L0A Buffer is removed. | Split the original GM->L0A Buffer LoadData 2D data movement into two parts:<br> 1. GM -> L1 Buffer (using LoadData 2D cube transfer);<br> 2. L1 Buffer -> L0A Buffer (using LoadData 2D cube transfer).<br> See [Compatibility Migration Guide - Removing the GM->L0A Buffer/L0B Buffer Path](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#gm-to-l0a-l0b-migration). |
| Cube Data Movement | The data pathway from GM to L0B Buffer is removed. | Split the original GM->L0B Buffer LoadData 2D data movement into two parts:<br> 1. GM -> L1 Buffer (using LoadData 2D cube transfer);<br> 2. L1 Buffer -> L0B Buffer (using LoadData 2D cube transfer).<br> See [Compatibility Migration Guide - Removing the GM->L0A Buffer/L0B Buffer Path](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#gm-to-l0a-l0b-migration). |
| Cube Data Movement | When using LoadData (convolution data movement), the SetLoadDataBoundary API is no longer supported. | The compatibility solutions are as follows:<br> 1. When the value of SetLoadDataBoundary on version 2201 is 0, directly remove the call on 3510;<br> 2. When the value of SetLoadDataBoundary on version 2201 is non-zero, split one transfer into multiple LoadData calls and explicitly update the source/destination offsets to implement wraparound.<br> For details, see [Compatibility Migration Guide - Not Supporting Setting the L1 Buffer Boundary Value](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#set-load-data-boundary-migration). |
| Cube Data Movement | The Fill API does not support initialization of L0A/L0B. | The compatibility solutions are as follows:<br> 1. Call the Fill API to complete initialization on L1 Buffer;<br> 2. Use LoadData 2D cube to move the data to L0A/L0B.<br> See [Compatibility Migration Guide - Removing the Hardware Instructions Related to L0A Buffer/L0B Buffer Initialization](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#fill-l0a-l0b-migration). |
| Cube Data Movement | Cube data load-in does not support the int4b_t data type. | The compatibility solutions are as follows:<br> 1. You can use fp4x2_e2m1_t and fp4x2_e1m2_t for movement. For details, see [LoadData (2D Cube Transfer MX)](../../../../../api/SIMD-API/basic_api/cube_compute_ISASI/cube_compute_load/LoadData_2D_MX.md);<br> 2. Convert the int4b_t data type to the int8_t data type on Vector;<br> 3. Use the UB->L1 data pathway to move the data to L1 Buffer.<br> See [Compatibility Migration Guide - The Cube Compute Unit No Longer Supports the int4b_t Data Type](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#cube-int4-migration). |
| Cube Data Movement | The LoadDataWithTranspose API does not support the L1->L0A pathway. | Replace it with another movement API, such as [LoadData (2D Cube Transfer V2)](../../../../../api/SIMD-API/basic_api/cube_compute_ISASI/cube_compute_load/LoadData_2D_V2.md) cube transfer. |
| Cube Data Movement/Cube Computation | The L0A cube fractal changes from Zz to Nz. | The fractal conversion involves compatibility adaptation for the following two typical scenarios:<br> 1. L0A is not reused. One mmad computation is performed on an entire A cube block.<br> 2. L0A is reused. The M axis is split, the A cube is divided into two sub-matrix blocks, and two mmad computations are performed.<br> For scenario 1, you need to modify the logic of the L1>L0A movement process, changing the fractal conversion from Nz->Zz to Nz->Nz. For details, see the sample implementation.<br> For scenario 2, on version 2201, because the Zz fractal itself is continuous on the M axis, the L1->L0A movement logic is the same as in scenario 1. However, for the Ascend 950PR&950DT products, splitting the M axis makes the cube discontinuous, so it needs to be split into two Nz cubes. For details, see the sample implementation.<br> For details, see the sample: [pattern_transformation](../../../../../../../examples/01_simd_cpp_api/06_compatibility_guide/pattern_transformation/README.md). |
| Cube Data Movement/Cube Computation | 4:2 structured sparse cube computation is not supported. The following instructions are not supported: LoadDataWithSparse and MmadWithSparse. | Remove this load path, retain/restore the dense B cube layout, and use the ordinary LoadData and Mmad. See [Compatibility Migration Guide - Removing the 4:2 Structured Sparsity Feature](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#structured-sparsity-migration). |
| Cube Computation | Cube computation does not support the int4b_t data type. | The compatibility solutions are as follows:<br> 1. Convert the int4b_t data type to the int8_t data type on Vector;<br> 2. Use the UB->L1 data pathway to move the data to L1 Buffer.<br> See [Compatibility Migration Guide - The Cube Compute Unit No Longer Supports the int4b_t Data Type](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#cube-int4-migration). |
| Cube Computation | In Cube computation scenarios, the float compute capability is 1/16 of the half compute capability. | In Cube computation scenarios, the float compute capability is 1/16 of the half compute capability. It is recommended to use the [HF32](../../../../../api/SIMD-API/basic_api/cube_compute_ISASI/mmad_compute_key_features/HF32.md) feature, whose compute capability is 1/2 of the half compute capability. For more theoretical compute capability specifications, see [Cube Instruction Theoretical Performance Summary](../../../../../api/appendix/cube_instruction_theoretical_perf_summary.md). |
| Instruction Queue Depth | The instruction queues of the Cube/Vector compute units and the movement units have depth specifications. When the corresponding instruction queue reaches its maximum depth, it blocks the dispatch of all other instructions on that Cube/Vector core, which may cause pipeline stalls. | The queue depth indicates the number of pending instructions that can be buffered in the same instruction queue. When the number of any pending instructions (Vector instruction queue, Cube instruction queue, MTE1/MTE2/MTE3 instruction queue, etc.) reaches the queue depth, if the corresponding Scalar unit dispatches an instruction to that instruction queue again, it will be blocked, preventing the Scalar unit from continuing to dispatch subsequent instructions in order. You can optimize performance by optimizing the number of instructions and other means. For more information, see [Typical Instruction Flow](../basic_architecture.md#typical-instruction-flow). For the specific specifications, see [3510 Instruction Queue Depth](../architecture_spec/npu_arch_3510.md#instruction-queue-depth). |
| Pipeline Synchronization (Intra-core) | If set/wait synchronization does not match, the state remains and affects subsequent operators. | Use the twin debugging/mssanitizer tool to identify such issues in advance. |
| Pipeline Synchronization (Intra-core) | On the same pipeline with the same eventID, using SetFlag consecutively causes undefined behavior, for example:<br> AscendC::SetFlag&lt;AscendC::HardEvent::M_MTE1&gt;(0);<br> AscendC::SetFlag&lt;AscendC::HardEvent::M_MTE1&gt;(0); | Use the twin debugging/mssanitizer tool to identify such issues in advance. |
| Pipeline Synchronization (Inter-core) | Kernel functions that use the inter-core synchronization APIs must use the [mix function qualifier](../../../language_extension/simd_builtin_keywords.md#function-execution-space-qualifiers). | Use the twin debugging/mssanitizer tool to identify such issues in advance. |
| Pipeline Synchronization (Inter-core) | When the mode of [CrossCoreSetFlag](../../../../../api/SIMD-API/basic_api/sync_control/inter_core_sync/CrossCoreSetFlag_ISASI.md) and [CrossCoreWaitFlag](../../../../../api/SIMD-API/basic_api/sync_control/inter_core_sync/CrossCoreWaitFlag_ISASI.md) is 0, 1, or 2, the template parameter pipe does not support being set to PIPE_ALL or PIPE_S. Mode 4 does not support PIPE_ALL. For details, see [New Inter-core Synchronization Control Mode 4](../../../../cross_gen_migration_guide/instructions_for_new_features/3510_new_features.md#section_crosscore). | Use the twin debugging/mssanitizer tool to identify such issues in advance. |
| Pipeline Synchronization (Inter-core) | The CrossCoreSetFlag counter has a restriction. If it exceeds 15 times, a reverse synchronization is required; otherwise, a hang occurs. | Use the twin debugging/mssanitizer tool to report errors in advance for scenarios that exceed the limit. |
| Scalar | When a scalar writes to GM, the data is cached in DCache. The hardware does not guarantee consistency between DCache and GM, and the user must ensure it. | You can use [DataCacheCleanAndInvalid](../../../../../api/SIMD-API/basic_api/cache_control/DataCacheCleanAndInvalid.md) to ensure consistency. If you do not expect to read/write data through DCache, you can call the [ReadGmBypassDCache](../../../../../api/SIMD-API/basic_api/scalar_compute/ReadGmBypassDCache_ISASI.md)/[WriteGmBypassDCache](../../../../../api/SIMD-API/basic_api/scalar_compute/WriteGmBypassDCache_ISASI.md) APIs. For details, see [Cache Coherence](../../memory_model/cache_coherence.md). |
| ICache | The AIC ICache hardware specification is limited to 32KB, and the AIV ICache hardware specification is limited to 16KB. | The ICache is located in the Scalar instruction fetch cache. The ICache size differs between the AIC and AIV sides. For cache coherence content, see [Cache Coherence](../../memory_model/cache_coherence.md). Split Tiling_key or use template functions to reduce the code segment. For details, see [Multi-Branch Strategy](../../../advanced_programming/aclnn_operator_development/design_and_implementation/multi_branch_strategy.md). |
| ICache | When different cores access instruction data from the same GM and load it into the ICache, the parallel access read performance degrades. | In small-shape scenarios, you can adopt optimization measures such as reducing the number of launched cores to reduce multi-core access to data on the same GM. |
| DCache | The SIMD DCache hardware specification is limited to 32KB, and the SIMT DCache hardware specification is limited to 128KB. | The DCache is located in the Scalar data cache. For cache coherence content, see [Cache Coherence](../../memory_model/cache_coherence.md). |
| AIPP | The AIPP hardware instructions are removed and software emulation is adopted. The functionality can be migrated but performance may degrade. The corresponding instructions are as follows: SetAippFunctions and LoadImageToLocal. | Re-evaluate the performance of operators that involve AIPP hardware instructions. |
| Debugging | The registers related to the CheckLocalMemoryIA API are removed, and this debugging API is not supported. | This is a debugging API, and the functional dependency needs to be removed. This API is an ISASI API on version 2201, and 950 does not guarantee compatibility. See [Compatibility Migration Guide - CheckLocalMemoryIA Is Not Supported, and the Related Registers Are Removed in Hardware](../../../../cross_gen_migration_guide/3510_arch_migration/2201_to_3510_guide/basic_api_migration.md#check-local-memory-ia-migration). |
