**Table 1** Hardware constraints and recommended solutions

| Classification | Hardware Constraint Description | Solution Suggestion |
| --- | --- | --- |
| Memory access (L0 Buffer/L1 Buffer/Unified Buffer (UB), etc.) | Minimum access granularity/address alignment requirements of each storage unit:<br> UB: 32-byte alignment.<br> L1 Buffer: 32-byte alignment.<br> L0A Buffer/L0B Buffer: 512-byte alignment.<br> L0C Buffer: 64-byte alignment.<br> BiasTable Buffer: 64-byte alignment.<br> Fixpipe Buffer: 128-byte alignment. | - When transferring data, be aware of the alignment constraints.<br>- For UB, in some unaligned scenarios, you can use unaligned transfer APIs or apply certain techniques (for example, including redundant data when moving in and removing redundant data when moving out). For details, see [Unaligned Scenarios](../../../../operator_practice/simd_operator_impl/vector_programming/unaligned_scenario.md). |
| Memory access (UB) | UB bank access conflicts (Vector computation access/transfer access).<br> | Stagger the addresses during software implementation as required by the chip to resolve bank conflicts. For the specific solution, see the [Avoiding UB Bank Conflicts](../../../../operator_practice/simd_operator_optimization/memory_access/avoid_ub_bank_conflict/avoid_bank_conflict_npu_arch_2201.md) chapter. |
| Memory access (GM) | Multi-core parallel same-address access to GM is serialized by hardware.<br> | Access to the same address is serialized by hardware, and the performance is the queueing time, which drops by about 10%-20%.<br> Multi-core access can be staggered (by adjusting the data access order and modifying the splitting strategy, etc.) so that data is loaded into L2 Cache on the first access and subsequent accesses actually improve performance. For the specific solution, see the [Avoiding Same-Address Access](../../../../operator_practice/simd_operator_optimization/memory_access/avoid_same_address_access.md) chapter. |
| Memory access (GM) | When the data length of a single transfer is 16 KB or more, the optimal bandwidth performance can be achieved. | Based on actual measurements, when the data length of a single transfer is 16 KB or more, the optimal bandwidth performance can usually be achieved. Therefore, for a single transfer, transfer data blocks as large as possible (this varies by chip).<br> For the specific solution, see the [Transferring Larger Data Blocks in a Batch If Possible](../../../../operator_practice/simd_operator_optimization/memory_access/transfer_larger_data_blocks.md) chapter. |
| Memory access (GM-->L1) | In DataCopy, the interval between adjacent contiguous data blocks of the source operand (the interval between the tail of the preceding data block and the head of the following data block) must not exceed 65535, in the unit of DataBlock (32 bytes). | When the interval between the tail of the preceding data block and the head of the following data block exceeds 65535, split it into multiple instructions. |
| Memory access (GM) | Data transfer is split into 128B/256B/512B segments of different lengths, and unaligned data is rounded up. | Tiling should align the inner axis of the transfer to 128B, 256B, or 512B as much as possible.<br> For the specific solution, see the [Aligning GM Addresses to 512B Whenever Possible](../../../../operator_practice/simd_operator_optimization/memory_access/gm_address_512b_alignment.md) chapter. |
| Cube | The depth of the MTE1 and MMAD instruction queues is 32. | The corresponding instruction queues tend to fill up, which blocks the issue of other instructions and causes pipeline stalls.<br> LoadData (2D cube transfer) transfers data from L1 Buffer to L0 Buffer and requires 32 instructions to be issued, while LoadData (convolution data transfer) requires only one instruction. It is recommended to use LoadData (convolution data transfer). |
| ICache | The ICache hardware specification limit is 32 KB. | Split Tiling_key or use template functions to reduce the code segment. For details, see [Multi-Branch Strategy](../../../advanced_programming/aclnn_operator_development/design_and_implementation/multi_branch_strategy.md). |
| ICache | Multi-core parallel same-address access to ICache is serialized by hardware.<br> | For small-shape scenarios, minimize the number of launched cores to reduce multi-core same-address access issues. |
| DCache | The DCache hardware specification limit is 32 KB. | None |
| Scalar | When a scalar writes to GM, the data is cached in DCache. The hardware does not guarantee consistency between DCache and GM, and the user must ensure it. | Use DataCacheCleanAndInvalid to ensure consistency. |
| Cube | The L0C Buffer capacity is 128 KB. | None |
| Cube | The BiasTable Buffer is 1 KB. | None |
| Cube | In Cube computation scenarios, the float computing power is 1/4 of the half computing power. | None |
| Cube | In Cube output on-the-fly quantization scenarios, quantization from int32_t to bfloat16_t is not supported. | - On AIV, int32_t->float and float->bfloat16_t conversions are available.<br>- AIC supports float->bfloat16_t on-the-fly quantization. |
| Vector | The Reduce API performs worse with half than with float. | When half is written back to UB, it is not 32-byte aligned, which degrades performance. It is recommended to convert half to float for computation. In this scenario, use the float data type. |
| Vector | The Exp/Ln APIs take the same amount of time to process the same number of half/float values. | float is optimized internally, so the two have comparable performance. Developers can select an appropriate precision type based on the actual situation. |
| Pipeline synchronization (intra-core) | Mismatched set/wait synchronization leaves residual states that affect subsequent operators. | Use the twin debugging/mssanitizer tools to identify such issues in advance. |
| Pipeline synchronization (inter-core) | The CrossCoreSetFlag counter has a limit. If it exceeds 15 times, a reverse synchronization is required; otherwise, a deadlock occurs. | Use the twin debugging/mssanitizer tools to report errors in advance for scenarios exceeding the limit. |
| General API constraints | When using Ascend C APIs, the general constraint on address overlap between the source operand and the destination operand. | When using the Tensor high-dimensional sharding computation APIs of the basic APIs, to save address space, developers can define one Tensor for both the source operand and the destination operand (that is, address overlap). Note the following constraints when using it:<br> - Within a single iteration: the source operand and the destination operand must overlap 100% completely; partial overlap is not supported.<br>- Across multiple iterations: overlap between the destination operand of a preceding iteration and the source operand of a subsequent iteration is not supported. For example, the destination operand of the Nth iteration is the source operand of the (N+1)th iteration. In this case, the Nth iteration may overwrite the value of the source operand, resulting in unexpected results. In particular, for some binary computation APIs (Add, Sub, Mul, Max, Min, AddRelu, SubRelu), when the data type is half, int32_t, or float, overlap between the destination operand of a preceding iteration and the source operand of a subsequent iteration is supported: only for the case where the destination operand overlaps with the second source operand, and src1RepStride or dstRepStride must be 0. |
