# Basic Process

This document covers basic content and describes the basic integration process on the Kernel side in the aclnn engineering operator development approach, focusing on the Kernel entrypoint function format, parameter order, Kernel type setting, TilingData processing, and how to obtain compile-time information.

## Kernel Format

### Naming Rules

The name of the Kernel entrypoint function must correspond to the operator type. The operator type uses PascalCase, while the Kernel entrypoint function uses lowercase with underscores. The framework matches them based on the naming rules during compilation and runtime.

| Operator Type | Kernel Entrypoint Function Name |
|---|---|
| `AddCustom` | `add_custom` |
| `MatmulCustom` | `matmul_custom` |
| `ReduceMaxCustom` | `reduce_max_custom` |
| `Conv2DCustom` | `conv2_d_custom` |
| `GatherV2Custom` | `gather_v2_custom` |

The complete conversion rules and more examples are provided in [Naming Conversion Reference Table](../appendix/naming_conversion_table.md).

### Function Form

The Kernel entrypoint function can use either a non-template entry or a templated entry.

**Non-template entry** uses `extern "C"` to specify the C language linkage rules. The basic template generated by msOpGen typically adopts this form.

```cpp
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z, GM_ADDR workspace, GM_ADDR tiling)
{
    // Kernel implementation details
    // ...
}
```

**Templated entry** carries the dtype, Tile count, and branch selection information through template parameters. The operator type corresponding to the following example is `AddCustomTemplate`, so the Kernel entrypoint is named `add_custom_template`. In the aclnn engineering operator development approach, you need to first declare the template parameters and their available combinations, then the Host-side Tiling selects a combination through `ASCENDC_TPL_SEL_PARAM`, and the compilation tool instantiates the corresponding Kernel based on the configuration.

```cpp
template <typename D_T_X, typename D_T_Y, typename D_T_Z, int TILE_NUM, int IS_SPLIT>
__global__ __aicore__ void add_custom_template(GM_ADDR x, GM_ADDR y, GM_ADDR z,
                                               GM_ADDR workspace, GM_ADDR tiling)
{
    // Kernel implementation details
    // ...
}
```

The preceding code uses `REGISTER_TILING_DEFAULT` to register the default TilingData structure, and parses the Tiling data by the specified type through `GET_TILING_DATA_WITH_STRUCT`. For template parameter declaration, Host-side selection, and compilation configuration, see the Tiling template programming section in [Multi-Branch Strategy](./multi_branch_strategy.md).

### Parameter Order

The parameters of the Kernel entrypoint function must be arranged in the order of "input, output, workspace, tiling". When the framework invokes the Kernel, it first passes the Tensor addresses in the input/output order defined in the operator prototype, and then appends the two parameters workspace and tiling.

```cpp
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z,
                                                  GM_ADDR workspace, GM_ADDR tiling);
```

The meanings of the parameters are as follows:

| Parameter | Source | Description |
|---|---|---|
| `x`, `y` | Inputs in the operator prototype | Point to the Global Memory addresses of the input Tensors |
| `z` | Output in the operator prototype | Points to the Global Memory address of the output Tensor |
| `workspace` | Appended by the framework | Points to the workspace memory address |
| `tiling` | Appended by the framework | Points to the data written by Host-side Tiling |

> **Note: Scenario Where Input and Output Have the Same Name**
>
> If the input and output in the operator prototype have the same name, msOpGen appends the `ref` suffix to the output parameter when generating the Kernel entrypoint parameters, to distinguish the input and output addresses.
>
> ```cpp
> extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y,
>                                                   GM_ADDR x_ref, GM_ADDR workspace,
>                                                   GM_ADDR tiling);
> ```

The internal organization of the Kernel implementation class is determined by the operator computation logic and the Ascend C programming model. In the aclnn engineering operator development approach, the Kernel entrypoint only needs to maintain the parameter order required by the framework, read the TilingData, and pass the input/output addresses and Tiling parameters to the Kernel implementation class.

The Kernel entrypoint of AddCustom connects the operator implementation through the following steps:

1. Read `totalLength` and `tileNum` passed from the Host side through `GET_TILING_DATA`.
2. Create a `KernelAdd` object and pass the input/output addresses and Tiling parameters to `Init`.
3. Call `Process` to move the input data of the current Tile from Global Memory to Local Memory.
4. Call `Add` to complete the element-wise addition.
5. Move the computation result from Local Memory back to Global Memory.

`Process` loops through steps 3 to 5 based on `tileNum` until all tiles of the current block are processed. Synchronization must be performed between data movement and computation based on data dependencies.

## Setting the Kernel Type

In the aclnn engineering operator development approach, the Kernel entrypoint is decorated with `__global__ __aicore__`, and the default Kernel type is set within the entrypoint function body through the `KERNEL_TASK_TYPE_DEFAULT` API. This setting takes effect for all TilingKeys.

For example, AddCustom only performs Vector computation, so the default type can be set to `KERNEL_TYPE_AIV_ONLY`. The following code shows where the type is set in the entrypoint:

```cpp
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z,
                                                  GM_ADDR workspace, GM_ADDR tiling)
{
    KERNEL_TASK_TYPE_DEFAULT(KERNEL_TYPE_AIV_ONLY);
}
```

When you need to set different types for specific TilingKeys, use the `KERNEL_TASK_TYPE(key, value)` API. For the product support status, type values, and usage constraints of this API, see [Setting the Kernel Type](../../../../../api/SIMD-API/basic_api/Kernel-Tiling/set_Kernel_type.md).

In the Tiling template programming scenario, use `ASCENDC_TPL_KERNEL_TYPE_SEL` within `ASCENDC_TPL_ARGS_SEL` in the template parameter definition header file to set the Kernel type for that group of template parameter combinations. Under the same `ASCENDC_TPL_SEL`, when explicit type setting is selected, each `ASCENDC_TPL_ARGS_SEL` must be configured with this API. For API details and supported types, see [Template Parameter Definition](../../../../../api/Utils-API/Tiling_template_programming/template_params_definition.md).

## TilingData Processing

The Tiling function on the host side writes the parameters required for Kernel execution into TilingData. TilingData can be defined using standard C++ syntax or macro definitions, and the registration location and registration API differ between the two approaches.

### Registering TilingData

Registering TilingData is used to determine the default TilingData structure type used by the Kernel. The registration location differs between standard C++ structures and macro definition structures.

**Standard C++ structure**

When TilingData is defined using standard C++ syntax, the Kernel side registers the default structure in the entrypoint function using [REGISTER_TILING_DEFAULT](../../../../../api/SIMD-API/basic_api/Kernel-Tiling/REGISTER_TILING_DEFAULT.md).

```cpp
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z,
                                                  GM_ADDR workspace, GM_ADDR tiling)
{
    REGISTER_TILING_DEFAULT(AddCustomTilingData);
    // ...
}
```

**Macro definition structure**

When TilingData is defined using macros such as `BEGIN_TILING_DATA_DEF`, the default structure is bound to the operator type on the Host side through `REGISTER_TILING_DATA_CLASS`.

```cpp
REGISTER_TILING_DATA_CLASS(AddCustom, AddStruct)
```

The Kernel entrypoint of a macro definition structure does not use `REGISTER_TILING_DEFAULT`; instead, it obtains data directly through the TilingData access macro generated by the build.

This section only describes how to register the default TilingData. When the same operator needs to organize multiple Kernel branches, for the registration of branch-specific TilingData and the configuration of Kernel template parameters, see [Multi-Branch Strategy](./multi_branch_strategy.md).

### Obtaining TilingData

The Kernel can convert the entry parameter `GM_ADDR tiling` into a GM pointer, and then read data according to the memory layout and field offsets of TilingData. However, this approach requires the Kernel to maintain the address conversion and offset relationships by itself, and makes the code directly depend on the GM address and memory layout of dynamic compilation; the static compilation scenario still needs to be handled separately.

`GET_TILING_DATA` and `GET_TILING_DATA_WITH_STRUCT` encapsulate the differences in how Tiling data is obtained in the dynamic and static scenarios. In the dynamic compilation scenario, the macro reads Tiling data from the GM memory pointed to by the entry parameter tiling at Kernel runtime, and initializes the corresponding Tiling structure. In the static compilation scenario, Host Tiling is executed during the operator compilation phase, and the generated Tiling data is directly embedded into the Kernel code. The macro uses this embedded data to initialize the Tiling structure and no longer accesses the tiling parameter of the Kernel entry. Both scenarios use the same macro calls and field access methods, so a single set of Kernel code can support both dynamic compilation and static compilation, achieving static-dynamic unification at the Kernel source code level.

The capabilities of the two macros differ as follows:

- [GET_TILING_DATA](../../../../../api/SIMD-API/basic_api/Kernel-Tiling/GET_TILING_DATA.md)`(tiling_data, tiling_arg)`: Parses using the default TilingData type registered for the current Kernel branch. It is suitable for scenarios where only the default structure needs to be accessed.
- [GET_TILING_DATA_WITH_STRUCT](../../../../../api/SIMD-API/basic_api/Kernel-Tiling/GET_TILING_DATA_WITH_STRUCT.md)`(tiling_struct, tiling_data, tiling_arg)`: Explicitly specifies the TilingData structure type used for parsing. It can be used both for scenarios where different TilingKeys use different structures, and for scenarios where TPL/SEL template branches explicitly specify the template TilingData structure.

The default TilingData structure is parsed through `GET_TILING_DATA`. The first parameter is the name of the parsed variable, and the second parameter is the `tiling` address in the Kernel entry.

```cpp
GET_TILING_DATA(tilingData, tiling);
```

After parsing is complete, the Kernel side can read the fields in `tilingData`, for example, passing `totalLength` and `tileNum` to `KernelAdd::Init`.

```cpp
KernelAdd op;
op.Init(x, y, z, tilingData.totalLength, tilingData.tileNum);
```

When the TilingData structure type needs to be explicitly specified, parse it through `GET_TILING_DATA_WITH_STRUCT`:

```cpp
GET_TILING_DATA_WITH_STRUCT(TilingDataTemplate, tilingData, tiling);
```

The first parameter can be a branch-specific structure registered by TilingKey, or a template TilingData structure used by TPL/SEL template branches. The macro calls and field access methods are the same for both branch organization approaches. For details on how to configure branches and structures, see [Multi-Branch Strategy](./multi_branch_strategy.md). Branches that use the default structure are still parsed through `GET_TILING_DATA`.

For the TilingData definition method and the Host-side write process, see [Host-side Tiling implementation](./host_tiling_implementation.md).

## Information Acquisition

In addition to the input/output addresses and TilingData, the Kernel side can also obtain the dtype and format information of the inputs and outputs through the macros generated by the framework. This information is typically used to specify the element data type for objects such as GlobalTensor and LocalTensor, select the computation path, or handle format differences.

### Obtaining Input/Output dtype and Format

On the kernel side, you can obtain the data type and format information of inputs and outputs through three types of macros: `DTYPE_<Arg>`, `ORIG_DTYPE_<Arg>`, and `FORMAT_<Arg>`. `<Arg>` is the Kernel entry parameter name converted to all uppercase.

| Prototype definition name | Kernel entry parameter name | dtype macro | Original dtype macro | format macro |
|---|---|---|---|---|
| `x` | `x` | `DTYPE_X` | `ORIG_DTYPE_X` | `FORMAT_X` |
| `y` | `y` | `DTYPE_Y` | `ORIG_DTYPE_Y` | `FORMAT_Y` |
| `z` | `z` | `DTYPE_Z` | `ORIG_DTYPE_Z` | `FORMAT_Z` |
| `input_data` | `input_data` | `DTYPE_INPUT_DATA` | `ORIG_DTYPE_INPUT_DATA` | `FORMAT_INPUT_DATA` |
| `output_result` | `output_result` | `DTYPE_OUTPUT_RESULT` | `ORIG_DTYPE_OUTPUT_RESULT` | `FORMAT_OUTPUT_RESULT` |

The meanings of the three types of macros are as follows:

| Macro | Meaning | Common use |
|---|---|---|
| `DTYPE_<Arg>` | A C++ data type that can be used directly on the Kernel side, such as `half`, `float`, and `int32_t` | Declaring variables, `GlobalTensor`, `LocalTensor`, or template parameters |
| `ORIG_DTYPE_<Arg>` | The dtype number declared in the operator prototype, such as `DT_FLOAT16` and `DT_FLOAT` | Comparing with the dtype number to select different computation paths |
| `FORMAT_<Arg>` | The format number declared in the operator prototype, such as `FORMAT_ND` and `FORMAT_NZ` | Selecting different data organization methods based on the format |

`DTYPE_X` and `ORIG_DTYPE_X` have different focuses. Taking `x` as an example, `DTYPE_X` can be used directly as a C++ type on the Kernel side, while `ORIG_DTYPE_X` is used for comparison with the dtype number. `ORIG_DTYPE_<Arg>` and `FORMAT_<Arg>` are passed in through compilation options and are typically used for preprocessing branches.

```cpp
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z,
                                                  GM_ADDR workspace, GM_ADDR tiling)
{
    GET_TILING_DATA(tilingData, tiling);

    DTYPE_X temp;
    func<DTYPE_Z>();

    #if FORMAT_Y == FORMAT_ND
    // ND format processing logic
    #endif

    #if ORIG_DTYPE_Y == DT_FLOAT
    // float type processing logic
    #endif
}
```

> [!NOTE] Macro Usage in the Kernel Template Scenario
> In the Kernel template scenario, use macros such as `DTYPE_<Arg>`, `ORIG_DTYPE_<Arg>`, and `FORMAT_<Arg>` with `#if/#endif` to split code with caution. Both preprocessing macros and template instantiation affect the final generated code. If they are used together, check whether the macro values, retained code branches, and template arguments are consistent for each template parameter combination, to avoid the macros trimming code required by a template instantiation, or causing duplicate definitions and symbol conflicts. For branches determined by template parameters, it is recommended to use `if constexpr`.
