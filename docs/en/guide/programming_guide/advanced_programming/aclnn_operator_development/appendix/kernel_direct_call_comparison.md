# Comparison Between aclnn Engineered Operator Development and Kernel Function Direct Call

<!-- md-trans-meta sourceCommit=a5a43d2880e9cf66fe2a6174d806fb56c18d0cca translatedAt=2026-10-23T13:34:58.118Z pushedAt=2026-11-03T07:05:13.394Z nl=2 -->

This document describes the differences between aclnn engineered operator development and kernel function direct invocation, helping developers choose a development method and migrate operators.

| Feature | Kernel Function Direct Call | aclnn Engineered Operator Development |
|---|---|---|
| Call entry | Uses `<<<>>>` as the operator invocation entry, with the kernel function and execution configuration specified by the user. | Calls the operator through the generated two-stage aclnn API: the first stage obtains the workspace size and executor, and the second stage passes in the workspace, executor, and stream for execution. For details, see [Single-Operator API Call](../invocation/single_operator_api_call.md). |
| Input parameter structure specification | The kernel function entry supports passing in a struct parameter, which must be a POD type. For example:<br>`struct AddParams;`<br>`__global__ __vector__ void add_kernel(__gm__ float* x, __gm__ float* y, __gm__ float* z, AddParams params);` | The kernel function entry does not support passing in a struct object directly (pass by value). The kernel function entry passes in addresses in the order of inputs and outputs in the operator prototype, followed by the workspace and tiling addresses. Tiling parameters are organized through the TilingData struct and passed and parsed through the tiling address. For example, AddCustom has two inputs x and y and one output z, and its entry is declared as:<br>`extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z, GM_ADDR workspace, GM_ADDR tiling);`<br>where x and y are input addresses, z is the output address, workspace is the workspace address, and tiling is the tiling data address. For details, see [Operator Implementation on the Kernel Function Side](../design_and_implementation/kernel_operator_implementation.md). |
| Kernel Type | Sets the kernel function type through the `__vector__`, `__cube__`, or `__mix__` function execution space qualifier. | The kernel function entry is modified with `__global__ __aicore__`. The default type is set through `KERNEL_TASK_TYPE_DEFAULT`, or the type is set by TilingKey through `KERNEL_TASK_TYPE`. In tiling template programming scenarios, the template combination type is set through `ASCENDC_TPL_KERNEL_TYPE_SEL`. For details, see [Operator Implementation on the Kernel Function Side](../design_and_implementation/kernel_operator_implementation.md). |
| Scheduling mode | Sets the kernel function scheduling mode through the `__schedmode__(mode)` qualifier. | Calls `TilingContext::SetScheduleMode` in the host-side tiling to set the scheduling mode. For details, see [Scheduling Mode Constraints of SyncAll](../../../../../api/SIMD-API/basic_api/sync_control/inter_core_sync/SyncAll.md). |
| KFC workspace address setting | In KFC scenarios, the system workspace must be reserved, and the workspace parameter of the kernel function entry must be marked with `__kfc_workspace__` so that the compiler can initialize the KFC workspace address. | In KFC scenarios, the required system workspace must be reserved in the host-side tiling. The KFC workspace address initialization on the kernel side is automatically handled by the framework. Users only need to keep the workspace entry parameter according to the engineering specification, without adding the `__kfc_workspace__` marker. For details, see [How to Use Workspace](../../../appendix/common_operations/how_to_use_workspace.md). |
| SuperKernel adaptation | Requires the user to provide a SuperKernel entry function modified with `__sk__` and bind it to the normal kernel function entry through the `SK_BIND` macro to complete SuperKernel adaptation. | SuperKernel entry adaptation is automatically completed inside the framework. Users do not need to configure `__sk__` and `SK_BIND`. The operator must still meet the general constraints in [Operator Adaptation Description](../../super_kernel/operator_adaptation.md). |
