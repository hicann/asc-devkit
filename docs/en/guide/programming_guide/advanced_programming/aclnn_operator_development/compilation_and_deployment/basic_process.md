# Basic Compilation and Deployment Process

<!-- md-trans-meta sourceCommit=fbd15d5df1f452aabb0f40f2b83dd25017ebaa8f translatedAt=2026-10-23T13:38:25.009Z pushedAt=2026-11-03T07:05:13.398Z nl=2 -->

This document covers the basics. It describes how to compile an operator project and generate a custom operator installation package \*.run after the kernel function side and Host side implementations are developed. The detailed compilation operations include:

-   Compile the Ascend C operator kernel function side implementation files \*.cpp. Two modes are available: source release and binary release.
    -   **Source release**<a id="source-release"></a>: The kernel function side implementation is not compiled, and the kernel function source files \*.cpp are retained. This mode supports online compilation of operators and compilation of operators through ATC model conversion.
    -   **Binary release**: The kernel function side implementation is compiled to generate a JSON file \*.json that describes operator-related information and an operator binary file \*.o. Use this compilation mode when the operator binary needs to be directly invoked, for example, to invoke a single operator through [single-operator API call](../invocation/single_operator_api_call.md), in single operator invocation scenarios in the PyTorch framework, and in scenarios where operators are invoked in dynamic networks.

-   Compile the Ascend C operator host side implementation files \*.cpp and \*.h.
    -   Compile the prototype definition and shape derivation implementation into the operator prototype definition dynamic library **libcust\_opsproto\_\*.so**, and generate the operator prototype external interface **op\_proto.h**.
    -   Compile the tiling implementation into the tiling dynamic library **liboptiling.so** and others.
    -   Based on the operator prototype definition, automatically generate the single operator API call code and header file **aclnn\_\*.h**, and compile them into the single operator API call dynamic library **libcust\_opapi.so**.

### Basic Process

A project generated by msOpGen already contains a complete CMake structure, so you do not need to write a separate CMakeLists.txt. If you need to write a CMakeLists.txt yourself, see [Compilation Organization](#compilation-organization-advanced). Taking [AddCustom in Quick Start](../aclnn_quick_start.md) as an example, compiling and deploying an operator project generated by msOpGen requires only three steps:

1. Modify `CMakePresets.json` and fill in compilation configuration options such as `ASCEND_SOC_SERIES` or `ASCEND_COMPUTE_UNIT` (choose either one) and `vendor_name` (vendor name).
2. Run `./build.sh` to generate the `custom_opp_*.run` installation package.
3. Run `./custom_opp_*.run` to install it to the runtime environment.

The following sections describe the options and details of each step.

## Compilation Configuration<a id="compile-configuration"></a>

There are two mandatory parameters for compilation configuration options. For the chip series, configure either `ASCEND_SOC_SERIES` or `ASCEND_COMPUTE_UNIT`:

| Parameter | Description | Default Value |
|---------|---------|--------|
| ASCEND_SOC_SERIES | AI processor series. One or more values can be configured. The input is case-insensitive, and the configured values are first normalized to lowercase. | None |
| ASCEND_COMPUTE_UNIT | AI processor model, configured based on the actual running chip. | "ascendxxx" |
| vendor_name | Vendor name of the custom operator, used to form the `vendors/<vendor_name>` installation directory to avoid conflicts with operator packages of other vendors. Operator packages with the same `vendor_name` under the same installation path are installed to the same directory, and files with the same name are overwritten. | "customize" |

`ASCEND_SOC_SERIES` and `ASCEND_COMPUTE_UNIT` cannot be configured at the same time, and `ASCEND_SOC_SERIES` cannot be empty.

In addition to the mandatory parameters above, other optional compilation configuration options are as follows:

| Type | Option Name | Default Value | Description |
|------|--------|--------|------|
| STRING | CMAKE_BUILD_TYPE | Release | Compilation type. Supports Release and Debug. Release version: does not contain debugging information and is compiled for the final release. Debug version: contains debugging information and is used for development and debugging. |
| PATH | ASCEND_AUTOGEN_PATH | <CMAKE_BINARY_DIR>/autogen | Storage path of the auto-generated code. |
| PATH | ASCEND_CANN_PACKAGE_PATH | - | CANN package path. An example of the default path is /usr/local/Ascend/cann. |
| BOOL | ENABLE_SOURCE_PACKAGE | TRUE | Whether to enable source code compilation. If npu_op_package is used to configure source code and binary compilation related settings, the npu_op_package configuration takes higher priority. |
| BOOL | ENABLE_BINARY_PACKAGE | TRUE | Whether to enable binary compilation. When the package type is configured as SHARED or STATIC, it must be set to TRUE. If npu_op_package is used to configure source code and binary compilation related settings, the npu_op_package configuration takes higher priority. |
| BOOL | ENABLE_CROSS_COMPILE | FALSE | Whether to enable cross compilation. For details, see [Cross Compilation](./cross_compilation.md). |
| PATH | CMAKE_CROSS_PLATFORM_COMPILER | /your/cross/compiler/path | Cross compilation tool path. |
| BOOL | ASCEND_PACK_SHARED_LIBRARY | FALSE | Whether to enable dynamic library compilation. |
| BOOL | ASCEND_SKIP_FAILED_COMPUTE_UNIT | FALSE | Controls whether to skip the failure and continue compiling operators of other models when the compilation of operators corresponding to some AI processor models fails. Set to True to skip the failure, which does not affect the compilation process of operators corresponding to other AI processor models. Set to False, and a failure affects the compilation process of operators corresponding to other AI processor models. |

There are two methods to modify compilation configuration options:

### Method 1: Modifying CMakePresets.json

If the project directory contains `CMakePresets.json`, modify the `cacheVariables` in it. Projects generated by msOpGen use this method by default.

> [!NOTE] Note
>
> Directly running `cmake --preset=default` requires CMake 3.19 or later. The `build.sh` generated by msOpGen parses `CMakePresets.json` and converts it into regular `cmake -D` parameters in lower-version CMake environments. Therefore, it is recommended to use the `build.sh` provided with the project.

**Minimal configuration example:**

```json
{
    "version": 1,
    "cmakeMinimumRequired": {
        "major": 3,
        "minor": 19,
        "patch": 0
    },
    "configurePresets": [
        {
            "name": "default",
            "cacheVariables": {
                "ASCEND_COMPUTE_UNIT": {
                    "type": "STRING",
                    "value": "ascendxxyy"
                },
                "vendor_name": {
                    "type": "STRING",
                    "value": "customize"
                }
            }
        }
    ]
}
```

### Method 2: Setting in CMakeLists.txt

Set variables directly in the top-level CMakeLists.txt and configure the compilation behavior through the `npu_op_*` interfaces, without the need for a CMakePresets.json file.

```cmake
# Set the required variables. You can also use the variable ASCEND_SOC_SERIES, but the two cannot be set at the same time.
set(ASCEND_COMPUTE_UNIT "ascendxxxyy") | set(ASCEND_SOC_SERIES "Ascendxxx")
set(vendor_name "customize")

# Configure the compilation output package (use the CONFIG parameter instead of variables such as ENABLE_SOURCE_PACKAGE / ENABLE_BINARY_PACKAGE).
npu_op_package(${vendor_name}
    TYPE RUN
    CONFIG
        ENABLE_SOURCE_PACKAGE True
        ENABLE_BINARY_PACKAGE True
        INSTALL_PATH ${CMAKE_BINARY_DIR}/
)
```

Other configurations (such as dynamic library compilation and cross compilation) can also be set in CMakeLists.txt through variables or the `npu_op_package` CONFIG parameter. For a complete description of the parameters, see [cmake function reference](../appendix/cmake_function_reference.md).

Note that if the values of `ENABLE_SOURCE_PACKAGE` or `ENABLE_BINARY_PACKAGE` are hardcoded in `npu_op_package(... CONFIG ...)` (for example, the sample in this section directly writes True), the variables with the same names on the command line or in `CMakePresets.json` cannot override them. To allow external variables to take effect, use the variable forms `${ENABLE_SOURCE_PACKAGE}` and `${ENABLE_BINARY_PACKAGE}` in CONFIG.

## Running Compilation

There are two compilation methods:

**Method 1: Use the build.sh script**

If the project directory contains a `build.sh` script (provided by default in projects generated by msOpGen), run it directly:

```bash
./build.sh
```

**Method 2: Run the cmake command**

```bash
cmake -S . -B build_out --preset=default
cmake --build build_out --target binary package -j$(nproc)
```

- `cmake -S . -B build_out --preset=default` is the CMake configuration and generation phase: it reads the source code, `CMakeLists.txt`, and the `default` configuration in `CMakePresets.json` from the current directory, and generates the build files required for subsequent compilation in the `build_out` directory.

- `cmake --build build_out --target binary package -j$(nproc)` is the actual compilation and packaging phase: it uses the build files already generated in `build_out` to execute the `binary` and `package` targets. `binary` is responsible for compiling the operator binary-related artifacts, `package` is responsible for generating the operator installation package, and `-j$(nproc)` indicates parallel compilation based on the number of CPU cores on the current machine.

After successful compilation, the custom operator installation package `custom_opp_<target os>_<target architecture>.run` is generated in the compilation output directory. This run package contains the operator prototype library, Tiling library, aclnn API library, and kernel function binaries. After deployment, the framework automatically scans and loads them.

**Compilation log storage** (optional):

If you need to save the compilation process logs, you can use the environment variable **ASCENDC\_BUILD\_LOG\_DIR** to control the storage path. After you set this option, if no error occurs during compilation, the suffix "\_success" is added to the corresponding log file name. If an error occurs during compilation, the corresponding error information is printed on the screen, and the specific path and file name of the log file are indicated. Meanwhile, the suffix "\_error" is added to the corresponding log file name.

```
# If you want the compilation logs to be stored in /home/build_log/, configure it as follows. Log storage is disabled by default.
export ASCENDC_BUILD_LOG_DIR=/home/build_log/
```

<a id="operator-package-deployment"></a>
## Operator Package Deployment<a id="operator-package-deployment"></a>

The operator installation package generated by compilation needs to be deployed to the runtime environment.

### Installing the Operator Package

In the directory where the custom operator package is located, run the installation command:

```bash
# Source the environment variables of the CANN package. The default installation path is used as an example.
source /usr/local/Ascend/cann/set_env.sh
# Install the custom operator run package.
./custom_opp_<target os>_<target architecture>.run --install-path=<path>
```

`--install-path` is an optional parameter that specifies the installation directory. It supports absolute paths and requires read and write permissions on the target path.

#### Default Installation (Without --install-path)

Install to the `$ASCEND_OPP_PATH/vendors/<vendor_name>` directory (`$ASCEND_OPP_PATH` is usually equal to `${CANN installation path}/opp`; take the default installation path as an example: `/usr/local/Ascend/cann/opp`).

> **Path relationship note**: In the default installation scenario, the operator package is deployed to `$ASCEND_OPP_PATH/vendors/<vendor_name>`. The installation script writes the current vendor to the `load_priority` configuration item in `$ASCEND_OPP_PATH/vendors/config.ini`, and the framework loads the operator package in the default path according to this configuration.

**Table 3** Comparison between default installation and installation to a specified directory.

| Installation method | Installation command | Installation path | Whether the user needs to source the environment variable of the custom operator package after installation | Priority |
|---------|---------|---------|----------------|--------|
| Default installation | `./custom_opp_*.run` | `${ASCEND_OPP_PATH}/vendors/<vendor_name>` | No, takes effect automatically | Lower |
| Installation to a specified directory | `./custom_opp_*.run --install-path=<path>` | `<path>/vendors/<vendor_name>` | Yes, the environment variable needs to be sourced | Higher |

> [!NOTE] Note
> - The permission of the default installation path is related to the CANN software package installation user and configuration. If the installation fails due to insufficient permissions, install to a specified directory or contact the CANN installation user to modify the permissions.
> - After installation to a specified directory, run `source <path>/vendors/<vendor_name>/bin/set_env.bash` before calling the operator. This script adds the operator package directory `<path>/vendors/<vendor_name>` to the beginning of the `ASCEND_CUSTOM_OPP_PATH` environment variable so that the framework can find the custom operator package at runtime. It also adds `<path>/vendors/<vendor_name>/op_api/lib/` to the beginning of the `LD_LIBRARY_PATH` environment variable so that the system dynamic linker can find the operator dynamic library.
> - The operator package architecture must be consistent with the system architecture and meet the glibc version dependency. Otherwise, use `--force` to force the installation.

<a id="configuring-custom-operator-priority"></a>
### Configuring the Priority of Custom Operators

When multiple operator packages coexist and contain operators with the same OpType, the version in the operator package with the higher priority takes effect.

#### Default Installation Scenario

When multiple operator packages contain the same OpType, you can adjust the loading priority of each custom operator by configuring the `opp/vendors/config.ini` file. In other scenarios, manually modifying this file is not recommended. The content of the `opp/vendors/config.ini` file is as follows:

```ini
load_priority=vendor_name1,vendor_name2,vendor_name3
```

A valid `load_priority` configuration must meet the following requirements:

- The configuration item name must be `load_priority` and cannot be modified.
- The right side of the equal sign must contain at least one vendor name and cannot be empty. The vendor name must be consistent with the directory name of the installed operator package under the `opp/vendors` directory.
- When multiple vendors are configured, separate them with commas. The priority of vendors is determined from left to right, with the leftmost vendor having the highest priority.

For example, `load_priority=vendor_name1,vendor_name2,vendor_name3` is a valid configuration. `load_priority=`, a missing `load_priority` configuration item, or a modified configuration item name are all invalid configurations.

During default installation, if `config.ini` does not exist, the installation script creates the file and writes the current vendor into it. If the file already exists, the installation script moves the current vendor to the first position based on the valid `load_priority` configuration. During installation or upgrade, if the configuration is invalid, the file cannot be read or written, or the configuration update result does not meet expectations, the script reports an error and stops the installation or upgrade without automatically completing or correcting the abnormal configuration.

#### Specified Directory Installation Scenario<a id="custom-install-path"></a>

Run the `set_env.bash` script in the installation path of each operator package separately. The later the script is executed, the higher its priority.

```bash
source <path>/vendors/vendor_name1/bin/set_env.bash  #Executed first, lower priority
source <path>/vendors/vendor_name2/bin/set_env.bash  #Executed later, higher priority
```

Example of `ASCEND_CUSTOM_OPP_PATH` after execution:

```
ASCEND_CUSTOM_OPP_PATH=<path>/vendors/vendor_name2:<path>/vendors/vendor_name1:
```

### Uninstalling and Updating an Operator Package

#### Uninstalling the Operator Package

The operator package installation directory contains the `uninstall.sh` script. Run the script to complete the uninstallation:

**Default installation scenario**:

```bash
bash ${INSTALL_DIR}/opp/vendors/<vendor_name>/scripts/uninstall.sh
```

**Specified directory installation scenario**:

```bash
bash <path>/vendors/<vendor_name>/scripts/uninstall.sh
```

#### Updating the Operator Package

**Default installation scenario**: Re-run the installation command to overwrite the old version.

```bash
# Source the environment variables of the CANN package. The default path is used as an example.
source /usr/local/Ascend/cann/set_env.sh
# Install the custom operator run package.
./custom_opp_<target os>_<target architecture>.run
```

**Specified directory installation scenario**: Uninstall the old version first, and then install the new version.

```bash
# 1. Uninstall the old version.
bash <path>/vendors/<vendor_name>/scripts/uninstall.sh

# 2. Install the new version.
# Source the environment variables of the CANN package. The default path is used as an example.
source /usr/local/Ascend/cann/set_env.sh
# Install the custom operator run package.
./custom_opp_<target os>_<target architecture>.run --install-path=<path>
```

> [!NOTE] Note
> - After the operator package is updated, source the environment variables again (specified directory installation scenario).
> - If you need to roll back to the old version, back up the old operator package first.

## Compilation Organization (Advanced)<a id="advanced-build-organization"></a>

An operator project organizes compilation through CMake. If you need to organize the project on your own or customize the compilation process using the CMake modules provided by CANN, refer to the following content.

The directory organization of an operator project is not fixed. The following only illustrates two common methods. You can also place the Host, kernel function, and Tiling files completely flat in the same directory, as long as CMakeLists.txt correctly passes the source files and the `npu_op_*` interface parameters.

| Method | Feature | Application Scenario |
|------|------|----------|
| By Host/kernel function | Host code and kernel function code are in separate directories, with three levels of CMakeLists. | Generated by msOpGen by default, for a single operator or a small number of operators. |
| By operator | Each operator has an independent directory that maintains its own source file list and kernel function declaration. | Multi-operator projects with high independence between operators. |

The msOpGen tool generates the "by Host/kernel function" structure by default.

### Directory Structure Divided by Host/Kernel Function

The Host-side code of all operators is centralized in the `op_host/` directory, and the kernel function-side code is centralized in the `op_kernel/` directory. The project contains three levels of CMakeLists.txt: the top level defines the operator package and adds subdirectories, `op_host/` compiles the Host-side library, and `op_kernel/` compiles the kernel function-side library.

**1. Top-level CMakeLists.txt**

The top-level CMakeLists.txt sets the compilation environment, defines the package form, and adds subdirectories:

1.  Use **find\_package** to locate the required compilation library.
2.  Use **npu\_op\_package** to set the compilation output form of the operator project. RUN, SHARED, and STATIC are supported, corresponding to the operator run package form, operator dynamic library form, and operator static library form, respectively. In addition, this API can configure the content of the package (that is, the compilation artifact) and the installation location of the package.
3.  Add the subdirectories to be compiled.

```cmake
cmake_minimum_required(VERSION 3.19.0)
project(opp)

# 1. Use find_package to find the ASC CMake modules provided by the CANN software package
find_package(ASC REQUIRED HINTS ${ASCEND_CANN_PACKAGE_PATH}/compiler/tikcpp/ascendc_kernel_cmake)

# 2. Set the compilation output form of the operator project
# vendor_name is configured in CMakePresets.json to distinguish operator packages of different vendors
set(package_name ${vendor_name})
npu_op_package(${package_name}
    TYPE RUN                                       #Compilation output form: RUN/STATIC/SHARED
    CONFIG
        ENABLE_SOURCE_PACKAGE True
        ENABLE_BINARY_PACKAGE True
        INSTALL_PATH ${CMAKE_BINARY_DIR}/
)

# 3. Add the Host and kernel function subdirectories for compilation
if(EXISTS ${CMAKE_CURRENT_SOURCE_DIR}/op_host)
    add_subdirectory(op_host)
endif()
if(EXISTS ${CMAKE_CURRENT_SOURCE_DIR}/op_kernel)
    add_subdirectory(op_kernel)
endif()
```

**TYPE parameter description**:
- `RUN`: generates a run package for operator deployment.
- `SHARED`: generates a dynamic library for integration into applications.
- `STATIC`: generates a static library for static linking.

**2. Host-side CMakeLists.txt**

The CMakeLists.txt under `op_host/` generates the aclnn call code and compiles various Host-side libraries:

1.  Use **npu\_op\_code\_gen** to generate the aclnn single-operator call code, the prototype definition code required for graph compilation, and so on.
2.  In the single-operator call scenario, use **npu\_op\_library** to compile the aclnn single-operator call library.
3.  In the operator graph compilation scenario, use **npu\_op\_library** to compile the operator prototype library required for graph compilation.
4.  Use **npu\_op\_library** to compile the tiling-related library.
5.  Use **npu\_op\_package\_add** to add the preceding host-side libraries to the corresponding package.

```cmake
aux_source_directory(${CMAKE_CURRENT_SOURCE_DIR} ops_srcs)

# 1. Generate the aclnn call code and prototype definition code
npu_op_code_gen(
    SRC ${ops_srcs}
    PACKAGE ${package_name}
    OUT_DIR ${ASCEND_AUTOGEN_PATH}
)

# 2. Compile the aclnn single operator call library
file(GLOB autogen_aclnn_src ${ASCEND_AUTOGEN_PATH}/aclnn_*.cpp)
set_source_files_properties(${autogen_aclnn_src} PROPERTIES GENERATED TRUE)
npu_op_library(cust_opapi ACLNN
    ${autogen_aclnn_src}
)
target_compile_options(cust_opapi PRIVATE -fvisibility=hidden)

# 3. Compile the operator prototype library (for graph integration)
file(GLOB proto_src ${ASCEND_AUTOGEN_PATH}/op_proto.cc)
set_source_files_properties(${proto_src} PROPERTIES GENERATED TRUE)
npu_op_library(cust_op_proto GRAPH
    ${ops_srcs}
    ${proto_src}
)
target_compile_options(cust_op_proto PRIVATE -fvisibility=hidden)

# 4. Compile the Tiling library
file(GLOB fallback_src ${ASCEND_AUTOGEN_PATH}/fallback_*.cpp)
set_source_files_properties(${fallback_src} PROPERTIES GENERATED TRUE)
npu_op_library(cust_optiling TILING
    ${ops_srcs}
    ${fallback_src}
)
target_compile_options(cust_optiling PRIVATE -fvisibility=hidden)

# 5. Add the Host-side library to the package
npu_op_package_add(${package_name}
    LIBRARY
        cust_optiling
        cust_opapi
        cust_op_proto
)
```

**3. CMakeLists.txt on the kernel function side**

The CMakeLists.txt under `op_kernel/` configures the kernel function compilation options, specifies the source code, and compiles the kernel function library:

1.  Use **npu\_op\_kernel\_options** to add [operator compilation options](#custom-compilation-options-advanced).
2.  Use **npu\_op\_kernel\_sources** to specify the operator-specific directory and source files to compile.
    -   If the operator's source files are not placed directly under the `SRC_BASE` directory (set through `npu_op_kernel_library`), you can specify a specific directory through `KERNEL_DIR`.
    -   If the operator's kernel function implementation cpp file needs a custom name, specify both `OP_TYPE` (operator type) and `KERNEL_FILE` (kernel function implementation cpp file name) to configure the correspondence between them. If not configured, the kernel function implementation cpp file name and OpType must comply with the [conversion rules](../appendix/naming_conversion_table.md).

3.  Use **npu\_op\_kernel\_library** to compile the kernel function library.
4.  Use **npu\_op\_package\_add** to add the preceding kernel function side library to the corresponding package.

```cmake
# 1. Set kernel function compilation options
npu_op_kernel_options(ascendc_kernels ALL OPTIONS --save-temp-files -g)

# 2. Specify the kernel function source code
npu_op_kernel_sources(ascendc_kernels
    OP_TYPE AddCustom                              # Operator type
    COMPUTE_UNIT ascendxxxyy                       # AI processor model
    KERNEL_FILE add_custom.cpp                     # Kernel implementation file name
)
Or
npu_op_kernel_sources(ascendc_kernels
    OP_TYPE AddCustom                              # Operator type
    SOC_SERIES Ascendxxx                           # AI processor model
    KERNEL_FILE add_custom.cpp                     # Kernel implementation file name
)

# 3. Compile the kernel function library
npu_op_kernel_library(ascendc_kernels
    SRC_BASE ${CMAKE_SOURCE_DIR}/op_kernel/        # Root directory of the kernel function source code
    TILING_LIBRARY cust_optiling                   # Dependent Tiling library
)

# 4. Add the kernel function library to the package
npu_op_package_add(${package_name}
    LIBRARY ascendc_kernels
)
```

In the example, the kernel function implementation file is named `add_custom.cpp`, so both `OP_TYPE` and `KERNEL_FILE` are specified in `npu_op_kernel_sources`. To scan the kernel function source code by directory, use `KERNEL_DIR ./` instead. In this case, `KERNEL_DIR` is relative to `SRC_BASE` in the subsequent `npu_op_kernel_library`.

### Operator-Based Directory Structure

When a project contains multiple operators with high independence, dividing by operator is more convenient for maintenance: the Host, kernel function, and Tiling files of each operator are placed in the same directory, and adding a new operator only requires adding an independent subdirectory.

In the following example, the top-level CMakeLists.txt centrally lists the Host source files of each operator and declares the kernel function source code information of each operator through `npu_op_kernel_sources`. Finally, `npu_op_code_gen`, `npu_op_library`, `npu_op_kernel_library`, and `npu_op_package_add` complete code generation, compilation, and packaging.

**1. Directory structure**

Take the three operators AddCustom, AddCustom2, and AddCustom3 as an example:

```text
add_custom/
├── add_custom.cpp           # Host-side prototype definition, shape inference, and Tiling implementation
├── add_custom_kernel.cpp    # Kernel function implementation
└── add_custom_tiling.h      # Tiling data structure definition
add_custom2/
├── add_custom2.cpp
├── add_custom2_kernel.cpp
└── add_custom2_tiling.h
add_custom3/
├── add_custom3.cpp
├── add_custom3_kernel.cpp
└── add_custom3_tiling.h
```

**2. Top-level CMakeLists.txt**

The top-level CMakeLists.txt sets up the compilation environment, defines the package form, declares the Host/kernel function files of each operator, and completes the packaging of the Host-side library, kernel function-side library, and operator package.

```cmake
cmake_minimum_required(VERSION 3.19.0)
project(opp)

# Find the ASC CMake modules provided by CANN. ASCEND_CANN_PACKAGE_PATH is usually configured in CMakePresets.json.
find_package(ASC REQUIRED HINTS ${ASCEND_CANN_PACKAGE_PATH}/compiler/tikcpp/ascendc_kernel_cmake)

# vendor_name is configured in CMakePresets.json and used as the vendor identifier of the operator package. npu_op_package defines an operator package target.
set(package_name ${vendor_name})
npu_op_package(${package_name}
    TYPE RUN
    CONFIG
        INSTALL_PATH ${CMAKE_BINARY_DIR}/
)

# 1. Declare the Host source files of all operators.
set(ops_srcs
    ${CMAKE_CURRENT_SOURCE_DIR}/add_custom/add_custom.cpp
    ${CMAKE_CURRENT_SOURCE_DIR}/add_custom2/add_custom2.cpp
    ${CMAKE_CURRENT_SOURCE_DIR}/add_custom3/add_custom3.cpp
)

# 2. Generate the aclnn call code and prototype definition code in a unified manner.
# npu_op_code_gen must be called before npu_op_kernel_sources,
# because npu_op_kernel_sources depends on the auto-generated file path set here.
npu_op_code_gen(
    SRC ${ops_srcs}
    PACKAGE ${package_name}
    OUT_DIR ${ASCEND_AUTOGEN_PATH}
)

# 3. Compile the aclnn single operator call library.
# After npu_op_code_gen is executed, aclnn_*.cpp/aclnn_*.h are generated under ASCEND_AUTOGEN_PATH.
file(GLOB autogen_aclnn_src ${ASCEND_AUTOGEN_PATH}/aclnn_*.cpp)
set_source_files_properties(${autogen_aclnn_src} PROPERTIES GENERATED TRUE)
npu_op_library(cust_opapi ACLNN
    ${autogen_aclnn_src}
)
target_compile_options(cust_opapi PRIVATE -fvisibility=hidden)

# 4. Compile the operator prototype library (for graph integration).
# The prototype library depends on both the Host source files of each operator and the auto-generated op_proto code.
file(GLOB group_proto_src ${ASCEND_AUTOGEN_PATH}/group_op_proto/*.cc)
file(GLOB proto_src ${ASCEND_AUTOGEN_PATH}/op_proto.cc)
set_source_files_properties(${group_proto_src} PROPERTIES GENERATED TRUE)
set_source_files_properties(${proto_src} PROPERTIES GENERATED TRUE)
npu_op_library(cust_op_proto GRAPH
    ${ops_srcs}
    ${group_proto_src}
    ${proto_src}
)
target_compile_options(cust_op_proto PRIVATE -fvisibility=hidden)

# 5. Compile the Tiling library.
# The Tiling implementation is located in the Host source file of each operator; fallback_*.cpp is the auxiliary code generated by npu_op_code_gen.
file(GLOB fallback_src ${ASCEND_AUTOGEN_PATH}/fallback_*.cpp)
set_source_files_properties(${fallback_src} PROPERTIES GENERATED TRUE)
npu_op_library(cust_optiling TILING
    ${ops_srcs}
    ${fallback_src}
)
target_compile_options(cust_optiling PRIVATE -fvisibility=hidden)

# 6. Declare the kernel function source code information of each operator.
# KERNEL_DIR is relative to the SRC_BASE of npu_op_kernel_library below.
npu_op_kernel_sources(ascendc_kernels
    OP_TYPE AddCustom
    KERNEL_DIR add_custom
    KERNEL_FILE add_custom_kernel.cpp
)
npu_op_kernel_sources(ascendc_kernels
    OP_TYPE AddCustom2
    KERNEL_DIR add_custom2
    KERNEL_FILE add_custom2_kernel.cpp
)
npu_op_kernel_sources(ascendc_kernels
    OP_TYPE AddCustom3
    KERNEL_DIR add_custom3
    KERNEL_FILE add_custom3_kernel.cpp
)

# 7. Compile the kernel function library.
# SRC_BASE is the common source root directory of all operator directories; TILING_LIBRARY points to the Tiling library compiled above.
npu_op_kernel_library(ascendc_kernels
    SRC_BASE ${CMAKE_CURRENT_SOURCE_DIR}/
    TILING_LIBRARY cust_optiling
)

# 8. Add the Host-side library and the kernel function library to the operator package to generate the run package.
npu_op_package_add(${package_name}
    LIBRARY
        cust_optiling
        cust_opapi
        cust_op_proto
        ascendc_kernels
)
```


> [!NOTE] Note
> - The example lists the Host source files and kernel function source code information of each operator centrally at the top level to show the calling relationship of the `npu_op_*` APIs. If the project has its own directory encapsulation, it is sufficient that the Host source files passed to `npu_op_code_gen`, the `OP_TYPE`/`KERNEL_DIR`/`KERNEL_FILE` passed to `npu_op_kernel_sources`, and the `SRC_BASE` passed to `npu_op_kernel_library` match.
> - `npu_op_kernel_sources` depends on the auto-generated file path set by `npu_op_code_gen`, so it must be called after `npu_op_code_gen`.
> - `OP_TYPE` must be consistent with the OpType in the operator prototype registration. When the kernel function file name is not the file name obtained by default conversion from OpType, `KERNEL_FILE` must be explicitly specified.
> - When adding an operator, you only need to add an operator subdirectory, append the Host source file to `ops_srcs`, and add a set of `npu_op_kernel_sources` configurations.

**Key differences from "division by Host/kernel function"**:
- Host-side source files are listed by operator directory, and `npu_op_code_gen` is called uniformly at the top level.
- The source code information of the kernel function is declared by operator directory, and `npu_op_kernel_sources` is called uniformly at the top level after `npu_op_code_gen`.
- `SRC_BASE` points to the common source root directory of all operator directories, and `KERNEL_DIR` points to the specific operator subdirectory.
- The Host, kernel function, and Tiling files of each operator are placed in the same directory.

> For details about the cmake function parameters, see [cmake Function Reference](../appendix/cmake_function_reference.md).

After the compilation organization is complete, you can complete operator compilation and deployment by following the three steps in [Basic Process](#basic-process).

## Custom Compilation Options (Advanced)<a id="custom-compile-options"></a>

In CMakeLists.txt, use `npu_op_kernel_options` to add compilation options for the kernel function side code:

```cmake
npu_op_kernel_options(<target_name> <op_type> [COMPUTE_UNIT <soc_version>... | SOC_SERIES <series>...] OPTIONS ...)
```

**Table 4** Parameters.

| Parameter | Optional/Required | Description |
|---------|----------|---------|
| target_name | Required | Target name of the kernel function library (for example, `ascendc_kernels`). |
| op_type | Required | Operator type. To apply to all operators, set it to `ALL`. |
| COMPUTE_UNIT | Optional | AI processor model. If not configured, it applies to all models. It cannot be used together with `SOC_SERIES`. |
| SOC_SERIES | Optional | AI processor series. The input is case-insensitive. It cannot be used together with `COMPUTE_UNIT`. |
| OPTIONS | Required | Custom compilation options, separated by spaces. Options such as `--save-temp-files`, `-g`, and `-DASCENDC_DEBUG` are supported. |

**Common examples**:

```cmake
# Keep the intermediate products of kernel function compilation for all operators.
npu_op_kernel_options(ascendc_kernels ALL OPTIONS --save-temp-files)

# Enable the AscendC debug macro for a specific operator on a specific model.
npu_op_kernel_options(ascendc_kernels AddCustom COMPUTE_UNIT ascendxxxyy OPTIONS -DASCENDC_DEBUG)

# Use SOC_SERIES to configure by series, with multiple values separated by spaces.
npu_op_kernel_options(ascendc_kernels AddCustom SOC_SERIES Ascendxxx OPTIONS -DASCENDC_DEBUG)
```

> [!NOTE] Note
> - Compilation options are configured based on "operator type + AI processor model series". That is, different "operator type + AI processor model series" combinations can be configured with different compilation options.
> - If compilation options are configured multiple times for the same operator type + AI processor model series, the last configuration takes effect.
> - If there is no conflict between compilation options that apply to ALL and those that apply to a single operator, both take effect. If there is a conflict, the compilation options for the single operator take precedence.

The compilation options provided by the Ascend C framework are described as follows:

-   `--tiling_key`: after this option is set, only the kernel function code related to the specified [TilingKey](../design_and_implementation/multi_branch_strategy.md#compile-selected-tiling-keys) is compiled, which accelerates the compilation process. If no TilingKey is specified for compilation, all TilingKeys are compiled by default. When multiple TilingKeys are configured, no spaces are allowed between them. An example is as follows, where 1 and 2 are TilingKey values.

    ```
    --tiling_key=1,2
    ```

-   For compilation macro switches, see [Built-in Compilation Macro Switches](../../../compilation_and_execution/operator_compilation/ai_core_operator_compilation.md).
-   `--op_relocatable_kernel_binary`: when this option is set to true, an additional relocatable binary file is compiled; when it is not configured or is set to false, this option does not take effect. This option is used in the scenario where a custom Tiling-offloaded operator enables SuperKernel. The binary file generated with this option configured allows the operator to directly reuse the binary file during SuperKernel compilation, reducing compilation time.
-   `--kernel-template-input`: compiles the kernel function code related to the specified template parameter combination to accelerate the compilation process. For more information, see [Compilation Acceleration — Selective Compilation](./compilation_acceleration.md#selective-compilation).
-   `-DFORCE_TILING_CONST_PROPAGATION`: this option is used for constant optimization of Tiling data in static shape scenarios. For complex operators, this compilation option can improve the static shape execution performance of the operator. This compilation option is supported only by custom operator projects, and it takes effect only when the operator uses `BEGIN_TILING_DATA_DEF` to register the Tiling structure; it does not take effect when the operator uses standard C++ syntax to define the Tiling structure. A usage example is as follows:
    ```
    -DFORCE_TILING_CONST_PROPAGATION
    ```
    The principle of this compilation option is that, in the scenario where the operator uses `BEGIN_TILING_DATA_DEF` to register the Tiling structure, when the custom operator project defines the Tiling structure, it defines all its member variables as static constexpr constants, that is, it turns the Tiling structure into a static constant class. Because the constants are marked at the frontend, the compiler performs more thorough constant folding and optimization based on the Tiling data.
    
    This option imposes constraints on the operator implementation. The following scenarios are not supported:

    1. The operator code must not define non-const objects using the Tiling structure, nor assign values to members of a Tiling object. Otherwise, a compilation error occurs because static constants cannot be reassigned.

    2. The operator code must not contain `reinterpret_cast<OtherType*>(tiling_data)`. Otherwise, unexpected results are obtained. This is because all members of the Tiling structure are constants, the object of this type has no entity, its size is always 1 byte, and `reinterpret_cast` on `tiling_data` produces undefined behavior.

    For the scenario where the operator uses standard C++ syntax to define the Tiling structure, this option does not take effect because when the operator defines the Tiling structure as static constexpr, the Tiling data cannot be obtained, and the members of the Tiling structure cannot be initialized at definition time.

-   --save-temp-files: this option is used to retain the temporary files generated during the compilation of the kernel function side. During compilation, different `kernel.o` compilations are triggered based on permutations and combinations of factors such as the chip type and the dtype/format of the input and output. Enabling this option allows you to view the compilation process of each `kernel.o`, which helps locate issues.

    After adding this compilation option and executing project compilation, you can view the intermediate files, such as the kernel function source code and compilation commands that actually participate in compilation, in the `build/op_kernel/<OpType>_<soc>/kernel_*/kernel_meta_*/kernel_meta` directory, where `<OpType>` indicates the operator type and `<soc>` indicates the target chip type for compilation.
