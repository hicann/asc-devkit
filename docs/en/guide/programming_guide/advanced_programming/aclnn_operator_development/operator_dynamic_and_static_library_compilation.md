## Operator Library Compilation<a name="section187261217143316"></a>

Compiling dynamic and static operator libraries is the process of compiling operator implementation code and related files into dynamic libraries and static libraries. Compared with custom operator package compilation, dynamic library and static library compilation can significantly simplify the integration and deployment process. This process involves compiling and linking the operator kernel implementation, host-side tiling implementation, [graph integration adaptation files](../operator_graph_development/basic_development_process.md), and [automatically generated single-operator call implementation code](./single_operator_api_call.md) into dynamic libraries and static libraries.

The following header files are also automatically generated:

-   The aclnn header file for single-operator call, used in [single-operator call scenarios](single_operator_api_call.md);

-   The operator prototype definition header file, used in [operator graph integration scenarios](../operator_graph_development/overview.md).

> [!NOTE]
> Operator dynamic library and static library compilation supports the following models:
> - Ascend 950PR/Ascend 950DT
> - Atlas A3 training products/Atlas A3 inference products
> - Atlas A2 training products/Atlas A2 inference products
> - Atlas inference products

The specific steps for compiling dynamic and static operator libraries are as follows:

1.  Complete the project compilation configuration.

    In addition to the [basic configuration](./operator_package_compilation/operator_project_compilation.md) described above, dynamic and static operator library compilation requires setting **ASCEND\_PACK\_SHARED\_LIBRARY** to **True** in the **cacheVariables** configuration item of **CMakePresets.json** in the project directory. The default value is **False** (which generates a run package).

    ```
    "ASCEND_PACK_SHARED_LIBRARY": {
        "type": "BOOL",
        "value": "True"
     }
    ```

2.  Run the following command in the operator project directory to compile the operator project.

    ```
    ./build.sh
    ```

After successful compilation, the following files are generated in the [\$\{CMAKE\_INSTALL\_PREFIX\}](./operator_package_compilation/operator_project_compilation.md#compilation-steps)**/op\_api** directory:

    -   Operator prototype definition header file, used in the operator graph integration scenario to define the operator prototype.

    -   Single-operator call aclnn header file, used in the single-operator call scenario to provide APIs for directly calling operators.

    -   Dynamic library **libcust\_opapi.so**, used for dynamic linking.

    -   Static library **lib\$\{vendor\_name\}.a**, used for static linking.

    -   Installation files **\$\{vendor\_name\}-config.cmake** and **\$\{vendor\_name\}-targets.cmake**, which make it convenient for developers to integrate the dynamic or static operator libraries of multiple vendors into a common dynamic library, where **\$\{vendor\_name\}** is the vendor name and can also be understood as the name of the operator package generated by the same operator project. For the specific integration method, see [Operator Library Integration and Usage](#section15157027143410).

    The specific directory structure is as follows:

    ```
    ├── op_api
    │   ├── include
    │       ├── aclnn_optype1.h                  // aclnn header file for single-operator call
    │       └── aclnn_optype2.h
    │       └── aclnn_optypexxx.h
    │       └── op_proto.h                       // Operator prototype definition header file
    │   ├── lib
    │       ├── cmake
    │         └── ${vendor_name}
    │            ├──${vendor_name}-config.cmake  // Installation file that defines the configuration options and variables of the project
    │            └──${vendor_name}-targets.cmake // Installation file that defines the build targets ${vendor_name}::static and ${vendor_name}::shared for the static library and dynamic library, allowing developers to use the static and dynamic libraries and automatically handling library dependencies
    │       ├── libcust_opapi.so                 // Operator dynamic library
    │       └── lib${vendor_name}.a              // Operator static library
    ```

## Operator Library Integration and Usage<a name="section15157027143410"></a>

-   Single-operator call scenario

    In the single-operator call scenario, the dynamic library and static library generated during [operator library compilation](#section187261217143316) can be integrated and used in the following ways.

    For a complete example, see the [static library integration and usage example](https://gitcode.com/cann/asc-devkit/tree/9.1.0/examples/01_simd_cpp_api/02_features/99_acl_based/00_acl_compilation/custom_op_static_lib).

    -   Dynamic library integration

        ```
        find_package(${vendor_name} REQUIRED     # ${vendor_name} is the name of the operator package generated by compilation.
            PATHS ${CUST_PKG_PATH}               # ${CUST_PKG_PATH} is the storage path of the operator package generated by compilation.
            NO_DEFAULT_PATH
        )
        target_link_libraries(op_runner PRIVATE
            ...
            ${vendor_name}::shared               # The related target dependencies are automatically included.
            ...
        )
        ```

    -   Static library integration

        ```
        find_package(${vendor_name} REQUIRED     # ${vendor_name} is the name of the operator package generated by compilation.
            PATHS ${CUST_PKG_PATH}               # ${CUST_PKG_PATH} is the path where the compiled operator package is stored.
            NO_DEFAULT_PATH
        )
        
        target_link_libraries(op_runner PRIVATE
            ...
            ${vendor_name}::static                # The related target dependencies are automatically included.
            ...
        )
        ```

    -   Mixed use of static and dynamic libraries

        ```
        find_package(${vendor_name1} REQUIRED     # ${vendor_name1} is the name of the compiled operator package.
            PATHS ${CUST_PKG_PATH_1}              # ${CUST_PKG_PATH_1} is the path where the compiled operator package is stored.
            NO_DEFAULT_PATH
        )
        find_package(${vendor_name2} REQUIRED     # ${vendor_name2} is the name of the compiled operator package.
            PATHS ${CUST_PKG_PATH_2}              # ${CUST_PKG_PATH_2} is the path where the compiled operator package is stored.
            NO_DEFAULT_PATH
        )
        
        target_link_libraries(op_runner PRIVATE
            ...
            ${vendor_name1}::static                 # The related static library target dependencies are automatically included.
            ${vendor_name2}::shared                 # The related dynamic library target dependencies are automatically included.
            ...
        )
        ```

>[!NOTE] Note 
>- The operator package path mentioned above refers to the [\$\{CMAKE\_INSTALL\_PREFIX\}](operator_package_compilation/operator_project_compilation.md#compilation-steps)**/op\_api** directory in the operator project by default. Developers can copy the files in the **op\_api** directory to their own directory, in which case **\$\{CUST\_PKG\_PATH\}** can be set to that custom directory.
>- Because the operator dynamic libraries generated by different operator projects have the same name, if you need to integrate multiple dynamic libraries, you must modify the name of **libcust\_opapi.so**:
>    Before compilation, modify the **CMakeLists.txt** file in the **op\_host** directory and add the following code to set different output file names, so that different dynamic libraries can be distinguished.
>    ```
>    set_target_properties(cust_opapi PROPERTIES
>    	OUTPUT_NAME ${vendor_name}
>    )
>    ```
>    After compilation, modify the **\$\{vendor\_name\}-targets.cmake** file in the generated **op\_api** directory and change **libcust\_opapi.so** to **lib\$\{vendor\_name\}.so** to ensure the consistency of the dynamic library name.

-   Operator integration into a graph

    -   Configure the **ASCEND\_CUSTOM\_OPP\_PATH** environment variable and append the absolute path of the dynamic library **libcust\_opapi.so** to it. The GE framework searches for and uses the operator dynamic library based on this environment variable during graph compilation and execution. The earlier the path appears in the environment variable, the higher the priority of the operator.

        ```
        export ASCEND_CUSTOM_OPP_PATH=${CMAKE_INSTALL_PREFIX}/op_api/lib/:${ASCEND_CUSTOM_OPP_PATH}
        ```

        >[!NOTE] Note 
        >When dynamic library compilation and [operator package compilation](operator_package_compilation/operator_project_compilation.md) are used together, the dynamic library generated by the former has a higher priority.
        >In the following example, path1 and path3 are directories generated by operator package compilation, and path2 and path4 are directories where dynamic library compilation outputs are stored. The priority of the compilation outputs is 2\>4\>1\>3.
        >```
        >ASCEND_CUSTOM_OPP_PATH=<path1>/vendor_name1:<path2>/op_api/lib/:<path3>/vendor_name3:<path4>/op_api/lib/
        >```

    -   If developers use Ascend Graph for graph development, in addition to configuring the environment variable, they can also directly link the dynamic library **libcust\_opapi.so** in the application's compilation file. For details about Ascend Graph graph development, see [*Graph Development*](https://www.hiascend.com/document/redirect/CannCommunityGraphguide). The so loading priority of the dynamic library linking method is higher than that of the environment variable configuration method.
