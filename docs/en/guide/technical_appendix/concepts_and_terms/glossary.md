**Table 1** Glossary<a name="table276611752817"></a>

| Term/Abbreviation | Meaning |
|---|---|
| A1 | AscendC::TPosition::A1 represents the logical memory on the device used for cube computation, which stores the left cube. Its physical storage corresponds to the L1 Buffer of the AI Core. |
| A2 | AscendC::TPosition::A2 represents the logical memory on the device used for cube computation, which stores small blocks of the left cube (for example, blocks obtained after splitting and adapted to the L0A Buffer capacity). Its physical storage corresponds to the L0A Buffer of the AI Core. |
| AddrReg | Address Register, a register used to store address offsets. |
| AI Core | The compute core of an AI processor, responsible for executing cube- and vector-computation-intensive tasks. |
| AIC | In AI Core Separation Mode, the Cube Core in a Cube Core and Vector Core combination. |
| AIV | In AI Core Separation Mode, the Vector Core in a Cube Core and Vector Core combination. |
| Ascend IR | Ascend Intermediate Representation, an abstract data structure dedicated to AI processors for expressing computation flows. In this document, unless otherwise specified, IR refers to Ascend IR by default. |
| B1 | AscendC::TPosition::B1 represents the logical memory on the device used for cube computation, which stores the right cube. Its physical storage corresponds to the L1 Buffer of the AI Core. |
| B2 | AscendC::TPosition::B2 represents the logical memory on the device used for cube computation, which stores small blocks of the right cube (for example, blocks obtained after splitting and adapted to the L0B Buffer capacity). Its physical storage corresponds to the L0B Buffer of the AI Core. |
| Block | Block has multiple meanings in different scenarios. Generally, it refers to the logical core of the AI Core. Typical scenarios are as follows:<br>- AI Core logical core: A Block represents a logical core of the AI Core, and its BlockID is a logical number starting from 0.<br>- DataBlock: A DataBlock represents the data unit processed by one NPU vector computation instruction. Its size is usually 32 bytes, and one instruction can process multiple DataBlocks simultaneously.<br>- Base block: It represents the typical data block size required for one computation. |
| BlockID | The logical number of the AI Core starting from 0, which can be greater than the actual number of hardware cores. |
| numBlocks | The number of logical AI Cores participating in computation. It is specified by the developer when calling the kernel function, and its value is generally equal to or greater than the actual number of physical cores. |
| BiasTable Buffer | Bias storage, a physical storage unit inside the AI Core, usually used to store the bias data required for cube computation. |
| Broadcast | Broadcasting, a tensor operation mechanism. Through broadcasting, a smaller tensor can be automatically expanded to match the shape of a larger tensor. |
| C1 | AscendC::TPosition::C1 represents the logical memory on the device used for cube computation, which stores bias data. Its physical storage corresponds to the L1 Buffer or Unified Buffer (UB) of the AI Core. |
| C2 | AscendC::TPosition::C2 represents the logical memory on the device used for cube computation, which stores small blocks of bias data (for example, blocks obtained after splitting and adapted to the BT Buffer capacity). Its physical storage corresponds to the BT Buffer or L0C Buffer of the AI Core. |
| C2PIPE2GM | AscendC::TPosition::C2PIPE2GM represents the logical memory on the device used for cube computation, which stores quantization parameters. Its physical storage corresponds to the Fixpipe Buffer of the AI Core. |
| Cache Line | The smallest data unit in a cache (DCache, ICache, or L2 Cache). |
| Core | A compute core with an independent Scalar compute unit. The Scalar compute unit is responsible for functions such as instruction issue within the core, and is also called the scheduling unit within the core. |
| CO1 | AscendC::TPosition::CO1 represents the logical memory on the device used for cube computation, which stores small blocks of cube computation results (for example, blocks of the split cube computation results). Its physical storage corresponds to the L0C Buffer of the AI Core. |
| CO2 | AscendC::TPosition::CO2 represents the logical memory on the device used for cube computation, which stores cube computation results (for example, the final computation result of the original cube). Its physical storage corresponds to Global Memory or the UB of the AI Core. |
| Compute | One of the three typical stages in the Ascend C Operator Programming paradigm, responsible for completing compute tasks. |
| CopyIn | One of the three typical stages in the Ascend C Operator Programming paradigm, responsible for moving the data to be computed from Global Memory to Local Memory. |
| CopyOut | One of the three typical stages in the Ascend C Operator Programming paradigm, responsible for moving the computation results from Local Memory to Global Memory. |
| Core ID | The physical number of the AI Core, which corresponds one-to-one with the actual number of hardware cores. |
| <a name="p1038918214519"></a>Cube | The Cube compute unit on the AI Core, responsible for executing cube operations. Taking the float16 data type as an example, each Cube execution can complete the multiplication of two 16x16 float16 cubes. |
| Cube Core | A cube compute core dedicated to cube computation. It consists of the Scalar scheduling unit, Cube compute unit, DMA unit, and others, and does not include a Vector compute unit. |
| DataBlock | The data unit processed by a vector computation instruction. Its size is usually 32 bytes. One execution of a vector computation instruction can process multiple DataBlocks simultaneously. |
| DataBlock Stride | The interval between DataBlocks within a single Repeat of a vector computation instruction, that is, the number of DataBlocks between the start data address of the next processing and the start data address of the current processing. |
| DCache | Data Cache.<br>It is used to cache data segments that the Scalar compute unit may access repeatedly in the near future, to improve access efficiency. |
| Device | Device refers to the hardware device on which the Ascend AI processor is installed. It connects to the host side through a PCIe interface and provides neural network computing capabilities for the host. If multiple Devices exist, the memory resources of different Devices cannot be shared. |
| Dim3 | Dim3 is a data type used to define the three-dimensional thread structure in a single thread block. AscendC::Simt::Dim3 is used to specify the values of the three dimensions when starting a SIMT VF. The product of the three dimensions must be less than or equal to 2048. |
| DMA | Direct Memory Access, a direct memory access unit.<br>It is responsible for data transfer, including data transfer between Global Memory and Local Memory and data transfer between different levels of Local Memory. It includes transfer units such as MTE2 and MTE3. |
| DoubleBuffer/DB | Double buffering, a common optimization method in the parallel computing field. It improves the parallelism of data processing by creating multiple buffers that hold data. |
| Elementwise | An element-wise operation is an operation performed independently on each element of a tensor. The result of each element depends only on the corresponding input element. |
| Fixpipe | The unit in the AI Core responsible for moving cube computation results from the L0C Buffer to Global Memory or the L1 Buffer. During the transfer, operations such as quantization and activation are completed along the way. |
| Fixpipe Buffer | A physical storage unit inside the AI Core, usually used to store data such as the quantization parameters required during Fixpipe transfer. |
| <a name="p1439018225112"></a>Global Memory/GM | The main memory on the device side and the external storage of the AI Core. It is used to store large-scale data, but access patterns need to be optimized to improve performance. |
| GlobalTensor | A Tensor that stores global data in Global Memory. |
| Host | Refers to the X86 server or ARM server connected to the device side. It uses the NN (Neural-Network) computing capability provided by the Device to complete services. |
| ICache | Instruction Cache.<br>It is used to cache recently or frequently used instructions. During extreme performance optimization, attention should be paid to how to reduce Icache miss. |
| InferShape | Operator shape inference, which is used only in GE graph mode. During the actual network model generation process, Tensor shape and datatype inference is performed first. In this way, the data type and shape of each Tensor can be known before graph execution, and their correctness can be verified in advance. At the same time, the output tensor description of the operator, including the tensor shape, data type, and data layout format, is inferred in advance. During the operator graph construction preparation stage, memory can be statically allocated for all tensors, avoiding the overhead caused by dynamic memory allocation. |
| ISASI | Instruction Set Architecture Special Interface. This type of interface does not guarantee compatibility across hardware versions. |
| Kernel | Kernel function, a parallel function executed on the Device. The kernel function is modified by __global__. Multiple cores execute the same kernel function in parallel. The main difference is that different kernel functions have different BlockIDs at runtime. |
| Kernel Launch | The process of submitting the kernel function program to the hardware for startup and execution. |
| L0A Buffer | A physical storage unit inside the AI Core, usually used to store the left cube for cube computation. |
| L0B Buffer | A physical storage unit inside the AI Core, usually used to store the right cube for cube computation. |
| L0C Buffer | A physical storage unit inside the AI Core, usually used to store the results of cube computation. |
| L1 Buffer | A physical storage unit inside the AI Core with a relatively large space, usually used to cache the input data of cube computation. The input of cube computation generally needs to be moved from GM to the L1 Buffer, and then moved to the L0A Buffer and L0B Buffer respectively. |
| L2 Cache | Level-2 cache, dedicated to storing frequently accessed data to reduce reads and writes to Global Memory. |
| Lane | Each thread in a Warp is called a Lane. |
| LCM | Local Cache Memory. AscendC::TPosition::LCM represents the temporarily shared UB space, which implements the same function as VECCALC. |
| <a name="p193901420518"></a>Local Memory | The internal storage of the AI Core, including storage units such as the L1 Buffer, L0A Buffer, L0B Buffer, L0C Buffer, and UB. |
| LocalTensor | A Tensor that stores local data in the Local Memory of the AI Core. |
| Mask | It is used to control the elements that participate in computation within each Repeat of a vector computation instruction. It can be set in two ways: continuous mode and bit-by-bit mode. |
| MaskReg | Mask register, a 256-bit register used to indicate which elements of the RegTensor participate in computation. |
| Membase | Membase refers to a memory-based architecture. In the Membase architecture, all operations are performed based on memory. This means that each computation requires loading data from Local Memory, and after the computation is completed, the results are moved back to Local Memory. All intermediate computation results need to be temporarily stored in Local Memory. |
| <a name="p339019220518"></a>MTE1 | Memory Transfer Engine 1, the data transfer engine of the AI Core, responsible for moving data from the L1 Buffer to the L0A Buffer or L0B Buffer. Note: The capabilities may differ on different hardware. |
| <a name="p53901325511"></a>MTE2 | Memory Transfer Engine 2, the data transfer engine of the AI Core, responsible for moving data from GM to the L1 Buffer, L0A Buffer, L0B Buffer, UB, and so on. Note: The capabilities may differ on different hardware. |
| <a name="p183901322511"></a>MTE3 | Memory Transfer Engine 3, the data transfer engine of the AI Core, responsible for moving data from the UB to Global Memory and the L1 Buffer, and from the L1 Buffer to Global Memory, and so on. Note: The capabilities may differ on different hardware. |
| NC1HWC0 | A five-dimensional data format, in which C0 is strongly related to the hardware architecture. Using this format can improve the computation efficiency of cube multiplication. |
| NCHW | Stores feature map data in the order of [Batch, Channels, Height, Width]. |
| ND | A common format, an N-dimensional tensor. |
| NHWC | Stores feature map data in the order of [Batch, Height, Width, Channels]. |
| NPU | Neural-Network Processing Unit. It adopts a "data-driven parallel computing" architecture and is dedicated to processing a large number of compute tasks in AI applications. |
| OP | An operator (OP) is the basic unit that performs a specific mathematical operation in a deep learning algorithm, such as an activation function (for example, ReLU), convolution (Conv), pooling, and normalization (for example, Softmax). A neural network model can be built by combining these operators. |
| OpType | Operator type, a general term for a class of operators. For example, multiple Add operators may appear in a network, named Add1 and Add2 respectively, but the OpType of all such operators is Add. |
| Pipe | One of the core concepts of the Ascend C programming paradigm. It is used to uniformly manage resources such as Device-side memory. A kernel function must and can only initialize one Pipe object. |
| Preload | Before a compute task starts, necessary instructions or data are loaded into the cache in advance to reduce the latency of instruction or data access and improve computation efficiency. |
| Reduce | A dimension reduction operation used to reduce the dimensions of a multi-dimensional tensor. Common dimension reduction operations include summation, averaging, maximum, and minimum. |
| RegTensor | Vector data register, the basic unit of Reg vector computation. |
| Regbase | Regbase refers to a register-based architecture. Under the Regbase architecture, intermediate results can be temporarily stored in registers, eliminating the overhead of moving data out to Local Memory. |
| Repeat | When a vector computation instruction is executed once, eight DataBlocks are read for computation, which is called one iteration (Repeat). Generally, multiple iterations must be executed in a loop to complete the reading and computation of all data. |
| Repeat Stride | When a vector computation instruction is executed in a loop, the number of DataBlocks between the start data address of the next Repeat and the start data address of the current Repeat. |
| Repeat Times | The number of times a vector computation instruction is executed in a loop. |
| <a name="p1739112219516"></a>Scalar | The scalar compute unit on the AI Core, mainly responsible for scalar data operations and instruction dispatch to other units (such as the MTE data transfer unit, the Vector computation unit, and the Cube computation unit). |
| SIMD | SIMD: Single Instruction, Multiple Data. One instruction simultaneously performs the same operation on multiple data elements. |
| SIMT | SIMT: Single Instruction, Multiple Threads. One instruction is executed in parallel by multiple threads, with each thread processing different data. |
| SPMD | Single-Program Multiple-Data, a parallel programming model whose main idea is to use the same program to execute in parallel on multiple cores, with each core processing different data. |
| SSBuffer | A physical storage unit inside the AI Core. In Separation Mode, when Cube Core and Vector Core communicate at a 1:2 ratio, SSBuffer can be selected for communication between the Scalar units of the Cube Core and the Vector Core. |
| SuperKernel | SuperKernel is a binary fusion technology for operators. Unlike source code fusion, it focuses on the binary scheduling scheme of kernel functions and performs deep optimization. Based on already compiled binary code, it fuses and creates a super kernel function (SuperKernel), which calls multiple other kernel functions, that is, sub-kernel functions, in the manner of calling subfunctions. Compared with dispatching a single operator, SuperKernel technology can reduce task scheduling wait time and scheduling overhead, and further optimize operator header overhead by utilizing Task gap resources. |
| Tensor | A Tensor is a container for operator computation data. It is an N-dimensional data structure, most commonly a scalar, vector, or cube. The elements of a tensor can contain integer values, floating-point values, or string values. |
| Thread Block | A thread block supports a maximum of 2048 threads. SIMT VF runs one thread block (Block) on the AI Core at a time. |
| Tiling | Tiling refers to the splitting and blocking of data. When the amount of computation data is large, the data needs to be split across multiple cores, and each core also needs to compute in blocks multiple times. |
| TilingData | TilingData refers to the parameters related to data splitting and blocking (such as the block size of each transfer and the number of loops). Given the limited Scalar computation capability on the device side, Tiling parameters are generally computed on the host side and then transferred to the device side for use by the kernel function. |
| TilingFunc | The default function provided by the operator project for computing Tiling on the host side. |
| TilingKey | Used to distinguish special implementations of different versions of a kernel function. Different TilingKeys are compiled into different binaries. |
| TPosition | When Ascend C manages physical memory at different levels, it uses an abstract logical position (TPosition) to represent storage at each level, replacing the concept of on-chip physical storage to hide the hardware architecture. TPosition types include VECIN, VECOUT, VECCALC, A1, A2, B1, B2, CO1, CO2, and so on. Among them, VECIN, VECCALC, and VECOUT are mainly used for vector programming, while A1, A2, B1, B2, CO1, and CO2 are used for cube programming. |
| <a name="p1392229512"></a>TSCM | AscendC::TPosition::TSCM represents the logical memory corresponding to the L1 Buffer space. Developers need to manage it themselves to efficiently utilize hardware resources. It is mainly used for Matmul computation. For example, developers can cache a copy of TSCM data and flexibly configure it as the A cube, B cube, or Bias cube of a Matmul operation in different usage scenarios, achieving memory reuse and computation efficiency optimization. |
| UnalignRegForLoad | An unaligned register used as a buffer to optimize the overhead of continuous unaligned address access between UB and RegTensor. It is applicable to continuous unaligned load-in scenarios. |
| UnalignRegForStore | An unaligned register used as a buffer to optimize the overhead of continuous unaligned address access between UB and RegTensor. It is applicable to continuous unaligned store-out scenarios. |
| <a name="p17392122195118"></a>Unified Buffer/UB | A physical storage unit inside the AI Core, mainly used for vector computation. It can also be used to store input, output, and temporary data during vector computation. |
| VECCALC | Vector Compute. AscendC::TPosition::VECCALC represents the logical memory on the device used for vector computation, used to store temporary variables. Its physical storage corresponds to the UB of the AI Core. |
| VECIN | Vector Input. AscendC::TPosition::VECIN represents the logical memory on the device used for vector computation, used to store the input data of vector computation. Its physical storage corresponds to the UB of the AI Core. |
| VECOUT | Vector Output. AscendC::TPosition::VECOUT represents the logical memory on the device used for vector computation, used to store the output data of vector computation. Its physical storage corresponds to the UB of the AI Core. |
| <a name="p203923211517"></a>Vector | The Vector compute unit on the AI Core, responsible for executing vector operations. Its computing power is lower than that of the Cube, but its flexibility is higher than that of the Cube (for example, it supports mathematical operations such as reciprocal and square root). |
| Vector Core | A vector compute core dedicated to vector computation. It consists of the Scalar scheduling unit, Vector compute unit, DMA unit, and others, and does not include a Cube compute unit. |
| VF | Vector Function, a group of consecutive vector instructions called by the scalar compute unit, marked with __simt_vf__ or __simd_vf__. |
| VL | Vector Length, the bit width of RegTensor, usually 256 bytes. |
| Warp | Each thread block is divided into multiple Warps. A Warp is a set of threads that execute the same instruction. Each Warp contains 32 threads. Multiple Warps of a Block are scheduled in sequence to the same AIV core in the AI Core for execution. |
| Workspace | Generally refers to a pre-allocated, temporarily used Global Memory area for storing intermediate results or temporary data. |
| CPU domain debugging | A twin debugging method provided by Ascend C. It simulates the execution and debugging of the Device-side kernel function on the CPU, and only debugs the operator functionality and precision. |
| Base block | The typical data block size required for one computation. |
| Static Tensor programming | The static Tensor programming method. Compared with the Pipe-based programming method, this method avoids the TPipe memory management initialization process (about several hundred nanoseconds), thereby reducing runtime overhead and helping developers achieve ultimate performance. By directly constructing a LocalTensor with a specified address and storage location and passing it to computation, transfer, and other APIs for programming, it provides higher flexibility. |
| Kernel Function Direct Call | A simple and direct way to invoke a kernel function.<br>After the kernel function-side operator implementation and the Host-side Tiling implementation are completed, the operator kernel function can be directly invoked through the runtime API. In this method, Tiling development is not restricted by the CANN framework. It is simple and direct, and is mostly used for rapid verification of operator functionality. |
| NPU domain debugging | A twin debugging method provided by Ascend C, referring to debugging based on NPU simulation software or NPU hardware. |
| Tiling offloading | Tiling offloading refers to offloading the Tiling computation to the AI CPU on the device side for execution, so that the entire computation is efficiently completed on the device side. |
| Separation Mode | A working mode of the AI Core in which the cube computation unit and the vector computation unit are scheduled by independent Scalar scheduling units and deployed separately on the Cube Core and the Vector Core. The Cube Core and Vector Core are combined at a certain ratio (1:N), and such a combination is regarded as one AI Core. The number of AI Cores is determined by the number of Cube Cores. |
| Twin debugging | An operator debugging method provided by Ascend C, supporting precision debugging in the CPU domain and precision/performance debugging in the NPU domain. |
| Pipeline Task | The Ascend C programming paradigm is a pipelined programming paradigm that divides the processing program within an operator kernel into multiple pipeline tasks. A pipeline task refers to a parallel task scheduled by the main program in a single-core processing program. Within a kernel function, pipeline tasks can be used to implement parallel data processing and further improve performance. |
| Continuous mode | One of the selectable modes when using Mask to control the elements participating in computation in each Repeat of vector computation. It indicates that the first consecutive elements participate in computation. |
| Coupled mode | A working mode of the AI Core in which the same Scalar scheduling unit simultaneously schedules the cube computation unit and the vector computation unit, and all units are deployed on one AI Core. |
| Fusion operator | A fusion operator is formed by fusing multiple independent small operators. Its functionality is equivalent to that of the multiple small operators, and its performance is usually better than that of the independent small operators. Users can freely fuse Vector and Cube operators according to specific algorithms based on actual business scenario requirements to achieve performance gains. |
| Operator graph integration | Operator graph integration refers to running operators through the GE graph mode. In graph mode, all operators are first constructed into a graph, and then the graph is dispatched to the AI processor for execution through GE. |
| Operator prototype | An operator prototype is an abstract description of an operator, defining information such as the operator's inputs, outputs, and attributes. |
| Communication-computation fusion operator | A communication-computation fusion operator is an operator that fuses a collective communication task and a compute task. During operator execution, the computation and communication tasks can achieve partial pipeline parallelism, thereby improving performance. |
| Reg vector computation | The Reg vector computation API is an API developed for the RegBase architecture. Through this type of API, users can directly operate the registers involved in Vector computation on the chip, achieving greater flexibility and better performance. |
| Bitwise mode | One of the selectable modes when using Mask to control the elements participating in computation in each Repeat of vector computation. It can control which elements participate in computation on a bit-by-bit basis. A bit value of 1 indicates participation in computation, and 0 indicates non-participation. |
| Custom operator project | An operator project generated by Ascend C based on the msOpGen tool. |
