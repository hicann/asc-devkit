# 多算子包组织

本文是扩展内容，介绍开发多个自定义算子时，如何决定这些算子的发布与部署方式——是全部放在一个算子包中，还是拆成多个算子包。

本文中的“算子包”指编译后生成的自定义算子安装包`custom_opp_*.run`。一个算子包可以包含一个或多个OpType，部署后通常位于`vendors/<vendor_name>`目录下。OpType是算子原型注册时的算子类型，例如`OP_ADD(AddCustom)`中的`AddCustom`。

本文主要讨论“多个算子如何拆分到一个或多个算子包”。如果需要了解多个算子如何编成一个算子包，需要如何组织多个算子的Host、Kernel、Tiling文件，请参考[编译与部署基本流程](./basic_process.md#编译组织)中的“按算子划分的目录结构”。

## 默认建议

默认建议放在同一个算子包中。只有在算子更新频率不同、需要独立编译部署，或由不同业务团队维护等情况时，才考虑拆成多个算子包。

| 场景 | 推荐策略 | 说明 |
|------|---------|------|
| 少量算子，由同一团队统一维护 | 单个算子包 | 编译、部署和验证流程最简单。 |
| 多个算子属于同一业务，一起发布和回归 | 单个算子包 | 减少算子包数量，避免额外优先级配置。 |
| 基础算子和实验算子更新频率不同 | 多个算子包 | 稳定包和实验包可以独立编译、部署和回退。 |
| 不同业务团队分别维护 | 多个算子包 | 每个团队维护独立包，通过优先级和部署路径集成。 |

## 单个算子包和多个算子包的区别

| 对比项 | 单个算子包 | 多个算子包 |
|--------|------------|------------|
| 产物数量 | 一个`custom_opp_*.run` | 多个`custom_opp_*.run` |
| `vendor_name` | 通常只有一个。 | 每个包可使用不同`vendor_name`。 |
| 编译部署 | 一次编译、一次部署。 | 每个包独立编译和部署。 |
| 优先级配置 | 通常不需要。 | 同OpType冲突时需要配置。 |
| 适合场景 | 同一批算子共同发布。 | 算子生命周期、优先级或维护边界不同。 |

单个算子包并不表示只能包含一个算子。它表示这些算子被打进同一个安装包、部署到同一个vendor目录，并作为一个整体发布。


## 适合拆成多个算子包的情况

### 更新频率不同

基础算子稳定后很少更新，而实验性算子或业务定制算子可能频繁迭代。将它们拆成不同算子包，可以降低每次修改的影响范围。

示例：

- 基础算子包：稳定的通用算子，更新频率低；
- 实验算子包：仍在调优或验证的算子，更新频率高；
- 业务定制算子包：只服务某个业务场景，独立发布和回退。

### 维护边界不同

不同业务团队维护的算子，通常不建议混在同一个算子包中。拆成多个算子包后，每个团队可以独立管理自己的源码、版本、部署节奏和问题回退。

## 优先级配置

多个自定义算子包共存时，只有包含相同OpType的算子才涉及优先级选择。不同OpType的算子不会因为`load_priority`互相覆盖。

不建议将同一OpType的多个版本作为常规部署方式长期共存。若确实需要临时共存并通过优先级选择版本，需要保证每个版本的Host侧库、Kernel二进制、算子信息等产物完整一致，并完成目标场景回归验证。否则在某个高优先级版本的`.o`等产物不完备时，运行时可能混用低优先级版本的产物，导致版本误用或行为异常。

默认安装场景下，通过`opp/vendors/config.ini`中的`load_priority`配置各vendor的优先级。指定目录安装场景下，通过执行各算子包安装目录下的`set_env.bash`脚本顺序控制优先级。

详细配置方法请参考[配置自定义算子优先级](./basic_process.md#配置自定义算子优先级)。
