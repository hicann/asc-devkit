# Matmul C-API High-Performance Sample

## Overview

This sample implements half matrix multiplication with the Ascend C C-API and compares a single-buffer baseline with L1 double buffering. L1 Ping/Pong buffers allow MTE2 transfers to overlap with downstream processing across different K iterations.

## Sample Description

The sample computes `C = A x B`. A and B are generated with a fixed random seed. B is transposed before it is written so that the K dimension is contiguous in GM and can be transferred in K tiles. Table2 lists the data specifications.

**Table2**  Input and Output Data Specifications

| Data | Input/Output | Data file | Data type | Logical shape | File and GM layout | Description |
| --- | --- | --- | --- | --- | --- | --- |
| A | Input | `input/x1_gm.bin` | half | `[M, K] = [1024, 1024]` | ND, stored as `[M, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| B | Input | `input/x2_gm.bin` | half | `[K, N] = [1024, 1024]` | Transposed ND, stored as `[N, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| C | Output | `output/output.bin` | float | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Result computed by the Kernel. |
| golden | Golden data | `output/golden.bin` | float | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Generated by running `np.matmul` on inputs cast to float. |

The sample computes `C = A x B`, where `M`, `N`, and `K` are all 1024. The matrices use `[128, 128, 64]` tiles and 64 logical Cube blocks, with each block computing one `[128, 128]` output tile. `block_idx` assigns the output tile, and each block accumulates it over 16 MMAD iterations along K.

Data moves from GM through L1 Buffer, L0A Buffer/L0B Buffer, and L0C Buffer before being written back to GM. Table3 lists the data layout at each stage.

**Table3**  Data Movement Path and Layout

| Storage unit | Data | Data layout |
| --- | --- | --- |
| GM | A and transposed B | ND |
| L1 Buffer | A and B data tiles | Nz |
| L0A Buffer | A data tile | Nz |
| L0B Buffer | B data tile | Zn |
| L0C Buffer | C output tile | Nz, float |
| GM | C | ND, float |

The `SCENARIO_NUM` build option selects the single-buffer baseline or the L1 double-buffer optimization. Both scenarios use the same matrix dimensions, tiles, K iterations, Block count, and MMAD parameters; only the number of L1 buffers differs.

**Table4**  Scenario Configuration

| `SCENARIO_NUM` | Kernel | Scenario | L1 Buffer | L0A Buffer/L0B Buffer | L0C Buffer | Pipeline behavior |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | `mmad_baseline` | Single-buffer baseline | One A/B group | One A/B group | One group for result accumulation | Uses one Mutex to serialize transfer, loading, and MMAD for each K tile before processing the next tile. |
| 1 | `mmad_l1_double_buffer` | L1-only double buffering | Ping/Pong A/B groups | One A/B group | One group for result accumulation | MTE2 can prepare a later K tile; MTE1 still waits to reuse the single L0 group. |

### Scenario 0: Single-Buffer Baseline

`mmad_baseline` allocates one A/B buffer group in L1 Buffer, L0A Buffer, and L0B Buffer. All 16 K iterations reuse the same addresses. Table5 lists the buffer sizes and purposes.

**Table5**  Single-Buffer Configuration

| Buffer | Array | Elements | Bytes | Purpose |
| --- | --- | --- | --- | --- |
| L1 Buffer A | `a_l1` | 8192 half elements | 16384 | Stores the current A tile loaded from GM and converted to Nz. |
| L1 Buffer B | `b_l1` | 8192 half elements | 16384 | Stores the current B tile loaded from GM and converted to Nz. |
| L0A Buffer | `a_l0` | 8192 half elements | 16384 | Stores the current A tile used by MMAD. |
| L0B Buffer | `b_l0` | 8192 half elements | 16384 | Stores the current B tile used by MMAD. |
| L0C Buffer | `c_l0` | 16384 float elements | 65536 | Accumulates the C output tile over 16 MMAD iterations. |

Each K iteration runs in the following order:

1. MTE2 calls `copy_a_to_l1` and `copy_b_to_l1` to move the current A/B tiles from GM to L1 Buffer and convert them from ND to Nz.
2. After MTE2 releases the Mutex, MTE1 acquires it and loads A/B into L0A Buffer and L0B Buffer.
3. After MTE1 releases the Mutex, M calls `asc_mmad` to compute `[128, 64] x [64, 128]`. Iteration 0 initializes L0C Buffer, and subsequent iterations accumulate into it.
4. After M releases the Mutex, the next MTE2 iteration acquires the same Mutex and waits for the current MMAD to complete before reusing the L1 and L0 buffers.
5. After the K loop, FIX acquires the same Mutex and waits for the final MMAD before storing L0C to GM. `asc_sync_pipe(PIPE_FIX)` then waits for the store to complete.

The single buffers and shared Mutex force MTE2, MTE1, and M to process one K tile in sequence without overlap across K iterations. This implementation serves as the performance baseline.

### Scenario 1: L1-Only Double Buffering

`mmad_l1_double_buffer` allocates Ping/Pong A/B groups only in L1. L0A and L0B still use one group. Even iterations use L1 Ping and Mutex 0, odd iterations use L1 Pong and Mutex 1, and the single L0 group uses Mutex 2.

Once MTE1 has read an L1 group, MTE2 can write a later K tile to that group without waiting for MMAD. Because L0 has only one group, MTE1 must still wait for MMAD to finish reading it before loading the next tile.

All scenarios use [asc_lock](../../../../../docs/zh/api/SIMD-API/c_api/sync/asc_lock.md) and [asc_unlock](../../../../../docs/zh/api/SIMD-API/c_api/sync/asc_unlock.md) to control buffer-reuse dependencies. These Mutexes ensure that data is written before it is read and read before it is overwritten; they are not a separate performance optimization.

**Table6**  Buffer-Reuse Dependencies

| Dependency direction | Mutex IDs | Purpose |
| --- | --- | --- |
| `MTE2 -> MTE1` and `MTE1 -> MTE2` | L1: `0` for one group and `0/1` for Ping/Pong | Controls L1 writes, MTE1 reads, and L1 reuse. |
| `MTE1 -> M` and `M -> MTE1` | L0: `0` in Scenario 0 and `2` in Scenario 1 | Controls L0 loads, MMAD reads, and reuse of the single L0 group. |
| `M -> FIX` | L0 Mutex used by the final iteration | Ensures that FIX reads L0C and stores it to GM only after the final MMAD completes. |

For example, Scenario 1 uses L1 Ping in iteration 0, L1 Pong in iteration 1, and L1 Ping again in iteration 2. While M computes iteration 0, MTE2 can transfer iteration 1 into L1 Pong. After MTE1 releases L1 Ping, MTE2 can also transfer iteration 2 into it. After the K loop, FIX waits on the L0 Mutex for the final MMAD before storing the result to GM.

The two scenarios compare the single-buffer baseline with L1 Ping/Pong double buffering to measure its pipeline-overlap benefit.

## Performance Comparison

Keep the matrix, MMAD parameters, and input data unchanged during performance testing. Mutexes express the required buffer read, write, and reuse dependencies.

### Test Conditions

| --- | --- |

| NPU architecture | `dav-3510` |
| Input data type | A and B are half |

### Performance Metrics

Use msOpProf to collect performance data. The metrics in Table8 come from the generated `op_summary_*.csv` file.

**Table8**  Performance Metric Descriptions

| Metric | Description |
| --- | --- |
| `Task Duration(μs)` | Total Task execution time. Use this metric for the end-to-end comparison. |
| `Block Num` | Number of Blocks launched by the Kernel. This sample should report 64. |
| `aicore_time(μs)` | Average Task execution time on AI Core. |
| `aic_mac_time(μs)` / `aic_mac_ratio` | Duration and ratio of MMAD execution on the Cube compute unit. |
| `aic_scalar_time(μs)` / `aic_scalar_ratio` | Scalar instruction duration and ratio. |
| `aic_mte1_time(μs)` / `aic_mte1_ratio` | Duration and ratio of L1 Buffer-to-L0A Buffer/L0B Buffer loads on the MTE1 pipeline. |
| `aic_mte2_time(μs)` / `aic_mte2_ratio` | Duration and ratio of GM-to-L1 Buffer transfers on the MTE2 pipeline. |
| `aic_fixpipe_time(μs)` / `aic_fixpipe_ratio` | Duration and ratio of L0C Buffer-to-GM stores on the FIX pipeline. |

When double buffering is enabled, some or all pipelines overlap across K iterations, so their durations or ratios cannot be added directly. Use `Task Duration` for the end-to-end comparison and the other metrics to identify where time is spent.

### Ascend 950PR Performance Comparison

Table9 lists measurements of Scenarios 0 and 1 for the current code with `TILE_M=TILE_N=128` and `TILE_K=64`. Use pipeline durations to analyze bottlenecks and `Task Duration` for the end-to-end comparison.

**Table9**  L1 Double-Buffer Performance Data

| Scenario | Configuration | Task Duration(μs) | Block Num | aicore_time(μs) | aic_mac_time(μs) | aic_mac_ratio | aic_scalar_time(μs) | aic_scalar_ratio | aic_mte1_time(μs) | aic_mte1_ratio | aic_mte2_time(μs) | aic_mte2_ratio | aic_fixpipe_time(μs) | aic_fixpipe_ratio |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Scenario 0 | Single-buffer baseline | 36.589 | 64 | 35.480 | 7.068 | 0.199 | 1.420 | 0.040 | 3.174 | 0.089 | 20.205 | 0.569 | 1.277 | 0.036 |
| Scenario 1 | L1 double buffering | 21.220 | 64 | 20.160 | 7.069 | 0.351 | 1.458 | 0.072 | 4.148 | 0.206 | 14.384 | 0.713 | 1.266 | 0.063 |

#### Performance Data Analysis

Using Scenario 0 as the baseline, the end-to-end duration reduction of Scenario 1 with L1 double buffering is

$$
R = \frac{T_{\text{baseline}} - T_{\text{double-buffer}}}{T_{\text{baseline}}} \times 100\%
  = \frac{36.589 - 21.220}{36.589} \times 100\%
  \approx 42.00\%
$$

`Task Duration` decreases from 36.589μs to 21.220μs, a reduction of 15.369μs or 42.00%. `aicore_time` follows the same trend, decreasing from 35.480μs to 20.160μs.

The `aic_mac_time` values of Scenarios 0 and 1 differ by only 0.001μs, so the Cube workload is essentially unchanged. The gain comes from overlapping MTE2 transfers with MTE1 loads and Cube computation across K iterations. `aic_mte2_time` decreases from 20.205μs to 14.384μs, the largest change among the pipeline metrics.

In Scenario 1, `aic_mte2_ratio` rises from 56.9% to 71.3% and remains the largest ratio. The higher ratio results from the shorter total `aicore_time`; it does not mean MTE2 became slower. Profiler pipeline durations cannot be added directly.

#### Conclusion

- **Optimization method**: With Ping/Pong Buffers in L1, MTE2 can prepare a later K tile while MTE1 and Cube process the current tile. Double buffering changes waiting relationships between stages; it does not reduce the Cube workload.
- **Measured gain**: In Table9, `Task Duration` decreases by 15.369μs, a reduction of 42.00%. The nearly unchanged `aic_mac_time` shows that the gain mainly comes from pipeline overlap.
- **Next steps**: MTE2 remains the largest-ratio stage in Scenario 1. Further work should use measured Memory and L2 Cache metrics to examine input-transfer volume, L2 reuse, and tile size. This data set contains only one measurement per scenario, so final performance conclusions should use the median of multiple runs.

## Build and Run

Configure the CANN environment:

```bash
source ${install_path}/cann/set_env.sh
```

Build and run one scenario from this sample directory:

```bash
SCENARIO_NUM=0
mkdir -p build && cd build
cmake -DCMAKE_ASC_ARCHITECTURES=dav-3510 -DSCENARIO_NUM=${SCENARIO_NUM} ..
make -j
python3 ../scripts/gen_data.py
./c_api_mmad_double_buffer_example
python3 ../scripts/verify_result.py output/output.bin output/golden.bin
```

Set `SCENARIO_NUM` to `0` or `1`, then rerun CMake, build, execution, and verification to test the corresponding scenario. Clear the CMake cache before switching scenarios.

**Table10**  Build Options

| Build option | Values | Description |
| --- | --- | --- |
| `CMAKE_ASC_ARCHITECTURES` | `dav-3510` | NPU architecture |
| `CMAKE_ASC_RUN_MODE` | `npu` (default), `cpu`, `sim` | Run mode |
| `SCENARIO_NUM` | `0`, `1` (default) | `0` selects the single-buffer baseline; `1` selects L1 double buffering. |

A successful verification prints:

```text
test pass!
```

## Functional Debugging

### printf

This interface provides formatted output for CPU-side and NPU-side debugging. In NPU execution and NPU simulation modes, this sample can call the [printf](../../../../../docs/zh/api/Utils-API/tuning_interface/printf.md) interface directly wherever logging is needed in the Kernel. Include `utils/debug/asc_printf.h` before using the interface.

For example:

```cpp
printf("mmad blockIdx=%ld\n", static_cast<int64_t>(block_idx));
```

> **Note:** The `printf` interface increases Kernel execution time and affects performance measurements. Use it only during functional debugging. Remove or disable printing before performance collection, or set `ASCENDC_DUMP=0` to disable printing as needed.

### msOpProf Tool Introduction

msOpProf is a single-operator performance analysis tool. It provides `msopprof` and `msopprof simulator` modes to help locate issues in operator memory access, code, and instructions. It supports performance-data collection and automatic parsing in NPU and simulation modes, using either executable files or operator binary `.o` files.

#### NPU Performance Collection

NPU collection measures operator execution time on the Ascend AI Processor and is useful for quickly locating operator performance issues on a device.

From the build directory, run msOpProf with the `c_api_mmad_double_buffer_example` executable:

```bash
msopprof ./c_api_mmad_double_buffer_example
```

**Performance Data**

The command creates an `OPPROF_{timestamp}_XXX` directory. Its performance files include:

```text
├── dump                       # Raw performance data; normally not needed for analysis
├── ArithmeticUtilization.csv  # Cycle ratios of Cube and Vector instructions
├── L2Cache.csv                # L2 Cache hit rate
├── Memory.csv                 # Read/write bandwidth of UB, L1, and main memory
├── MemoryL0.csv               # Read/write bandwidth of L0A, L0B, and L0C
├── MemoryUB.csv               # Read/write bandwidth between Vector/Scalar and UB
├── OpBasicInfo.csv            # Basic operator information
├── PipeUtilization.csv        # Duration and ratio of compute and data-transfer pipelines
├── ResourceConflictRatio.csv  # UB bank-group, bank-conflict, and resource-conflict ratios
└── visualize_data.bin         # Data for MindStudio Insight visualization
```

View the detailed performance results:

```bash
# View Task Duration and pipeline metrics
cat ./OPPROF_*/PipeUtilization.csv
```
