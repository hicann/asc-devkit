# Kernel 调试接口诊断流程

## 1. 先收集上下文

至少确认：

- SoC/产品、`__NPU_ARCH__` 或编译架构。
- SIMD、SIMT、SIMT VF 还是 SIMD VF。
- CPU 调试、仿真还是 NPU 上板。
- 直接调用还是算子入图。
- CANN/AscendC 版本、编译命令和相关 `acl.json` 配置。
- 期望观察的是文本、张量内容、异常还是周期数据。

## 2. 按症状排查

### 没有任何输出

1. 先确认目标平台/模式支持接口。
2. 检查头文件、命名空间和地址空间重载。
3. 检查 `ASCENDC_DUMP=0` 是否关闭了 `printf`、断言或 dump。
4. 检查 `asc_time_stamp` 是否重新编译并开启 `ASCENDC_TIME_STAMP_ON`。
5. 检查语句是否在执行路径中，是否被线程条件过滤。
6. 用无参数短 `printf` 或 1 个已知值的 dump 做最小验证。

### 输出不全或顺序异常

1. 区分 SIMD FIFO、SIMT FIFO、SIMD VF reserved UBUF 和每核 dump 上限。
2. 减少 Block/线程输出，缩短单条消息，减少 dump 元素数。
3. `asc_dump` 计算 32B 补齐后的容量；不要只计算有效元素字节数。
4. 使用 `desc`、Block/线程 ID 和阶段标签建立来源关系。
5. 多核输出不要假设全局顺序；必要时写回带索引的 GM 缓冲区。

### 断言未触发或算子仍继续

区分条件为真、代码路径未执行、`NDEBUG`、`ASCENDC_DUMP=0` 和场景不支持。用一个确定失败的最小输入验证断言宏是否生效，再恢复原条件。

### 断言或 Trap 导致算子失败

保留失败日志和返回码。断言通常带源码位置和条件；`__trap` 只负责中断，需在触发前用少量输出或可观测数据记录上下文。若失败伴随错误码、plog、卡死或崩溃，继续路由 `ascendc-runtime-debug` 或 `ascendc-crash-debug`。

### `asc_dump` 数据异常

检查实际地址空间、模板数据类型、元素数量和起始地址。不要用 `dump_size` 试探未知长度；先构造已知值的小数组。L1/L0C/BiasTable/Fixpipe 的支持与结果格式具有平台差异，优先查看当前 API 文档和示例。

### 周期结果异常

把打印移出测量区，确认 `start` 和 `end` 位于同一线程和同一逻辑阶段。检查同步、冷启动、编译优化和测量次数；`clock` 不是 profiling 采集器。

## 3. 最小验证和清理

验证顺序建议为：接口能编译 -> 语句确实执行 -> 输出/异常符合预期 -> 扩大到真实数据和多核 -> 关闭或删除调试代码。不要为了让输出出现而修改算子算法或放宽真实边界检查。
