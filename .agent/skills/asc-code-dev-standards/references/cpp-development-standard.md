# C/C++ 开发细则

本细则补充[核心开发规范](development-standard.md)，覆盖 C/C++ 编码、安全、设计和度量检查。
适用范围以实际语言、编译选项、ABI、Host/device 和库能力为准；标有 `-CPP` 的要求不能机械用于 C。
规则编号用于检索约束，不代表仅凭规则名即可确认缺陷；同类检查合并落实，不重复修改代码。

## 阅读导航

- 类与异常：第一、二节。
- 类型、数值、表达式和控制流：第三、四节。
- 内存、容器和接口：第五、六节。
- 并发、文件、进程与安全：第七、八节。
- 头文件、宏、命名和注释：第九至十一节。
- Ascend 性能接口、规模和设计：第十二至十四节。

## 适用与冲突处理

- 核心 ASC-01～ASC-28 继续有效；函数长度采用 ASC-26 的 **50 行**评估口径，控制流嵌套采用
  ASC-27 的 **3 层**建议。不得用度量配置中的 30 行或 4 层替换项目约定。
- 本细则的所有章节，包括边界/EChecker、度量和设计章节，都是正式规则；章节分组只服务于按场景加载，
  不表示“后续补充”可选，也不表示某一批次的规则优先级更低。
- `development-standard.md` 是语言无关的核心规范，本文件是 C/C++ 详细规范；两者互相补充，不复制同一条规则来制造多个版本。
  具体的 C/C++ 规则优先于通用表述，项目、ABI、编译器、SoC 和 device API 的真实约束优先于通用建议。
- 参数数量建议不超过 **5 个**，包含构造函数；超出时评估职责和参数对象，不能把无关参数机械打包。
  稳定 ABI、回调、协议和 device API 的例外按核心规范记录。
- 分析器的编译错误过滤、忽略宏、自动修复开关等是工具配置，不是代码安全豁免。
  编译数据库不完整、分析失败或被过滤时，不能据此判定规则通过。
- 规则只提供名称、未给算法清单或度量定义时，保留检查方向，不虚构禁用 API、阈值、单位或通过结论。
- 不增加告警来源清单或规则映射表；不以 `test/`、`tests/` 中的代码、规则或 UT 行为作为产品实现依据。

## C/C++ 边界、污点与解引用检查

下面的 EChecker 项把外部输入、指针运算和循环边界的检查落到实际代码路径。它们与本文件其他章节同等适用，
不能仅凭分析器是否报出告警判断通过；先沿当前代码路径确认对象容量、单位和生命周期。

- **EChecker_BufferSize**：任何访问长度不超过目标缓冲区真实容量，明确字节/元素单位；长度来自外部输入时先校验，再进行复制、读取或写入。
- **EChecker_OutOfBound**：指针强制转换、指针偏移前证明对象边界、对齐和剩余长度；不把强转成功当成目标对象足够大。
- **EChecker_Overrun**：数组下标同时检查下界和上界；有符号下标先拒绝负值，再与有效元素数量比较。
- **EChecker_TaintedArgument**：污点传播到有符号整数时检查上下界，传播到无符号整数时至少检查上界；当前检查器不覆盖指针污点，仍必须按真实对象边界人工校验。
- **EChecker_TaintedLoopBound**：外部或污点数据参与循环边界时校验上下界、步进和溢出，保证循环能按设计终止，见 `G.CTL.03`。
- **EChecker_TaintedPtrDereference**：数组下标、指针偏移和解引用前证明指针非空且仍绑定有效对象，检查上下界和生命周期。

分析器给出的 trace 只用于定位当前路径；结合业务前提、调用方契约和实际分支判断根因。对同一问题，
优先在信任边界或对象所有权处补充一次可证明的校验，避免在每个使用点堆叠无效判空或仅修改告警文本。

## 一、类、对象与继承

- **G.CLS.01-CPP**：类的成员变量必须显式初始化；覆盖每条构造路径，不能依赖未定义初值。
- **G.CLS.02-CPP**：优先在成员声明处或构造函数初始化列表初始化；遵循成员声明顺序，避免先默认构造再赋值。
- **G.CLS.03-CPP**：单参数构造函数声明为 `explicit`，避免非预期隐式转换。
- **G.CLS.04-CPP**：需要声明拷贝构造或拷贝赋值时，两者成对审视并声明、`= default` 或 `= delete`；
  无需手写特殊成员的普通类不为形式增加冗余实现。
- **G.CLS.05-CPP**：需要声明移动构造或移动赋值时，两者成对处理，并核对拷贝、析构及所有权语义。
- **G.CLS.06-CPP**：构造函数和析构函数中不调用虚函数，也不通过辅助函数间接依赖派生类虚分派。
- **G.CLS.07-CPP**：多态基类的拷贝/移动构造和赋值为非 `public` 或 `= delete`，防止对象切片。
- **G.CLS.09-CPP**：移动后正确重置源对象的资源所有权；源对象保持有效、可析构且符合接口约定，避免双重释放。
- **G.CLS.10-CPP**：通过基类指针释放派生类时，基类析构函数必须为虚函数；同时核对实际删除路径。
- **G.CLS.11-CPP**：派生类重写虚函数不重新定义默认参数值，避免静态类型与动态分派产生不同语义。
- **G.CLS.12-CPP**：重写虚函数明确写 `override`；确需禁止继续重写时使用 `final`。
- **G.CLS.13-CPP**：不重新定义 `public` 继承得到的非虚函数；用明确接口或组合表达不同功能。
- **G.CLS.14-CPP**：不把派生类对象数组的指针当作基类数组指针使用，避免按错误步长访问。
- **G.CLS.15-CPP**：不重载逗号、`&&`、`||` 操作符，不破坏调用者对求值和短路语义的预期。

## 二、断言、异常和错误处理

- **G.AST.03**：断言用于开发期不变量；外部输入错误、资源不足等运行期可能发生的错误必须用实际错误处理代码处理。
- **G.ERR.01-CPP**：仅使用 `std::exception` 的派生类作为异常对象，优先复用项目异常体系。
- **G.ERR.02-CPP**：抛出异常对象本身，不抛出指向异常对象的指针。
- **G.ERR.03-CPP**：以左值引用捕获异常，通常用 `const` 引用，避免切片和无谓复制。
- **G.ERR.04-CPP**：`catch` 从具体派生异常到一般基类排列，兜底在最后，前项不能遮蔽后项。
- **G.ERR.05-CPP**：析构函数不抛出异常；必要清理失败按项目机制报告，不能破坏栈展开。
- **G.ERR.06-CPP**：不添加旧式 `throw(...)` 异常说明；需要表达不抛异常时，在目标语言支持且确实成立时使用 `noexcept`。
- **G.ERR.07-CPP**：构造函数 function-try-block 的处理器不访问基类或成员；它们可能未构造或已经销毁。

无异常编译或设备侧按实际支持的错误码/状态机制实现，不为套用 Host 规则擅自开启异常。

## 三、类型、初始化与数值

- **G.ARR.02、G.ARR.03**：不对数组形参或指针使用 `sizeof` 获取数组大小；传递真实元素数/字节容量，见 ASC-08。
- **G.ENU.01-CPP**：C++ 优先使用 `enum class`；公开 C ABI 和既定协议保持兼容。
- **G.ENU.02-CPP**：避免未命名枚举，局部作用域同样适用；使用有语义的具名类型或常量。
- **G.INT.09**：枚举常量映射到唯一值；协议既定别名等必要例外必须明确记录，不能无意重复。
- **G.CNS.01-CPP**：数值字面量不使用容易与数字 `1` 混淆的小写后缀 `l`，需要时使用 `L`。
- **G.CNS.02-CPP**：按 ASC-01 处理数值字面量，包括模板参数和下标；除独立且语义明确的 `0`、`1`
  外须具名，成组或上下文关联的 `0`、`1` 也须具名。优先编译期常量并收窄作用域，见 ASC-01。
- **G.CNS.03-CPP、G.CNS.04-CPP**：不改变逻辑状态的成员函数、只读对象的指针/引用参数使用适当 `const`，见 ASC-07。
- **G.EXP.01-CPP**：不声明或定义语言/实现保留标识符；头文件保护符也采用合法、不冲突的项目名称。
- **G.EXP.02-CPP、G.EXP.03-CPP**：不重复定义基本类型；有业务含义的 C++ 类型别名用 `using`，见 ASC-05。
- **G.EXP.04-CPP**：遵守单一定义原则，核对跨翻译单元、头文件定义、模板和链接属性。
- **G.EXP.05-CPP**：不在使用处临时声明外部函数或变量以替代正式头文件，避免声明与真实接口不一致。
- **G.EXP.07-CPP**：不依赖不同翻译单元中全局对象的初始化顺序，采用明确初始化流程或符合生命周期要求的方案。
- **G.EXP.08-CPP、G.EXP.09-CPP**：对象在使用前初始化；变量靠近首次使用处声明并初始化，覆盖错误和分支路径。
- **G.EXP.10-CPP**：嵌套作用域不重用外层名称，避免遮蔽变量、参数和成员。
- **G.EXP.12-CPP**：不对非 trivially copyable 对象进行逐位复制、清零或比较；调用其构造、赋值及语义操作。
- **G.EXP.13-CPP**：用 `char`、`wchar_t` 等表达字符，数值字段选合适整数类型，见 ASC-05。
- **G.EXP.14-CPP、G.EXP.15-CPP、G.EXP.16-CPP**：C++ 使用命名转换，避免 `reinterpret_cast`、`const_cast`；
  确需底层转换时证明对象生命周期、对齐、别名和地址空间前提，见 ASC-06。继承体系的下行转换按对象关系选用
  `dynamic_cast` 等适当转换；指针确需保存为整数时使用目标平台支持的 `uintptr_t`，并核对可逆性和位宽。
- **G.EXP.17-CPP**：避免隐式有损算术转换；缩窄前检查范围和精度，显式 `static_cast` 只表达已验证的转换，不能代替范围校验。
- **G.EXP.18-CPP**：避免整数与指针互转；设备地址或 ABI 边界确需转换时使用支持的 `uintptr_t`/地址类型，证明位宽、对齐、地址空间和生命周期，
  不直接在 `int`、`long` 或其无符号类型之间保存指针。
- **G.EXP.19-CPP**：不对 `const` 对象使用 `std::move` 伪装资源转移；确认操作实际为移动还是复制。
- **G.EXP.20-CPP、G.EXP.21-CPP**：有符号运算不溢出，无符号运算不意外回绕，检查发生在运算前，见 ASC-03。
  加、减、乘、递增、递减和转换都要按实际类型检查范围；有符号值检查上下限，无符号值至少检查上限，不能先回绕或截断后再判断。
- **G.EXP.22-CPP**：除法和取余前检查非零除数；同时处理有符号最小值除以 `-1` 的不可表示结果。
- **G.EXP.23-CPP**：位运算使用适当的无符号整数类型，留意整型提升后的实际类型；即使有符号值当前为正，
  也不能以有符号类型参与按位操作。转换为无符号类型前先确认业务语义和范围。
- **G.EXP.24-CPP**：移位量非负且小于被移位类型的位宽，结果及提升也须合法。
- **G.EXP.25-CPP**：避免混合有符号和无符号运算/比较；转换前验证负值和范围。
- **G.EXP.26-CPP**：需要更大类型的计算时在运算前提升操作数，不先用窄类型计算再赋给宽类型。
- **G.EXP.27-CPP**：运算符的基本类型符合操作语义，布尔、枚举、指针、字符不当作可随意互换的数值。
- **整数除法精度**：需要小数结果时在除法前选用合适类型或定点算法；不能将已截断的商转浮点补救。
  偏移、容量等需要整数语义的计算不盲目改浮点。

## 四、表达式、控制流与函数

- **G.EXP.30-CPP**：用括号明确运算顺序，不过分依赖默认优先级。
- **G.EXP.31-CPP**：不依赖未求值或因短路未执行的操作数中的副作用；`sizeof`、`typeid` 等未求值操作数中不放必须执行的状态修改，
  必要状态更新单独表达。
- **G.EXP.32-CPP**：`&&`、`||` 右侧不包含副作用；副作用包括修改对象、访问 `volatile` 对象和修改文件等。
  保留必要调用的顺序和错误处理，不能简单删掉调用。
- **G.EXP.33-CPP**：含自增/自减的表达式中不再次引用该变量，拆成顺序明确的语句。
- **G.EXP.35-CPP**：C++ 用 `nullptr` 表示空指针；C/共享 ABI 采用语言兼容写法。
- **G.EXP.36-CPP**：控制表达式表达布尔语义；状态、计数、位标志显式比较，指针判空沿用 ASC-02 的约定。
  返回整数或枚举的接口使用比较运算；仅对明确返回 `bool` 的接口保留直接条件。编译器内建函数等特殊例外按工具配置核实。
- **G.EXP.37-CPP**：`switch` 有明确 `default` 分支；非法状态应处理或按接口约定说明，不用空分支掩盖缺失逻辑。
- **G.EXP.38-CPP**：`switch` 至少有两个实际条件分支，单条件优先 `if`，不凑无意义分支。
- **G.EXP.40-CPP**：不使用浮点循环计数器；整数次数与实际计算量分开表达，检查累计误差。
- **G.EXP.42-CPP**：避免 `goto`，优先结构化控制流；必要底层清理场景不得因形式重构漏释放。
- **G.EXP.43-CPP、G.OTH.01**：删除无用、无效和永不执行的代码，不通过注释长期保留废弃实现。
- **G.CTL.03**：循环能够按设计安全退出；校验边界、步进、溢出、取消和超时。常驻服务循环需有明确生命周期。
- **G.FUN.01-CPP**：函数职责单一；参数建议不超过 5 个，函数 50 行、嵌套 3 层按 ASC-26/27 评估。
- **G.FUN.02-CPP**：函数所有声明与定义的参数名、类型和限定符一致，修改时核对完整调用接口。
  C 中无参数函数的声明和定义统一按项目语言标准写 `void`；C++ 空参数列表按目标标准保持一致，不能只改单侧。
- **G.FUN.03-CPP**：不保留无用途的参数；稳定 ABI、虚函数或回调必须保留的槽位可采用未命名参数等项目允许方式并说明。
- **G.FUN.04-CPP**：避免定义 C 风格变参函数，优先有类型约束的重载、模板或现有类型安全接口。
- **G.FUN.07-CPP**：不以 `return std::move(local)` 返回局部变量而妨碍返回值优化；采用符合实际类型的直接返回。

## 五、内存、资源与空指针

- **G.FUU.09、G.FUU.10**：不使用 `realloc()`、`alloca()`；使用容量可控、符合对象构造和所有权的方案。
- **G.FUU.11**：检查安全函数返回值并正确处理失败/截断，不在失败后使用不完整数据。
- **G.FUU.12**：`destMax` 使用真实可写目标容量及正确单位，不把期望复制长度假作容量。
- **G.FUU.13、G.FUU.14**：直接使用批准的安全函数，不新增同义封装或宏重命名以绕过检查；既有语义封装按 ASC-12 核实。
- **G.FUU.15、G.FUU.21**：Host 内存操作使用华为安全函数库或经项目认可的其他安全函数，不引入不安全内存操作函数。
  未提供库或 device API 场景按 ASC-12 的兼容边界处理，不捏造接口。
- **G.RES.01-CPP**：外部数据作为索引或内存长度前验证合法性和真实对象边界。
- **G.RES.02-CPP**：分配前校验大小、元素数、乘法溢出、上限与资源预算；零长度语义按接口处理。
- **G.RES.03-CPP**：数组参数不能仅传指针，还须表达长度/容量和单位，见 ASC-08。
- **G.RES.04-CPP**：局部对象地址不逃逸到作用域外继续使用，包括返回值、成员、异步任务和延迟调用。
  重点排查返回局部变量地址，以及函数结束后仍由全局对象、堆对象或后台任务保存的栈地址；需要延长生命周期时使用明确的静态存储或动态所有权，
  不以修改指针类型掩盖栈地址泄漏。
- **G.RES.05-CPP**：逃逸 lambda 不按引用捕获局部变量；`this` 的借用也须保证生命周期。
- **G.RES.06-CPP**：lambda 使用明确捕获，避免默认 `[=]`、`[&]`，见 ASC-13。
- **G.RES.07-CPP**：释放资源后立即将仍保留的句柄/描述符置为其约定无效值；优先让所有权对象负责。
  重置单个变量不能消除其他别名，仍需排查悬空使用。
- **G.RES.08-CPP**：使用 RAII 管理资源，覆盖正常、失败、提前返回和异常路径。
- **G.RES.09-CPP**：适用时用 `std::make_unique` 创建独占对象；核对目标 C++ 标准与自定义删除器要求。
- **G.RES.10-CPP**：适用时用 `std::make_shared` 创建共享对象；先证明需要共享所有权，不能机械扩大共享。
- **G.RES.11-CPP**：`new/delete`、`new[]/delete[]` 配对，其他分配器用各自匹配的释放接口。
- **G.RES.12-CPP**：自定义 `new/delete` 配对定义，遵循被替换操作符的分配、失败、对齐及释放约定。
- **G.RES.13-CPP**：按实际分配方式处理失败：普通抛异常的 `new` 按项目异常边界处理 `std::bad_alloc`，
  `nothrow new` 返回 `nullptr` 时显式判空；不把普通 `new` 的判空当成完整异常处理，无异常构建遵从工具链约定。
- **G.RES.15-CPP**：禁止直接解引用可能为空的指针。沿当前 trace 和业务契约证明指针非空、指向的对象仍有效，
  在解引用前完成必要判空或范围校验；不能仅在无关位置判空，也不能用一次置空掩盖其他别名。
- **内存与资源泄漏（SecK_MemoryAndResourceLeakChecker）**：检查内存、文件、锁、设备句柄等的所有权和全部退出路径。
- **空指针解引用（SecK_NullPointerDereferenceChecker、安全 TOP）**：验证获取/查找/转换结果，判空与使用间对象仍须有效，
  并结合 `G.RES.15-CPP` 处理可能为空的路径。
- **越界（SecK_OutOfBoundsChecker）**：核对数组、缓冲区、指针偏移和容器的真实范围，不以类型大小代替对象容量；
  对实际分配的数组还要确认访问下标和终止位置，例如最后一个合法元素与越界访问的区别。
- **释放后使用（SecK_UseAfterFreeChecker）**：排查全部别名、异步回调和容器失效；置空一个指针不等于风险消失。
- **构造分配与析构释放**：构造函数分配并保存到字段的资源须有匹配所有权管理；同时核对构造失败、拷贝、移动和析构。

## 六、字符串、容器、算法与格式化

- **G.STD.01-CPP**：C++ 使用适用的新标准头，如 `<cstring>`、`<cstdio>`；共享 C 头和目标工具链保持兼容。
- **G.STD.02-CPP**：Host 拥有的普通文本优先用 `std::string`，不改变 C ABI/device 地址语义，见 ASC-10。
- **G.STD.03-CPP**：不从空指针构造 `std::string`，先验证输入及长度；空文本使用合法空字符串表示。
- **G.STD.04-CPP**：不长期保存 `c_str()`、`data()` 返回指针；同步借用满足 ASC-11 的生命周期前提。
- **G.STD.05-CPP**：C 字符串缓冲区容纳有效字符及 NUL 终止符，校验容量、终止及截断，不把任意字节块当字符串。
  使用 `itoa/ltoa` 等转换接口时核对目标缓冲区长度；使用 `realpath` 等路径接口时按平台 API 要求提供 `PATH_MAX`、`_PC_PATH_MAX`
  或等价的真实容量，不能用未经确认的自定义上限。
- **G.STD.07-CPP**：敏感信息不用普通 `std::string` 存储，避免不可控复制、重分配和不可证明的清除；
  密码、口令、令牌等敏感字段使用项目批准的安全存储，并在所有副本生命周期结束时清除。
- **G.STD.08-CPP**：外部索引或迭代器偏移必须在有效范围内，先校验再构造/推进迭代器。
- **G.STD.09-CPP**：只使用有效迭代器、元素指针和引用，明确插入、扩容、删除及容器销毁的失效规则；
  不解引用 `end()` 返回的尾后迭代器，也不把已失效迭代器传给后续算法。
- **G.STD.11-CPP**：算法目的区间已有足够大小，或通过合法 `back_inserter`/`insert_iterator` 等增长；
  `reserve` 不等于已创建元素。使用 `copy`、`copy_n`、`fill_n`、`transform` 等算法前确认目标区间真实可写。
- **G.STD.12-CPP**：需要删除时，`remove/remove_if` 后配合容器 `erase`；越界等具体缺陷按 ASC-15 实际诊断。
- **G.STD.13-CPP**：格式化输入/输出使用有效格式串，占位符、修饰符、参数类型与数量一致，见 ASC-23；
  单独核对格式参数个数和转换指示符与实参实际类型，不用无依据的 cast 掩盖不匹配。
- **G.STD.14-CPP**：格式串不受外部数据控制；外部文本作为普通数据参数传入。

## 七、并发、文件、进程与外部命令

- **G.CON.01-CPP**：条件变量等待必须循环检查受保护的条件，或使用等价的谓词重载；处理虚假唤醒、超时和退出。
- **G.CON.02-CPP**：避免手动调用 mutex 的 `lock/unlock`，使用 RAII 锁；必要底层所有权转换需证明配对和异常安全。
- **数据竞争（SecL_DataRace）**：同一共享状态所有读写使用一致同步策略，包含回调、销毁与库内部共享存储，见 ASC-16/17。
- **G.OTH.02**：信号处理函数不访问普通共享对象；只采用平台允许的信号安全通信和状态访问机制。
- **G.STD.18-CPP**：调用库函数时检查可重入性和共享缓冲区，避免库返回值、环境状态和静态存储竞争。
- **G.STD.19-CPP**：信号处理例程只调用异步信号安全函数，不使用普通日志、分配器或不安全的锁。
- **G.FIL.01**：创建文件显式指定合适访问权限，遵循最小权限，考虑实际 `umask` 和平台语义。
  例如 POSIX `open` 使用 `O_CREAT` 时传入权限参数，并核对该权限确实适合目标文件。
- **G.FIL.02**：外部文件路径按“平台支持的规范化，再按预期目录/用途校验”的顺序处理，见 ASC-18。
  Linux 可在适用场景使用 `realpath`，Windows 使用平台对应的路径规范化 API；调用前核对返回值、缓冲区容量和符号链接/TOCTOU 风险，
  不把某个平台 API 当成所有 Host/device 环境都可用。
- **G.FIL.03**：不在共享目录直接创建可被他人干扰的临时文件；使用权限受控的私有目录和安全、原子的创建方案。
- **G.FUU.18**：不把外部输入直接拼接 SQL；采用参数绑定/预编译接口，对不可绑定的标识符按明确允许集合校验。
- **G.STD.15-CPP**：禁止外部可控数据直接充当进程启动或 `dlopen/LoadLibrary` 参数；先校验外部整数、数组索引、
  分配大小和内存复制长度，再对程序、参数、模块和路径使用明确白名单。不把 shell 转义当作全部安全保证，
  不加载来源未确认的模块；SQL 外部输入也必须使用参数绑定或白名单校验。
- **G.STD.16-CPP**：不新增直接程序/线程退出或 `atexit` 调用，优先显式生命周期和错误传播；遗留场景按 ASC-19 分析，不删必要清理。
- **G.STD.17-CPP**：不直接用 `kill/TerminateProcess` 终止其他进程；合法自有子进程管理按 ASC-19 的所有权与回收约束审查。
- **G.OTH.04**：发布版本不输出对象或函数地址，日志、报错和格式化指针同样检查。`%p` 或把保存地址的 `intptr_t/uintptr_t`
  用 `%d/%x/%o` 输出都属于地址泄漏；优先删除，确需诊断时使用项目批准的不可逆脱敏方案，不能未经评估直接改成哈希。
- **G.OTH.05**：产品代码不硬编码公网地址；宏、变量赋值及 `strcmp/strncmp/memcmp` 等比较中的公网 IP 也要检查。
  网络端点采用经项目批准的配置。规范/许可证中的文档链接不作为网络访问配置替换。

## 八、敏感信息、随机数与密码应用

- **G.MEM.04**：内存中敏感信息用完立即通过批准的、不会被优化移除的清除接口清零，并核对副本和错误路径。
- **G.OTH.03**：安全用途不使用 `rand` 等弱随机源，使用批准的安全随机接口并处理失败，见 ASC-20。
- **安全 TOP：不安全 IPSI 算法**：核对目标 IPSI 库和项目批准的算法清单，替换被禁用/废弃的密码接口；
  未提供清单时不能从检查名猜测具体禁用函数，也不能声称全部检查通过。
- **安全 TOP：scrypt 口令单向哈希**：本项目给定最低参数为 CPU/内存代价 `N >= 2^14`、
  盐至少 **16 字节**、块规模 `r >= 8`、并行参数 `p >= 1`、输出至少 **256 比特（32 字节）**。
  `N` 是代价参数而非内存字节数；同时满足库的合法取值和资源上限，检查参数单位，盐使用批准的随机来源。
  参数含义见 [RFC 7914 §2/§6](https://www.rfc-editor.org/rfc/rfc7914.html#section-2)；
  上述最低值是项目约束，不声称 RFC 为所有环境规定了该最低值。
- **安全 TOP：分组密码填充**：当所选模式/协议需要填充时，正确选择 CMS-Padding 或 ISO-Padding，
  通过批准的密码库实现；不向不需要该填充的模式机械添加填充，不自造填充、验证或错误处理。
- **安全 TOP：加密与 MAC 同密钥**：分别使用独立、用途明确的加密密钥和 MAC 密钥，不复用同一个对称密钥。
  标准 AEAD 算法按批准接口和算法规范使用，不擅自改造其内部密钥安排。
- **安全 TOP：弱加密算法**：使用项目当前批准的算法、模式和密钥长度，不新增弱算法或自行设计密码方案；
  兼容迁移必须确认协议和数据处理方案，不仅改函数名。
- **安全 TOP：时间种子**：不直接使用系统时间作为安全随机数种子，不将时间戳伪装成不可预测随机数。
- **安全 TOP：安全随机数后处理**：产品不对安全随机接口输出自行做进一步处理后充当安全随机数；
  不自行截断、取模、拼接或混合以改变安全属性。需要特定格式/范围时采用批准的专用接口或方案，不能自行豁免。
- **安全 TOP：密码应用与密钥管理**：检查算法用途、密钥生成、存储、访问、分发、轮换、销毁和日志暴露；
  依赖项目正式密码规范和批准组件，不把静态检查器覆盖的部分要求当成完整密码审计。

## 九、头文件、命名空间与模板

- **G.INC.01-CPP**：头文件不能循环依赖；通过合理模块边界解决，不用保护宏掩盖依赖环。
- **G.INC.02-CPP**：不包含无用头文件；保留真实直接依赖及有意的公开聚合导出，见 ASC-22。
- **G.INC.03-CPP**：头文件自包含，不依赖调用者预先包含其他头；用受影响消费端验证包含关系。
- **G.INC.04-CPP**：采用仓库统一的重复包含保护，保护符合法且唯一。保护符避免首尾下划线、使用项目路径相关的唯一名称，
  保护区域前后不放业务代码；使用 `#pragma once` 前核对目标编译器支持。
- **G.INC.05-CPP**：不在 `extern "C"` 块内包含头文件；需要 C 链接的头在自身正确声明语言边界。
- **G.INC.06-CPP**：优先包含正式类声明头，避免易与实际类型不一致的手写前置声明；确有边界约束时保持准确声明。
- **G.INC.07-CPP**：按仓库约定排序包含。现有配置允许同名头在最前或最后，识别 `stdAfx.h`、`pch.h` 预编译头；
  实际顺序服从构建要求，不为排序破坏预编译头；各依赖组保持一致。
- **G.INC.08-CPP**：不在 `#include` 前用 `using` 导入命名空间，避免改变后续头的名称解析。
- **G.INC.09-CPP**：头文件不向全局命名空间导入符号或使用全局 `using namespace`。
- **G.INC.10-CPP**：头文件不以匿名命名空间或 `static` 隐藏普通非导出定义，避免每个翻译单元产生独立状态；
  按目标标准正确组织模板、内联实体和常量，不机械破坏合法头文件定义。
- **G.INC.12-CPP**：`.cpp` 中无需导出的变量、常量和函数使用匿名命名空间或适当 `static` 限定。
- **G.TMP.01-CPP**：模板的各部分与显式特化放在模板所在文件，确保调用点可见并满足单一定义原则；
  核对特化的声明、定义和链接方式，不把非内联普通定义复制到多个翻译单元。

## 十、预处理与宏

- **G.PRE.01-CPP**：C++ 用 `constexpr` 或具名枚举替代表示数值的宏；C/共享头和平台预处理常量保持兼容。
- **G.PRE.02**：宏参数和整体表达式使用完备括号，仍须检查类型和重复求值。
- **G.PRE.02-CPP**：优先函数、`inline` 或模板替代函数式宏。
- **G.PRE.03**：多语句函数式宏采用 `do { ... } while (0)`，同时遵守 ASC-21 的控制流限制。
- **G.PRE.03-CPP**：`#if/#elif` 常量表达式明确表达布尔条件，不依赖含义不清的数值判断；检查宏是否定义时使用 `defined`，
  开关宏使用约定的 `0/1` 值。
- **G.PRE.04**：不向函数式宏传递带副作用的实参，避免多次求值和顺序变化。
- **G.PRE.04-CPP**：`#if/#elif` 中被求值的标识符预先定义；需要检测是否存在时使用 `defined` 等正确机制。
- **G.PRE.05-CPP**：配对的 `#if/#ifdef/#ifndef`、`#elif/#else/#endif` 位于同一文件且结构完整。
- **G.PRE.07**：宏名不与语言关键字相同，不通过宏改变关键字含义。
- **G.PRE.08**：宏调用实参中不出现预处理指令。
- **G.PRE.09**：宏定义末尾不附加分号；分号由调用语句提供。
- **G.PRE.10**：宏不隐式依赖调用处局部变量名，所有依赖显式表达。

## 十一、格式、命名与注释

- **G.FMT.11-CPP**：选择、循环语句使用大括号，单语句同样处理。
- **G.FMT.14-CPP**：指针 `*`、引用 `&` 按仓库规则跟随类型或变量，风格一致，不破坏多级指针可读性，见 ASC-22。
- **G.FMT.17-CPP**：按逻辑分组合理留空行，连续空行不超过 **2 行**；不压缩代码规避规模检查。
- **G.CMT.03-CPP**：文件头保留正确版权和许可证说明。适用仓库要求时，中文可采用
  `版权所有 (c) 公司名称 起始年-最后重大修改年`，英文可采用
  `Copyright (c) Company Name 起始年-最后重大修改年. All rights reserved.`；起始年必须有文件历史依据，
  重大特性扩展或重构再更新结束年。既有华为/海思文件遵循其原有声明，不因分析器识别名称就把第三方或个人作品版权改写为其他权利人，
  也不凭空添加版权年份。开源工程还要遵守实际许可证文本。
- **G.CMT.04-CPP**：不写空有格式的函数头注释；注释说明真实语义、前提和边界。
- **G.CMT.05-CPP**：正式交付不留未闭环 TODO/TBD/FIXME，先处理实际缺口，不以改大小写或删关键字绕过，见 ASC-24。
- **G.NAME.03-CPP**：采用统一命名；仓库既有明确规范和公开 API 兼容性优先。没有更具体约定时采用下表，
  不借此次局部修改全仓重命名。未给定的模块名和前缀不自行编造。

| 对象 | 默认命名 |
| --- | --- |
| 类、结构体、联合体、枚举类型 | `CamelCase` |
| 函数、成员方法 | `CamelCase` |

## 十二、Ascend 性能接口

- **SecA_Ascend_GEDeprecatedLowPerformanceInterface**：不新增目标版本已废弃或低效的 GE 接口调用；
  根据正式接口说明、实际调用链及适用架构确认替代方案。例如目标 API 确实提供时，评估用
  `Node::GetOutNodesSize()` 替代 `Node::GetOutNodes().size()`；不能只凭检查名或示例跨版本替换。
- **SecA_Ascend_GERecommandHighPerformanceInterface**：在功能、精度和资源语义一致时优先使用推荐的高性能 GE 接口。
  例如目标 API 确实支持时，评估将返回副本的 `AttrUtils::GetStr` 形式替换为返回只读指针的形式；
  未提供具体接口清单时不得从检查名猜测 API。替换前验证生命周期、错误语义和 ABI，性能主张需实际测量，不能把命名或本地检查当性能结果。

## 十三、规模、重复与检查质量

度量用于发现需评审的位置，不等于自动认定缺陷。阈值的计数/包含关系以分析器定义为准；
未运行分析器时仅报告人工检查，不声称度量通过。表中新增/修改阈值相同处只写一个值。

| 度量项 | 给定配置及开发要求 |
| --- | --- |
| `code_duplication_ratio[C++]`、`non_hfile_code_duplication_ratio[C++]` | 切片 10 行，重复率阈值 0.1（10%）；通过合理抽象和代码管理减少重复，不为去重合并不同架构/协议行为。 |

| `huge_folder[C++]` | 阈值 50，配置启用告警；设置合理的目录结构提升可读性和可维护性。原配置未注明计量单位，先核实工具定义，不解释为 50 个文件或 50 行。 |
| `huge_headerfile[C++]` | 新增/修改阈值 500，配置启用告警；超大头文件通常提示架构或依赖管理需要评审，实际计数口径按工具。 |
| `huge_non_headerfile[C++]` | 新增/修改阈值 2000，配置启用告警；超大源文件通常提示架构管理需要评审，按职责拆分并验证行为。 |
| `lines_per_file[C++]` | 阈值 300，为文件规模观察值；与大文件告警阈值分别记录，不当作同一个硬上限。 |
| `lines_per_method[C++]`、`huge_method[C++]` | 规则配置分别为 30 和 50（后者新增/修改均启用告警）；项目函数拆分统一以 ASC-26 的 50 行评估，30 只保留为度量观察值。 |
| `redundant_code[C++]`、`redundant_code_kloc[C++]` | 检查冗余代码，后者阈值 0；删除确认无效代码，不改变必要行为。 |
| `unsafe_function[C++]`、`unsafe_functions_kloc[C++]` | 检查不安全函数，后者阈值 0；按批准清单和实际 Host/device 能力处理，不用改名绕过。 |
| `warning_suppression[C++]` | 审查告警抑制并删除无依据的抑制代码；不得新增屏蔽、放宽阈值或工具忽略项来宣称质量达标，必要例外按核心规范留证据。 |

## 十四、设计与可维护性

以下检查没有给出检测阈值。结合真实职责、依赖与修改场景审查，不凭类名、行数或单个告警强制重构。

- **上帝文件、上帝类**：避免一个文件/类掌握过多业务职责和跨模块状态；按内聚职责划分边界。
- **复杂文件、复杂类**：减少交织控制流、隐式状态和过多依赖；先明确接口与不变量，再评估拆分。
- **传统破坏者**：派生类不破坏继承体系已有接口约定、不变量和行为；不适合的复用优先考虑组合。
- **依恋情节**：行为长期大量操作其他对象的数据时，评估职责是否应归属该对象，避免扩大访问权限解决。
- **循环依赖**：类、模块和文件依赖保持可理解方向；以接口分层或职责调整断环，不仅让头文件勉强编译。
- **拒绝父类馈赠**：子类长期拒用/禁用继承来的大部分能力时，重新评估继承关系，考虑窄接口或组合。
- **数据泥团**：反复共同传递且具有共同业务含义的数据可封装为有约束的类型；不为减少参数机械打包无关数据。
- **重写签名不一致**：重写时核对参数、`const`、引用限定符和返回类型，使用 `override` 让编译器检查，避免意外隐藏基类函数。
- **破坏稳定抽象原则**：稳定模块通过稳定抽象表达依赖，避免核心接口依赖频繁变化的实现细节。
- **精神分裂文件、精神分裂类**：同一文件/类不混装互不相关且独立变化的职责；名称和公开接口应准确表达用途。
- **继承层次混乱**：继承表达有效的可替代关系，避免多余层次、交叉依赖及含糊所有权；不为共享少量实现滥用继承。
- **霰弹式修改**：单一业务变化不应要求散落修改大量无关位置；优先集中变化点、消除重复知识，保持真实架构差异。
