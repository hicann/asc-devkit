# ASC 代码开发规范

适用：ASC 工程 C/C++、主机侧工具、AscendC 中适用的通用代码及 Shell 脚本。
本文件包含 28 项核心规范，其中 ASC-26～ASC-28 为用户指定的函数长度、嵌套深度与产品实现参考来源约定。
涉及 C/C++ 时同时按[C/C++ 开发细则](cpp-development-standard.md)检查类、异常、表达式、资源、
并发、安全、头文件、宏、命名、代码度量和设计；细则补充核心规则，不改变 ASC 编号或既有约定。
这是项目工作规范，不是完整的官方编码标准；具体问题需结合代码上下文判断。

## 使用与优先级

- **规则**：从原始告警归纳，应用于本次变更中相关语言、模块和代码路径。
- **实现建议**：为落实规则补充的方法，不代表原分析器的额外强制要求。
- **规范组织**：本文件是语言无关的核心规范；C/C++ 变更还必须读取[C/C++ 开发细则](cpp-development-standard.md)的适用章节。
  细则按场景分组便于加载，不按来源或时间划分优先级；已读取的核心规则和语言细则都属于正式约束。
- 默认先处理越界、生命周期、资源泄漏、竞争和路径边界，再处理类型与可维护性。
- C ABI、固定协议/文件格式、工具链版本和 device API 的真实限制必须保留。不得机械替换已有公开接口。
- 用新增代码和本次修改范围开展自检，不因这份规范擅自对整个仓库进行风格翻修。

## 一、输入、容量与数值

### ASC-01 常量表达业务含义

规则：新增或修改的产品代码中，除独立且语义明确的 `0`、`1` 外，所有数值字面量均按魔鬼数字处理，
必须使用表达业务含义的具名常量、枚举或已有定义。十进制、十六进制、负数、浮点数、下标、模板参数
和默认参数均适用，注释不能代替命名。常量的定义处允许写对应字面量；命名应反映含义和适用单位，
不要生成只复述数值的名称。相同数值的不同业务含义不能合并。

- `0`、`1` 不是无条件豁免：与其他数值构成同一组状态、协议取值、索引、边界或其他上下文关系时，
  应与同组数值一起命名，例如用 `enum class State { Idle = 0, Busy = 1, Failed = 2 };`。
  独立且语义明确的计数初值或递增步长可直接使用 `0`、`1`；不明确时也应命名。
- 优先复用同语义、同单位、同适用范围的已有常量；协议偏移、字段宽度、寄存器位、架构 ID、
  缓冲区大小、单位换算和权限值均须具名。PMU 系数、指令 ID 等须说明来源和架构范围，不自行改值。
- 采用能保持编译期求值和原行为的语言机制，避免为命名引入运行时计算、动态分配或额外访问开销：
  C++ 优先使用合适类型的 `constexpr` 或枚举；C、共享头和 Shell 采用目标工具链支持的兼容形式。
  设备代码遵守实际编译器和地址空间限制，不为套用写法改变 ABI、类型或性能。
- 常量定义收拢到满足使用需求的最小作用域。仅在一个函数内使用一两次的常量直接定义在函数内；
  同一函数内使用超过三次也不因此提升作用域。跨函数复用时选择最小可行的私有作用域，
  只有同一语义常量在较大范围使用**超过三次**，且确需跨函数共享时，才可放到文件级匿名
  `namespace`；恰好三次不满足该条件。公开接口或跨文件确需共享时按接口和链接约束选择位置，
  不为凑使用次数扩大作用域，也不重复定义同义常量。
- 预算、容量、超时类常量集中在实际共享所需的最小作用域，注明单位、依据和可覆盖方式；
  不在多个文件重复同一语义裸数字。无法采用具名定义时，按本 skill 的例外要求逐项记录约束与证据。

### ASC-02 运算符使用恰当类型

规则：比较、算术、位运算和移位使用语义匹配的操作数；检查符号、位宽、提升、截断和枚举域。
控制条件显式比较状态码、计数或标志位，例如 `count != 0U`、`status == SUCCESS`、
`(flags & mask) != 0U`，指针可直接判空。不把返回零表示成功的接口改成相反含义。

实现建议：位运算优先采用适当位宽的无符号类型，移位量须小于位宽；转换前检查范围。
不要通过“给两边都加 cast”掩盖类型错误。浮点计算结果的近似比较需按业务选误差尺度，
不能对所有 `double ==` 统一套固定 epsilon；精确哨兵值和枚举式状态需结合 API 判断。

### ASC-03 边界算术不发生意外回绕

规则：长度、分配大小、偏移、累计计数在加减乘之前验证范围；不能先算溢出的结果再检查。
例如无符号 `offset <= capacity` 后再验证 `length <= capacity - offset`，
非零元素大小下验证 `count <= max / elementSize`。

有意的模运算必须单独说明。样本的 `hash * kPrime` 告警可能属于哈希算法规定的无符号回绕，
不能直接改为拒绝溢出或饱和计算；先确认算法、类型和兼容性，并以已知向量验证。
此例外不能用于缓冲区容量或指针偏移。

### ASC-04 外部输入在使用前完成校验

规则：命令行、环境变量、文件、IPC、二进制元数据或回调携带的外部值进入数组索引、
指针偏移、循环次数、分配大小或敏感调用前，检查范围及实际对象容量。
负数转无符号前先拒绝非法负值；校验枚举、数量、版本及必要对齐。
不要把“类型转换成功”当成“输入合法”。

实现建议：二进制解码先证明字段在消息剩余长度内，再读取及推进游标；循环同时考虑合法上限和资源消耗。
失败返回项目约定错误，并保留可定位的信息。校验要覆盖真实使用路径，不能只加在无关入口。

## 二、类型与接口

### ASC-05 别名和枚举具有语义

规则：不通过宏/重复别名重定义基础类型。C++ 的确需别名优先 `using`，确需枚举优先 `enum class`。
字符使用字符类型；数值字段使用合适整数类型，不依赖 `char` 的有符号性。

边界：公开 C 头、兼容 ABI、自动生成的协议类型不机械替换为 C++ 语法或作用域枚举。
字符差值如数字解析应先验证字符范围，再明确转换到目标数值类型；不能把文本处理一律改成整数处理。

### ASC-06 类型转换有可证明的前提

规则：C++ 避免 C 风格转换，按含义选择命名转换；C 源码和 C ABI 宏保持语言合法性。
避免不必要的 `reinterpret_cast` 和 `const_cast`。`static_cast` 也不保证截断、对齐或范围安全。

底层设备地址、动态符号、寄存器/二进制接口确需转换时，限制在接口边界，并说明大小、对齐、地址空间、
对象生命周期及别名规则。不要通过解引用重解释指针解析任意字节流；选用该目标支持的受控复制/解码手段。
不得用 `const_cast` 写入本来就是 const 的对象。

### ASC-07 只读意图用 const 表达

规则：不修改目标对象的指针/引用参数使用 `const`；不改变逻辑状态的成员函数可加 `const`。
确认修改的是 pointee 还是指针本身，不把句柄的浅层 const 误解为底层资源只读。
声明、定义和调用链同时核对；公开 API、回调签名及虚函数接口的兼容性优先。

### ASC-08 数组参数携带长度

规则：裸缓冲区参数明确传入长度/容量，或采用目标语言版本支持的数组引用、容器等能表达边界的类型。
统一单位是字节还是元素，写接口还需区分容量和有效长度。
禁止对已退化为指针的数组形参使用 `sizeof` 求数组大小。

实现建议：C++17 使用指针与长度、`std::array`/`std::vector` 或数组引用；仅在项目支持时采用 C++20 `std::span`。
保留需要固定签名的 C/设备 ABI，内部入口补充可验证的边界信息。

### ASC-09 声明和定义保持一致

规则：函数各处声明与定义参数名一致；覆盖虚函数显式写 `override`，确需禁止后续重写才用 `final`。
变量靠近首次使用处声明并初始化。调整名字或限定符时同时核对所有声明，避免只改单侧。

## 三、字符串、内存和生命周期

### ASC-10 Host 文本所有权清楚

规则：Host C++ 拥有的文本优先 `std::string`。C ABI、输出缓冲区、非拥有字符串和设备地址可保留原接口，
但必须明确长度、终止条件、所有权和有效期。

实现建议：只读非拥有视图可用 C++17 `std::string_view`，但它不延长生命周期，也不保证以 NUL 结尾；
不能直接当作 C 字符串传入系统接口。

### ASC-11 不持有会失效的字符串指针

规则：使用 `c_str()`/`data()` 结果前证明所属字符串仍存在且未发生使指针失效的修改。
不得保存临时字符串结果指针或让该指针逃逸到异步回调；同步 C 调用期间的临时借用可以保留。
需要保存时保留字符串所有权，在调用点重新取指针。

### ASC-12 安全内存接口直接使用且检查结果

规则：样本基线要求 Host 内存/格式化操作使用项目已提供的安全函数，样本点名 `memcpy_s` 和 `snprintf_s`。
替换前确认库是否存在及真实签名，传入真实目标容量、有效源长度，并检查错误/截断结果；
不能只是改函数名、把复制长度假作目标容量，或在失败后继续使用不完整结果。

原始 `G.FUU.13` 的标题是“禁止封装安全函数”，描述却把 `MirrorMemcpy`/`MirrorMemset`
标为疑似自定义风险函数。按该基线直接调用经批准的安全接口，不新增同义包装来绕过扫描。
既有业务封装要核实其远端/设备内存语义和实际检查，不能仅凭名称删除。

device `DataCopy`、GM/LocalTensor 操作不能机械换成 Host Secure C 函数；CANN 地址空间和 API 能力优先。
若目标没有该库，使用已支持的受控方案并说明限制，不自行捏造 `_s` 接口。

### ASC-13 异步任务不引用失效对象

规则：不让局部对象地址、引用和 `this` 在对象销毁后被线程/回调使用。
lambda 使用显式捕获，避免 `[=]`、`[&]` 隐藏依赖；捕获 `[this]` 仍然只是借用，不延长对象寿命。

实现建议：按语义选择值捕获、适当的所有权转移或有明确 join/cancel 的借用；析构前保证后台任务已结束。
不要为了延长生命周期盲目引入共享所有权或循环引用。

### ASC-14 资源所有路径回收

规则：文件描述符、锁、映射、socket、设备句柄等在正常返回、失败、提前返回和异常路径均完成回收。
检查获取结果；文件描述符 `0` 也合法，应按 `fd >= 0` 判断。

实现建议：Host 使用仓库已有 RAII 管理对象；需要共享所有权且适用时优先 `std::make_shared`。
需要自定义 deleter、私有构造或其他受限资源时按真实所有权选择构造方式，不能机械把所有资源改为 shared_ptr。

### ASC-15 删除容器元素不使用失效迭代器

规则：C++17 使用 `erase(remove(...), end())` / `erase(remove_if(...), end())` 完成真正删除，
并检查算法和容器 API 的返回值；对 `end()`、删除后的迭代器/引用不解引用、不继续使用。

样本虽以 erase-remove 规则名报出，实际描述为“迭代器已越过容器末尾”。必须按真实控制流确认根因，
不能看到规则名就无条件套入 remove。遍历删除时遵循对应容器的迭代器失效规则。

## 四、并发、路径和进程

### ASC-16 共享状态使用一致同步策略

规则：检查每条锁获取/释放路径、同一共享状态的全部读写及线程退出。
既避免漏锁，也避免未加锁就解锁；确认共享返回值和跨线程 `this` 的生命周期。

实现建议：Host 优先使用 RAII 锁，维持明确锁顺序。不能只靠“存在一个 mutex”证明线程安全；
回调、条件变量和提前释放需要逐条分析。原子变量需验证足够的同步语义，而非机械替换所有变量。

### ASC-17 库返回的借用存储及时复制

规则：对 `getenv` 等可能返回共享/可变存储的接口，检查返回值并及时复制到自己持有的对象，
不要把原指针跨后续库调用长期保存。

实现建议：程序初始化时读取所需环境并保存快照；若有并发环境修改，复制本身不足以消除竞争，
需要统一同步或避免运行期间修改。不要假定“多调用一次 getenv 后原指针一定有效”或“必然失效”。

### ASC-18 路径规范化与用途校验

规则：使用文件路径前规范化并检查用途所要求的类型、权限及允许范围；规范化失败走错误路径。
读已有目标和创建新目标分别处理；新文件不能简单要求目标已经存在，应验证父目录与最终文件名。

实现建议：对受限目录内的输出拒绝 `..` 逃逸和不允许的符号链接；按路径组件判断归属，
不能用裸字符串前缀把 `/safe2` 当 `/safe` 子目录。规范化不自动消除 TOCTOU；有对抗性并发风险时使用
目录 fd、`openat`/`O_NOFOLLOW` 等平台已支持方案，打开后核实实际对象。
不为没有约束的合法绝对路径凭空增加固定白名单。

### ASC-19 进程操作明确目标和回收

规则：样本基线禁止直接终止其他进程，另有 `atexit` 被同一规则报警；两者要分别判断，
不能把注册退出回调等同于杀进程。

实现建议：优先现有的取消、退出、回收和超时机制。若工具确实需要控制自己启动的子进程，
确认所有权、有效 PID、进程组、信号范围和 wait/reap；不得因消警删除必要清理或扩大终止范围。
遗留 `atexit` 则单独核查退出顺序、对象寿命和资源清理，可用显式生命周期管理替代时再修改。

### ASC-20 安全随机数满足真实用途

规则：认证令牌、保密 nonce、不可预测标识等安全用途不使用 `rand` 或其他未经确认的弱随机源。
按平台支持使用密码学安全随机源并处理失败。非安全采样/可重复测试不盲目更换算法；
对随机临时名称还需考虑安全创建，不能只靠名称随机。

## 五、结构、格式和交付

### ASC-21 宏与分支不隐藏控制流

规则：函数式宏慎用 `return/goto/continue/break` 等影响调用者流程的语句；能使用 inline 函数或模板时优先替代。
确需错误返回宏时，清楚标识调用者控制流及参数求值语义。`do { ... } while (0)` 不能消除宏内 `return` 的影响。
`switch` 至少有两个实际条件分支；仅一个 case 时优先改为 `if`，不能加无意义空 case 凑数。

### ASC-22 头文件与指针格式保持清晰

规则：去除确实未使用的头文件，同时保留必要直接依赖及有意的公开聚合头导出。
格式以仓库 formatter 和公开 C/C++ 头规则为准；`*`/`&` 与类型或变量保持一致且留出可读空格，
多级 const/指针不黏连成歧义写法，例如 `const char * const *sections`。

不能只凭当前翻译单元无直接引用就删除 umbrella 头导出的 API；修改头文件后验证受影响的消费端。

### ASC-23 格式串与实际类型严格对应

规则：格式化输入/输出的占位符、长度修饰符及实参一致；检查可变参默认提升，
尤其是三目运算后的真实类型，不能只看其中一个分支。固定宽度整数采用项目支持的正确格式宏或类型安全接口。

实现建议：格式串不受外部输入控制；同步检查安全格式化接口的容量参数、返回值和截断处理。
不为格式串简单加 cast 而截断原值。

### ASC-24 注释有内容且交付闭环

规则：去掉没有实际内容的函数头模板；注释解释前提、单位、协议、所有权或特殊实现原因。
正式交付代码不留下未闭环的 TODO/TBD/FIXME。
不能仅删关键字来隐藏功能缺口；先实现、移入可跟踪事项并明确不属于本次交付，或按项目流程记录例外。
开发期间的暂存标记不等同于已完成。

### ASC-25 Shell 解释器声明明确

规则：样本基线要求 Bash 脚本首行是 `#!/bin/bash`，前面无 BOM、空白或注释。
修改前核对目标平台解释器和脚本语法，不只更换 shebang。
若项目明确要求 POSIX sh 或目标无该路径，应保留可运行方案并说明与此告警基线的差异。

## 六、函数规模、嵌套与参考来源（用户指定的项目约定）

以下三项为用户补充的项目约定。后续规则资料中的行数或嵌套配置不覆盖这里的 50 行、3 层约定。

### ASC-26 单个函数建议不超过 50 行

规则：C/C++ 函数、成员函数及 lambda 保持职责单一，函数体建议不超过 **50 行**。
超过 50 行时检查职责边界，优先将独立的校验、解码、计算或资源操作提取为有语义的辅助函数。
50 行是拆分评估阈值，不是无条件硬性上限；不能靠压缩多条语句到同一行规避检查。

本项目统计口径：按仓库格式化后的函数体物理行计算，排除空行、纯注释行和函数签名，
包括独占行的大括号；外层函数中的 lambda 定义仍计入外层行数，同时独立检查 lambda 本身。
这是项目口径，不声称是 Google 的统计定义。

状态分发、连续初始化、性能敏感的 AscendC 内核等，若拆分会损害结构、可读性或性能，
可说明理由后保留；性能例外提供适用的验证证据，不凭猜测免除检查。
避免为了满足行数拆出没有独立语义的函数，或把复杂逻辑全部搬进 lambda。

来源说明：Google C++ 指南建议函数超过约 40 行时考虑拆分，并未设硬性上限；
本项目按用户要求将评估阈值调整为 **50 行**。
参考：Google C++ Style Guide 的 Write Short Functions 章节。

### ASC-27 控制流嵌套建议不超过 3 层

规则：C/C++ 函数中控制流嵌套建议不超过 **3 层**。超过时优先用 guard clause 提前返回、
提前 continue 或提取有语义的辅助函数，减少多层 if/else 和循环的交织。
重构不得跳过必要清理、改变同步顺序或改变设备侧执行语义。

本项目统计口径：函数体本身不计层；每进入一层 `if/else`、`for`、`while`、`do`、
`switch` 或 `try/catch` 的控制体增加一层。同一 `else if` 链按同一层计算，
`case/default` 标签不另加层；普通作用域花括号不增加控制流层数。
lambda 作为独立函数检查其内部嵌套，但不能借 lambda 包装掩盖原有复杂度。

状态机、算法固有循环或性能敏感内核等必要情形可说明理由后保留。
3 层是项目建议值，不声称是 Google C++ 指南的硬性规定。

### ASC-28 产品代码开发不参考测试目录

规则：开发、修改或重构产品代码时，不参考 `test/`、`tests/` 及其任意子目录中的任何规则、
文档或代码。代码检索、实现模式查找、调用链分析和方案论证应排除这些目录。
其中的 UT 不作为真实业务场景；mock、stub、测试桩、测试专用实现或简化参数也不能用于
推定真实接口行为、设备能力、资源约束、同步顺序或错误处理要求。

实现依据来自用户需求、正式 API 文档、非测试目录中的产品声明与实现，以及可确认的真实使用场景。
如果这些来源不足，应明确缺失依据，不用 UT 的预期值或模拟行为填补事实。

本规则约束产品实现的参考来源，不禁止执行 UT 验证。单独编写或维护 UT 时可以处理对应测试文件，
但不得把测试中的规则或实现反向作为产品代码设计依据；UT 通过也不能替代真实场景验证。

## AscendC 应用提示（推导建议）

原告警主要来自 `asc/asc-tools/npu_tools`，没有提供 kernel 同步或 TQue 正确性的证据。
以下是把上述规则用于设备侧时的检查方向，不是原始告警得出的已确认缺陷：

- 对 tile 数量、核数、偏移、尾块、workspace 和字节/元素换算应用 ASC-01～04、08。
- 对 GM/LocalTensor 和设备指针转换应用 ASC-06、11～13 中适用的范围及生命周期要求，
  但按真实地址空间、CANN/SoC API 和编译模式选择实现。
- 使用 `ascendc-ar-develop` 原有调用层级和构建校验；本规范不改变设备端支持的 C++ 特性。
