# ASC 代码开发规范

本 Skill 提供 ASC 代码的编码约束和检查项；具体告警需结合代码上下文判断，
不能直接视为已经确认的缺陷。
另包含用户指定的项目约定：C/C++ 单个函数建议不超过 50 行，控制流嵌套建议不超过 3 层；
超过时优先拆分函数或提前返回，必要例外需说明理由。具体统计口径见开发规范 ASC-26、ASC-27。

## 使用流程

开发产品代码时必须遵守 ASC-28：不参考 `test/`、`tests/` 及其任意子目录中的规则、文档或代码。
其中的 UT、mock、stub 和测试专用实现不作为真实场景、接口语义或实现方案的依据。
代码检索和调用链分析应排除这些目录，以需求、正式 API 文档、非测试产品代码和真实场景证据为准。

必须执行 ASC-01 魔鬼数字约束：除独立且语义明确的 `0`、`1` 外数值字面量须具名；
有并列或上下文关系的 `0`、`1` 也须具名。优先复用已有定义、编译期求值并保持最小作用域；
具体范围和例外见核心规范。

1. **编码前**读取[开发规范](references/development-standard.md)，确认本次修改属于 Host C++、C ABI、
   device kernel 还是 Shell，并选出适用规则。涉及 C/C++ 时，同时读取
   [C/C++ 开发细则](references/cpp-development-standard.md)中与变更相关的章节；类/异常、类型/数值、
   资源/并发、污点/边界、安全、头文件/宏以及规模/设计的阅读入口见该文件导航。
   无需先索取 devkit/CANN/SoC 才能整理规范或审查普通 Host 片段；
   真正实现 AscendC 需求时沿用调用方的输入和架构约束。
2. 实现时明确输入信任边界、容量/单位、资源所有权、异步生命周期和共享状态。优先复用仓库已有、
   已验证的接口和语义常量，仅修改本次任务涉及的代码。
3. **交付前**按开发规范末尾的检查表及 C/C++ 细则适用章节复核变更，执行与修改相称的编译、静态分析或测试。
   没运行的检查必须写“未执行”；没有原分析器结果时不得声称“告警清零”。
4. 修复具体告警时，结合当前分析器输出和代码上下文确认根因；不能仅靠扫描文本认定真实缺陷，
   也不能仅为消除告警改变 ABI、协议或算法。

## 规则索引

所有产品代码变更先读取[核心开发规范](references/development-standard.md)，并按 ASC-28 排除测试目录。
涉及 C/C++ 时，再按变更信号读取[C/C++ 开发细则](references/cpp-development-standard.md)对应章节；
下表是加载入口，不是规则优先级。所有已读取章节都属于正式约束。

| 变更信号 | C/C++ 细则读取范围 |
| --- | --- |
| 类、继承、虚函数、异常、声明和接口 | 类/对象与继承；断言、异常和错误处理；类型、初始化与数值；表达式、控制流与函数 |
| 外部输入、长度、索引、指针、循环边界或解引用 | C/C++ 边界、污点与解引用检查；内存、资源与空指针；字符串、容器、算法与格式化 |
| 资源、内存、线程、锁、文件、进程或外部命令 | 内存、资源与空指针；并发、文件、进程与外部命令；敏感信息、随机数与密码应用 |
| 头文件、宏、命名、注释或模板 | 头文件、命名空间与模板；预处理与宏；格式、命名与注释 |
| 性能接口、重复代码、复杂度、文件规模或设计重构 | Ascend 性能接口；规模、重复与检查质量；设计与可维护性；同时执行 ASC-26/ASC-27 |

同一变更命中多个信号时合并读取范围；不因规则来自不同批次或不同章节而跳过检查。

## 应用边界

- 用户明确要求和适用仓库规则优先；CANN/编译器/SoC 的真实能力必须满足。
  若通用建议与目标 API、C ABI 或设备侧限制冲突，采用兼容实现并记录原因。
- 函数长度和嵌套深度继续采用 ASC-26/27 的 50 行、3 层；细则中分析器的 30 行观察值、
  4 层配置不替代项目约定。分析器过滤、忽略项及分析失败不构成代码安全豁免或通过证据。
- Host 的 `std::string`、RAII、线程和 Secure C 库要求不自动适用于设备侧。
  不把 C++20 `std::span`/`std::erase_if` 引入仅支持 C++17 的构建。
- 本 Skill 不另行定义 AscendC 调用层级。AscendC 实现继续使用 `ascendc-ar-develop` 现有的
  host/device 调用约束、地址空间、tiling、内存搬运和架构校验。
- 需要例外时记录“规则编号、具体代码、不可替代的约束、安全前提和验证证据”。
  有意哈希回绕、必要的底层强转、稳定 C ABI 等要逐项判断，不能扩大为全局豁免。
- 只修饰风格不应引入行为变化；风险修复优先于格式清理。原始告警未涉及的推导建议在开发规范中明确标出。
